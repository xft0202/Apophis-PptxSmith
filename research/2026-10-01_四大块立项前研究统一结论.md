# 四大块立项前研究统一结论

日期：**2026-10-01**。状态：**所有者已确认四大块研究收口，不立项**。阶段：立项前研究。本文把竞品、需求、可行性与技术选型四块材料连接起来，供所有者判断是否继续、如何继续；不是立项批准、PRD、预算、技术终决或开发计划。

## 一、结论先行

当前证据支持继续保留一个可验证的产品方向，但**不支持现在启动完整独立产品开发**。问题线索真实存在，成熟方案也展示了若干可行机制；然而，本项目相对现有作者环境与成熟 AI 演示工具的完整工作链净收益尚未证明。

本轮最重要的判断轴已确认：**优先判断能否减少全流程返工**。全流程包括材料组织、目标和受众改编、内容与视觉调整、事实核对、局部修改、交付以及交付后的再次修改。首次生成更快、样页更漂亮或文件能打开，都不能单独证明值得自建。

当前条件性建议是：

- 把现有作者环境与成熟 AI 演示工具的组合工作链作为真实替代基线，不绑定具体厂商，也不代表采购或采用。
- 若未来验证显示主要价值来自跨材料、跨版本和跨交付环节的连续性，优先研究“产品层 + 可替换组件”这一架构假设；它只是候选，不是低成本或已选路线。
- 若问题只集中在一个现有应用的明确缺口，有限二开可能比独立产品更合适；若旧稿和既有编辑习惯是主约束，作者环境内辅助应作为竞争性路线。
- 若任务主要是网页演示、播放或阅读，网页主表达与按用途导出值得比较；但不能预先把网页导出等同于图片 PPTX，也不能把可编辑导出等同于原生图表和无损往返。
- 完整自研文件引擎与全功能产品暂不优先。只有当其他路线在关键任务上都无法承载价值，且文件级责任本身被证据证明值得承担，才应重新进入候选。

这些是研究建议，不是所有者选择。正式开发前还需要有界的完整任务证据，并由所有者重新确认范围、预算、技术路线和授权。

## 二、四块研究的统一判断

### 1. 竞品：机制已经存在，净收益没有被替我们证明

已完成的横向研究覆盖 SANDUN、Gamma、Canva、PowerPoint Copilot，以及 Presenton、PPTAgent、banana-slides、Anthropic pptx skill、frontend-slides、baoyu-slide-deck 和 Slidev 等开源项目／Skills。比较维度覆盖：

- 交互与生成流程；
- 页面设计与视觉机制；
- 内容生成与材料处理；
- 输出产物与后续修改。

可吸收的机制不是某家产品的完整功能全集：

| 观察到的机制 | 可借鉴之处 | 不应直接推出的结论 |
| --- | --- | --- |
| 大纲、材料、目标和页面阶段的组织 | 让用户能知道当前在处理什么，也能在材料、结构和视觉之间切换 | 固定阶段门或完整问卷一定适合所有任务 |
| 页级／元素级修改、版本与恢复 | 减少“每次修改都从头生成”的风险 | 有撤销入口就代表影响范围可解释、可控 |
| 模板、风格和既有稿件复用 | 让既有资产成为输入，而不是只在最后套模板 | 复制模板或导入 PPTX 就等于无损复用 |
| 图片页、形状页、原生对象和网页表达并存 | 按播放、阅读、改字、改数据等用途选择交付表示 | 任一表示是所有任务的质量标准 |
| 渲染、导出后检查和人工接手 | 把交付后的检查责任显式化 | 结构合法、能渲染或 HTTP 成功就是可用交付 |

SANDUN 的历史样本只能约束当时版本、材料和环境；其流程和产物是重要参考，不是当前全产品能力证明，也不产生“必须超过 SANDUN”的承诺。公开产品文档和源码能证明入口、机制或代码分支存在，不能证明本项目获得净省时、事实准确、持续采用或付费价值。

### 2. 需求：形成候选需求，不冻结首期功能

现有任务和痛点证据来自限定样本与公开材料，支持候选需求，但不能推出全体使用者的频率、市场规模或人群排除条件。用户可以自由组合目标、材料、修改和交付方式；研究探针不是产品白名单。

当前九项候选需求为：

| 候选需求 | 要解决的工作结果 | 主要反例或代价 |
| --- | --- | --- |
| R1 材料组织 | 看出重点、缺口和取舍，减少搬运与重排 | 提取遗漏、来源冲突、漂亮结构掩盖错误 |
| R2 目的／听众改编 | 改变重点、术语和叙事，而不是机械删字 | 目标冲突，询问和控制项增加负担 |
| R3 局部修改与恢复 | 保留有效成果，理解影响并在必要时回退 | 小改动引发重排，恢复成本高 |
| R4 旧稿、模板和风格资产复用 | 避免反复寻找版本或重建风格 | 旧对象复杂、许可不清、旧结论过时 |
| R5 数据及相关解释更新 | 数据变化后数字、图表和解释仍可核对 | 图片图表没有数据关系，自动联动可能误导 |
| R6 视觉表达与调整 | 能比较视觉方向并继续微调 | 主观偏好、字体和全稿一致性造成负担 |
| R7 适配后续用途的交付 | 交付前知道能否播放、阅读、改字或改数据 | 格式支持不等于保真和后续可编辑 |
| R8 可调整自动化程度与入口 | 从已有进度接续，不被固定问卷或全自动阻挡 | 控制项本身可能变成工具管理负担 |
| R9 可检查的反馈改稿 | 区分已处理、冲突和待判断意见 | 多人权限、批准和实时协作会显著加重范围 |

这些需求共同指向四项待证价值：修改延续、材料到表达少一次返工、视觉意图更易表达和调整、交付与后续用途衔接。研究优先级不是首期范围，也不代表所有需求都必须同时实现。

### 3. 可行性：机制可实现与产品值得做是两个问题

可行性证据分为五层：

| 层次 | 当前结论 | 尚未证明 |
| --- | --- | --- |
| 问题与任务 | 有限定样本的问题线索 | 总体频率、严重度、持续使用价值 |
| 单项机制 | 竞品文档和源码显示材料、提纲、局部修改、版本和导出机制存在 | 本项目任务中的质量和净负担 |
| 端到端工作链 | 固定 Presenton 可启动；无模型直接 JSON 路径有局部导出和 LibreOffice 渲染观察 | AI 生成、连续修改、交付后修改和完整检查 |
| 运行与维护 | 已识别模型、渲染、字体、外部服务、版本和人工接手等依赖 | 故障恢复、服务变化、支持责任和长期维护 |
| 经济与采用 | 已定义人工、等待、失败、返工和外部支出的记录口径 | 重复使用、替代成本、转换意愿和付费价值 |

因此，以下推理均不成立：

- 初稿漂亮，所以完整工作链可行；
- PPTX 生成成功，所以用户会少返工；
- 页面可渲染，所以交付后能继续修改；
- 有局部编辑，所以影响范围和恢复成本可接受；
- 模型返回结构化 JSON，所以事实正确、材料完整或依据可追溯；
- 一次指定模型失败，所以整个产品方向不可行。

当前已确认的记录原则是：主动人工与总交付历时分开记录，等待与人工可能重叠但不能忽略任务时限；材料核对、失败、重试、手工修复和放弃均要计入。没有实测数据就不填成功率、价格、工期、市场规模、收入或付费意愿。

### 4. 技术选型：比较责任边界，不先挑库

技术一手资料已从需求和可行性重新调查，未恢复旧候选排序。代表性来源包括 PptxGenJS、python-pptx、Open XML SDK、Aspose.Slides、Slidev、Docling 和 Office.js；它们用于说明能力边界，不是推荐清单。

| 架构路线 | 可能适合的条件 | 主要责任与反转条件 |
| --- | --- | --- |
| 网页主表达，按用途导出 | 视觉迭代、网页演示、播放或阅读占主导 | 需要维护网页与文件的表示差异；复杂元素、字体和换行可能降级。若交付后频繁改数据或结构，反转 |
| 直接文件对象表达 | 后续编辑、表格／图表对象和文件交付是主约束 | 需要承担对象图、布局、字体、预览、导入和未覆盖特性的处理；库能写文件不等于应用有状态 |
| 保留作者环境，辅助扩展 | 旧稿、模板和既有编辑习惯比迁移到新应用重要 | 受宿主、账号、API requirement set、分发和版本限制；若不接受宿主依赖或需要离线独立工作，反转 |
| 复用既有应用 + 可替换组件 | 现有入口／编辑工作链已接近目标，差异集中且接口可接受 | 必须核查状态格式、迁移、许可、上游升级和导出边界；二开若牵动全链，收益会被维护负担抵消 |
| 产品层 + 可替换组件 | 价值确实来自材料依据、任务状态、修改范围和跨交付衔接 | 要新增状态、失败恢复、人工接手和版本责任；如果任务级净收益不清楚，薄层会变成额外复杂度 |
| 完整自研文件引擎 | 其他路线均无法承载被证明重要的对象级责任 | 责任和成本最大，需同时证明用户价值和长期维护可承担；当前不优先 |

几个边界必须保持清楚：原生编辑、形状编辑、图片编辑、应用内编辑和 PPTX 往返不是同一个能力。Slidev 固定提交包含普通图片 PPTX 与 `pptx-editable` 路径；官方仍说明复杂元素可回退为图片、字体不嵌入、浏览器与 PowerPoint 的换行可能不同。python-pptx 的文档同时描述 Open XML 往返和未支持特性；Open XML SDK 明确是低层框架而非高层生产力工具。Aspose 的 Linux 运行条件和商业授权另有责任；Office.js 受 Authorized Apps 和分发条款约束。任何组件都不能替应用承担完整材料依据、状态、失败恢复和净收益证明。

许可应按最终分发清单审查：根仓库许可证不自动覆盖子目录、依赖、字体、模板、模型、素材或商业服务；商用库的评估模式也不能替代合同判断。技术报告中的版本、提交和来源见 [技术路径一手资料调查](2026-10-01_技术路径一手资料调查.md)。

## 三、当前推荐与竞争性替代

### 当前推荐：暂缓完整独立产品，保留有界路线比较

这不是“项目不可做”，而是现有证据还没有证明自建层能在完整任务上减少总负担。当前最稳妥的研究姿态是：

1. 以现有作者环境与成熟 AI 演示工具的共同工作链作为基线；
2. 用 T1「材料到初稿」、T2「既有稿局部修改」、T3「交付后继续修改」观察完整过程；
3. 先比较任务级差异，再决定是否需要产品层、二开、作者环境辅助或网页主表达；
4. 任何路线都保留人工接手、失败恢复和退出条件。

### 条件性路线判断

- **产品层 + 可替换组件**：只有当跨工具连续性、材料依据或修改范围被证明是基线无法承担的核心差异时，才值得进入重点候选。
- **有限二开**：如果只存在一个清晰、可局部修补且不会绑定完整上游的缺口，优先于从零建设；若必须接管核心编辑、导出和状态，退出。
- **作者环境内辅助**：如果 T2/T3 的主要负担是旧稿迁移和交付后编辑，且宿主 API 能覆盖关键操作，这条路线可能比新应用更贴近用户习惯；账号、版本和分发限制必须先接受。
- **网页主表达**：如果用户主要播放、阅读或进行视觉迭代，网页路线有竞争力；若“交付后继续修改”是核心，应对图片回退、字体、换行和外部改动覆盖做反例验证。
- **直接文件对象表达**：如果后续用途明确要求对象级修改，文件路线值得比较；但不能把文件库当作完整产品架构。

## 四、正式开发前的证据门槛

公开研究完成后，仍只允许给出条件性方案。正式开发前至少需要一次获授权的、有边界的完整任务比较，不能只验证单项导出或一次生成。比较样例由代理构造，不构成用户任务白名单。

### 最小比较结构

| 环节 | 必须记录 |
| --- | --- |
| 输入与目标 | 材料、目标用途、听众／时限、交付形式、允许的人工接手 |
| 基线与候选 | 现有工作链和待比较路线的实际步骤、版本、依赖与账号／服务条件 |
| 过程负担 | 主动人工、等待、检查、失败、重试、放弃和修复；等待与人工分开记录 |
| 内容与依据 | 材料是否遗漏、数字和引用是否可核对、改写／创作边界是否明确 |
| 视觉与表示 | 是否达到当前用途；字体、换行、布局、复杂元素和降级是否可见 |
| 修改连续性 | 局部修改是否影响无关内容；能否恢复；人工改动是否被覆盖 |
| 交付后变化 | 收件人一次新改字或改数据后，是否能继续工作而不是重做 |
| 运行与责任 | 数据去向、许可、依赖变化、失败接手、资源支出和维护动作 |
| 结果判断 | 是否成为“可用交付”；不达用途的产物不计为省时 |

### 必须保留的反例

- **材料变化反例**：源表更正后，图表数字变了但摘要仍声称“增长”。文件结构和 JSON 都合法，仍可能是错误交付；需要观察依据关联、失效提示和人工确认。
- **交付后编辑反例**：导出物中的收件人改了图片或形状，源稿再次导出覆盖这些修改；或关键图表已退化为图片，后续只能重新制作。能移动图片或形状不代表修改连续性成立。

### 停止信号

出现以下任一情况，应停止扩展该路线并保留研究资产：

- 相对基线没有清楚的任务级净改善；
- 核对、修复和交付后返工抵消了整理或生成收益；
- 关键依赖、许可、账号、数据去向或维护责任无法接受；
- 必须扩张到全格式、全对象、完整协作或完整自研，才能勉强证明价值；
- 证据仍停留在公开声明、静态代码、单次演示或局部结构检查。

停止某条路线不等于永久否定整个方向，也不意味着必须马上换另一条路线。

## 五、当前已确认与尚未确认

### 已确认

- 项目仍处立项前研究；不按职业、身份或人群设置使用资格。
- SANDUN 四个维度都纳入参考，但不照搬、不把它当唯一基线。
- 用户可自由组合目标、材料、修改和交付；研究样例不构成能力上限。
- 主判断轴是减少全流程返工。
- 交付按实际用途判断，明确限制和降级，不把文件后缀当作能力证明。
- 主动人工与总交付历时分开记录，按任务时限判断；失败、核对和修复计入。
- 正式开发前需要有界完整任务证据。
- 当前不正式立项、不定技术栈、不启动产品开发；Presenton 固定运行验证已封口。

### 尚未确认

- 首阶段具体任务组合、材料类型、外部目标软件和数值质量门槛；研究探针不能替所有者冻结这些内容。
- 是否建设产品层、采用二开、辅助作者环境、使用网页主表达，或继续直接采用现有工具。
- 是否需要对象级编辑、数据联动、版本合并、多人协作、账号、BYOK、自托管或长期发布支持。
- 可接受的预算、等待时间、人工接手、外部服务、数据边界和维护责任。
- 是否存在足以改变“不启动完整独立产品”建议的完整任务证据。

## 六、授权边界与下一步

本阶段可以继续做文档整合、公开一手资料核对、路线条件分析和决策讨论；未经另行确认，不自动执行：

- 产品实现或生产脚手架；
- 登录、付费或外部产品运行；
- 新模型调用、模型比较或 Presenton 继续排错；
- 办公软件安装或恢复 Windows／COM 验收链；
- 不可逆的路线、采购、发布或部署决定。

若所有者决定补强证据，最小下一步不是扩大功能，而是为 T1/T2/T3 各选一个有边界的任务，准备同材料、同用途、同记录口径的基线与候选比较。具体样例、工具、账号和外部服务在执行前单独确认。
