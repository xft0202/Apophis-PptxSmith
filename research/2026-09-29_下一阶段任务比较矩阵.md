# 下一阶段任务比较矩阵

日期：**2026-09-29**。阶段：立项前研究收口后的任务比较材料。本文保留 T1/T2/T3 的任务定义和证据边界，不是首期范围、PRD、验收标准、预算、技术栈或执行授权。

## 一、使用方式

本矩阵把下一阶段要比较的对象从“哪个模型或引擎”改成“哪类任务产生了什么结果”。默认基线是现有作者环境与成熟 AI 演示工具的共同工作链，不绑定厂商，也不代表采购、登录或采用。

每一项后续如获授权，均应同时记录：

- 输入材料、目标用途和交付形式；
- 基线做法与候选路线做法；
- 主动人工、等待、检查、返工、失败和放弃；
- 哪些结果是公开资料声明、哪些是静态代码证据、哪些是本机运行观察、哪些仍是推断；
- 交付后继续修改时是否仍保留有用成果。

没有后续授权时，本矩阵只作为决策材料，不运行工具、不调用模型、不使用非公开材料、不登录或付费。

## 二、三个默认任务原型

### T1：材料到初稿

| 项目 | 定义 |
| --- | --- |
| 任务问题 | 从一份或多份材料形成有讲述重点、适合目标受众和用途的初稿 |
| 典型输入 | 材料文件、主题／目标、受众、时长或交付形式 |
| 公开基线工作链 | 从提示词或文件开始，形成提纲／草稿，再由人增删、改写、复核 |
| 主要观察 | 材料搬运和重排是否减少；重点、缺口、事实依据是否更容易检查；系统是否让用户更快进入可修改状态 |
| 关联需求 | R1、R2、R6、R8 |
| A 的问题 | 现有作者环境或成熟 AI 工具是否已经足够；新增层是否只增加迁移、检查和账号负担 |
| B 的问题 | 复用某个现有应用，是否能以小改动减少已明确的整理或依据缺口 |
| C 的问题 | 产品层是否能稳定保存材料依据、任务状态和修改范围，而不是只串接一次生成 |
| D 的问题 | 现有作者环境内的辅助是否能减少整理，又不接管完整编辑器和文件链 |
| 不能直接宣布 | 初稿漂亮不等于事实正确；生成文件不等于材料理解、可修改或交付可用 |
| 停止信号 | 人工核对和修复抵消整理收益；依据无法追溯；受众改编需要反复重做；新增层不比基线更省事 |

### T2：既有稿局部修改

| 项目 | 定义 |
| --- | --- |
| 任务问题 | 在已有演示文稿上完成一次明确的内容、受众或视觉变化，同时保留无关的有效成果 |
| 典型输入 | 既有稿、单一修改请求、保留条件、目标受众／风格约束 |
| 公开基线工作链 | 在现有作者环境中选定页面或内容范围，改写／调整后人工检查全稿 |
| 主要观察 | 影响范围是否可预期；无关页面是否被连带改变；是否能看到依据、差异和回退点；修改后检查与返工是否减少 |
| 关联需求 | R3、R6、R8，必要时 R2 |
| A 的问题 | 现成工具是否已提供足够的局部编辑、版本或撤销能力 |
| B 的问题 | 应用已有状态和交互是否足以承载小范围二开，而不被升级和导出链绑死 |
| C 的问题 | 产品层是否真正掌握修改范围、来源和失败恢复；组件替换是否仍可行 |
| D 的问题 | 作者环境 API 是否覆盖目标操作；宿主限制是否小于自建编辑和转换负担 |
| 不能直接宣布 | 有内容路径更新不等于 PPTX 原位无损修改；有撤销不等于能解释影响范围；一次成功不等于连续修改稳定 |
| 停止信号 | 修改一个局部导致不可控的全稿变化；恢复依赖人工重做；对象／数据关系丢失；路线需要接管完整编辑器才能成立 |

### T3：交付后继续修改

| 项目 | 定义 |
| --- | --- |
| 任务问题 | 交付一个演示文稿后，面对一次新的内容或数据变化，继续修改而不是重新制作 |
| 典型输入 | 已交付稿、交付用途、一次后续修改、需要保持的对象和关系 |
| 公开基线工作链 | 在作者环境中打开交付物，定位文字、形状、图片、表格或图表，人工检查并再次交付 |
| 主要观察 | 对象能否继续编辑；图表／表格与数据关系是否仍可核对；降级是否在交付前可见；二次修改的人工修复量 |
| 关联需求 | R4、R5、R7，必要时 R3 |
| A 的问题 | 现有工具的交付路径是否已满足后续用途，复杂可编辑文件是否反而增加负担 |
| B 的问题 | 复用应用和导出依赖是否支持目标对象；二开是否会承担完整文件引擎责任 |
| C 的问题 | 产品层是否能保留作者依据和对象关联，同时让工具可替换；转换损失由谁承担 |
| D 的问题 | 宿主是否能在原作者环境内保留既有稿件、对象和修改习惯 |
| 不能直接宣布 | PPTX 结构合法不等于对象级可编辑；截图导出不等于原生对象；LibreOffice 渲染不等于所有办公软件兼容 |
| 停止信号 | 交付后必须重新整理；约定后续用途所需的关键对象退化且无法继续修改；数据和解释无法对应；人工修复负担超过基线；许可或依赖来源无法接受 |

## 三、证据分层

| 证据层 | 可以说明 | 不能说明 |
| --- | --- | --- |
| 官方产品资料 | 现有方案声明支持哪些入口、编辑动作和人工复核要求 | 本项目实际质量、成功率、净收益或适用性 |
| 竞品／公开源码 | 某些工作流、状态模型、导出分支或检查机制存在 | 这些机制在本项目任务中一定减少人工负担 |
| 本项目静态核查 | 固定版本代码具有什么分支和依赖边界 | 常规入口已经启用、对象级效果通过或路线值得采用 |
| 本机有限运行 | 固定环境下某条具体输入路径的启动、产物或错误结果 | R1/R2/R3 完整通过、连续修改成立、用户采用或长期运维可承担 |
| 任务级比较 | 某个代表性任务相对基线的人工与交付差异 | 所有任务、所有人群、所有格式都成立 |

## 四、路线比较记录模板

后续如有授权，每条路线只填写与三个任务原型直接相关的内容：

| 路线 | 主要假设 | 需要观察的最小差异 | 进入条件 | 退出条件 |
| --- | --- | --- | --- | --- |
| A 直接采用／有限整合 | 基线已经能完成任务，新增层没有足够净收益 | 现成工作链的质量、修改、交付和完整负担 | 核心任务可完成且平台边界可接受 | 关键任务缺失、账号／费用／数据边界不可接受，或不值得自建 |
| B 有界二开 | 现有应用接近目标，差异可以局部修补 | 一项明确差异是否能降低 T1/T2/T3 的负担 | 依赖来源、许可、升级和导出边界可接受 | 必须 fork 大量核心、来源不闭合或修复负担抵消收益 |
| C 产品层＋可替换组件 | 价值在任务状态、依据和修改控制，不在单个生成器 | 产品层是否减少跨工具丢失和失败恢复负担 | 组件边界清楚，额外状态确有任务级收益 | 薄层承担完整产品负担却没有清楚差异 |
| D 作者环境内辅助 | 价值应留在用户已有画布、稿件和习惯内 | 宿主内完成 T2/T3 的关键操作是否可行 | API、账号、分发和版本边界覆盖关键任务 | 宿主限制迫使自建完整编辑和文件链 |

这张表不用于打分，不自动选出最高路线；它只防止把“能实现”误写成“值得做”。

## 五、下一阶段的停止规则

以下任一情况成立，就停止继续扩展该路线：

1. 相对基线没有清楚的任务级净改善；
2. 材料核对、连续修改或交付后返工负担反而增加；
3. 关键依赖、许可、账号、数据去向或维护边界无法接受；
4. 需要扩张为全格式、全对象、完整协作或完整自研才能证明价值；
5. 证据仍只停留在公开声明、静态代码或单次演示，无法形成任务比较。

停止不等于项目永久不可做；它表示保留研究资产和重启条件，不用沉没成本推动下一阶段。
