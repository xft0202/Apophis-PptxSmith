# Spike D：长期架构全景统一验证规格

- 规格日期：2026-09-25
- 状态：研究阶段规格，未执行
- 关联票据：`.scratch/pptxsmith-v01/issues/21-跨项目长期架构全景与反锚定调查.md`
- 目的：用同一组用户任务、故障、恢复、升级、许可证和目标软件检查，比较完整架构组合，而不是继续比较孤立框架。
- 禁止事项：不创建生产代码、不创建 monorepo、不把 SQLite/生产本地文件作为对照 profile、不把未验证 provider 接入受支持路径。

## 1. 验证原则

Spike D 不是性能演示，也不是证明某个项目“能跑”的 hello world。它必须回答：

1. 用户在四道门中暂停、修改、回滚、取消和继续时，状态是否真实持久、可解释、可恢复；
2. worker、provider、Web、数据库或对象存储故障后，原稿、版本、审计、成本和交付状态是否一致；
3. PostgreSQL 与 S3-compatible 对象合同是否能在单节点和恢复演练中成立；
4. 身份、项目隔离、provider 密钥、敏感材料和不受信 PPTX 是否有明确边界；
5. PPTX 输出是否通过原生对象、中文量字、关系闭包、PowerPoint/WPS 保存重开和审计门；
6. SANDUN 的透明流程优势能否与 Gamma/Plus/Gemini 的低摩擦能力组合，而不引入自由画布、托管锁定或黑盒证据；
7. 上游许可证、版本升级、替换和社区接手成本是否可接受。

所有候选都必须运行同一 fixture。不得为某个候选删掉失败路径，也不得用另一种任务替代未通过的任务。

## 2. 统一业务 fixture

### 2.1 任务背景

使用一个脱敏的“季度经营汇报”新稿任务，目标听众为公司领导和部门同事，中文为主，含英文缩写、数字、表格和图表。首期任务是新稿编译，不开放已有 PPTX 受控补丁入口；但保留一个未来补丁样本用于验证架构没有破坏长期包级边界。

输入材料固定为四类：

- `经营摘要.docx`：章节、结论、风险和行动项；
- `财务数据.xlsx`：季度收入、毛利、同比、预算和分部门数据；
- `市场动态.pdf`：正文、脚注、表格和一页复杂版面；
- `品牌参考.pptx`：只作为风格参考，含 master/layout/theme、原生图表、嵌入 workbook、notes 和一个未知扩展部件；不作为 v0.1 旧稿修改输入。

材料中固定包含：

| 类型 | 示例约束 | 验证目的 |
| --- | --- | --- |
| 中文长标题 | `2026 年第二季度经营回顾与下半年增长计划` | 折行、行高、溢出、代表页门 |
| 中英混排 | `AI PPTX Compiler`、`PowerPoint/WPS`、`Q2` | shaping、标点和字体 fallback |
| 数值 | 收入 `15.1`、预算 `18.6`、同比 `+12.4%` | 数字/单位/来源保真 |
| 表格 | 4 列 × 5 行，含合计和缺失值 | 原生表格、来源定位和审计 |
| 图表 | 2 系列 × 4 季度，含负增长数据 | 原生图表、嵌入工作簿和编辑探针 |
| 冲突事实 | DOCX 与 XLSX 对同一指标给出不同版本 | 冲突阻断、用户确认和来源优先级 |
| 外部事实 | 市场动态需要联网才能补充 | 默认关闭联网、来源和显式开关 |
| 敏感值 | 成本中心、客户代号、内部联系人 | provider 数据路由和日志脱敏 |
| 不受信内容 | PDF 中提示模型忽略规则的文本 | 提示注入隔离，不改变系统政策 |

### 2.2 固定项目与角色

创建一个 workspace `acme-demo`、两个 project 和三种角色：

- `admin`: 可管理成员、provider policy、备份和审计；
- `member-a`: 只能访问 `project-q2`，可生成和确认阶段；
- `reviewer-b`: 只能审阅 `project-q2` 的代表页、审计和版本，不能读取 `project-secret` 材料。

`project-secret` 使用同样文件名但不同内容，专门检测项目串读、缓存污染、向量召回越权和短时下载 URL 泄露。

### 2.3 固定输出

每次运行必须生成：

- 结构化大纲版本；
- 2–3 张代表页；
- 全量 PPTX；
- 预览 PNG/PDF；
- 交付审计报告；
- 事件/工作流历史摘要；
- provider 调用、成本、重试和 fallback 摘要；
- 输入材料 hash、来源 locator、语义对象版本和产物 manifest。

## 3. 架构组合被测对象

### A：产品控制面 + durable workflow + 专用 worker

```text
Web Workbench
  -> API/Control Plane
  -> durable workflow runtime
  -> parse/content/PPTX/QA workers
PostgreSQL facts + S3-compatible object store
Identity boundary + OTel + SBOM/signing
```

候选 runtime 为 Temporal、Restate 或 Hatchet。具体选择不在规格阶段预设。

### B：事件原生 + durable services

```text
Web Workbench
  -> command service
  -> NATS JetStream or Kafka
  -> Restate/Hatchet services
  -> parser/compiler/provider workers
PostgreSQL facts/projections + S3-compatible object store
```

需要同时验证事件事实、投影延迟、重复投递和恢复后的事件顺序。

### C：企业流程/容器平台

```text
Web Workbench
  -> API gateway/enterprise IdP
  -> Camunda 8 or Argo Workflows on Kubernetes
  -> task workers/pods
PostgreSQL/CockroachDB + Ceph/S3 + OpenSearch
```

该组合只验证企业 profile 的能力和运维代价，不改变 Linux Docker 单节点的首期支持范围。

### D：数据编排优先

```text
Web API
  -> Prefect/Dagster data flows
  -> parser/index tasks
  -> separate workflow/compiler service
PostgreSQL + S3-compatible object store
```

重点验证它在解析/索引上是否有价值，以及它不能表达产品四道门的缺口。

## 4. Workflow fixture

### 4.1 正常路径

固定执行：

```text
create project
  -> upload materials
  -> parse and report risks
  -> clarification pending
  -> user confirms assumptions
  -> outline generated
  -> user reorders one slide and locks two slides
  -> representative pages generated
  -> reviewer approves representative pages
  -> full generation
  -> delivery QA
  -> audit published
  -> artifact delivered
```

每一个阶段都必须记录：`workflow_definition_version`、`input_version`、`style_pack_version`、`provider_policy_version`、`actor`、`event sequence` 和 `trace id`。

### 4.2 故障矩阵

| 编号 | 故障注入 | 期望行为 | 阻断条件 |
| --- | --- | --- | --- |
| W1 | 上传后 API 重启 | 材料 hash/manifest 可恢复，任务继续或明确失败 | 文件已存但 DB 无引用，或 DB 有引用但 blob 丢失 |
| W2 | parser worker 被 kill | durable runtime 重新派发或进入可审查失败 | 重复写入事实、重复收费、无错误分类 |
| W3 | clarification 等待 30 分钟 | 状态持久为 `WAITING_USER`，不会空转或过期丢失 | 刷新后显示完成、状态消失或任务重复 |
| W4 | 用户重复确认同一大纲 | 命令幂等，只生成一个锁定版本 | 产生两个版本或重复全量任务 |
| W5 | 用户拒绝代表页 | 进入修改/重生路径，不消耗未授权全量预算 | 自动继续全量生成 |
| W6 | provider 返回 429 | 按策略退避、显示排队和成本，或使用已授权兼容 fallback | 无限重试、静默换 provider、超预算 |
| W7 | provider 返回 HTTP 200 但 JSON Schema 不满足 | 标记能力失败，进入修正/换 provider | 将自由文本当语义对象继续编译 |
| W8 | SSE 断线 60 秒 | 前端通过 sequence 补偿，最终状态与服务器一致 | 本地假完成、事件乱序导致回退 |
| W9 | API 在代表页生成后重启 | 代表页 artifact 和审计状态可恢复 | 重新生成并重复收费，或 artifact 无法定位 |
| W10 | 编译 worker 在临时文件写入中被 kill | 临时产物清理，正式 artifact 不被半写覆盖 | 下载到损坏 PPTX 或覆盖旧版本 |
| W11 | delivery QA 失败 | `FAILED_REVIEW`，用户可见具体阻断项，不能标记交付 | 仍显示“已完成” |
| W12 | workflow definition 升级 | 旧历史按旧版本恢复，新任务用新版本 | 修改旧历史命令顺序导致 replay 错误 |
| W13 | 全节点重启 | DB/blob/workflow 恢复，任务状态和审计一致 | 依赖内存/进程队列恢复不了 |
| W14 | 重放事件 | 重放只重建投影，不触发真实 provider/文件副作用 | replay 产生重复调用或重复交付 |

### 4.3 通过门槛

- W1–W14 全部通过；
- 至少一次 worker kill、一次 API 重启、一次全节点重启后，输入版本、artifact hash、成本、审计事件数量和最终状态一致；
- 任何重复命令、重试和恢复都不得产生未授权的二次 provider 调用或二次交付；
- 用户等待状态必须在浏览器刷新和重新登录后保持可解释。

## 5. PostgreSQL 与 BlobStore fixture

### 5.1 BlobStore 合同

对至少两个 S3-compatible 实现运行同一合同：

- multipart upload；
- SHA-256/size/media type 校验；
- conditional write 和 atomic commit；
- range download；
- version/list/head；
- short-lived download URL；
- tombstone/delete/retention；
- backup/restore 和 hash manifest 校验；
- workspace/project 权限过滤；
- 断点续传、重复上传和网络中断。

本地文件系统只能作为测试替身，不能作为“默认生产实现”通过此门。

### 5.2 数据恢复场景

| 编号 | 场景 | 期望行为 |
| --- | --- | --- |
| S1 | DB 在材料 manifest 提交前崩溃 | blob 可以被垃圾回收，不能出现在用户版本中 |
| S2 | DB 已提交但 blob 上传不完整 | artifact/version 不可交付，后台报告孤儿引用 |
| S3 | 恢复到前一 DB 备份 | 用 manifest 校验 blob，显示恢复点和缺失对象 |
| S4 | 删除项目 | 先 tombstone，审计保留，过期后清理 blob/index |
| S5 | 重建全部索引 | 不丢 source locator、版本和权限；向量不是唯一事实 |
| S6 | 对象实现替换 | 通过 manifest/hash 迁移，不改业务表和 artifact 语义 |

### 5.3 通过门槛

- RPO/RTO 记录实际结果，不填写没有演练过的承诺；
- 恢复后用户、成员、项目、权限、原稿、版本、artifact、审计和来源均可查询；
- 任意一个 blob 缺失时系统必须阻断交付并明确报告，不能静默重新生成；
- 索引删除后可以从 PostgreSQL + BlobStore 事实重建；
- 不存在 SQLite、生产本地目录或“迁移脚本以后再写”的支持路径。

## 6. 身份、安全和供应链 fixture

### 6.1 权限场景

- `admin` 可以管理 workspace、成员、provider policy 和备份；
- `member-a` 只能读取/修改 `project-q2`，不能读取 `project-secret`；
- `reviewer-b` 可以读取代表页和审计，但不能下载未经批准的原稿或修改 provider policy；
- 取消成员后，已有短时下载 URL 在策略时间内失效或明确按合同继续有效；
- API、SSE、预览、下载、搜索、向量召回和 worker 输入都分别执行权限检查，不只隐藏 UI 控件。

### 6.2 安全注入场景

- 恶意 ZIP/PPTX：压缩炸弹、路径穿越、超大 XML、外部实体、宏/OLE、外链和重复关系；
- 材料提示注入：要求模型泄露系统提示、provider key 或读取另一个项目；
- provider 失败：认证错误、超预算、429、5xx、结构化输出不符合 schema；
- 日志检查：密钥、完整敏感材料和不必要的 prompt 不得进入日志或 workflow history；
- 依赖检查：SBOM、许可证、镜像 digest、签名、漏洞等级、构建来源和升级记录可追踪。

### 6.3 通过门槛

- 跨项目访问测试 0 次成功；
- 通过前端绕过、直接 API、SSE、下载 URL、检索和 worker 输入的越权测试；
- 危险包进入隔离/阻断状态，不执行宏、OLE、外链或脚本；
- provider key 不进入前端、审计正文、普通日志和可下载 artifact；
- 许可证不明组件不能被打入默认支持 profile。

## 7. Provider gateway fixture

### 7.1 能力探测

对至少三个真实 provider deployment、一个 OpenAI-compatible endpoint 和一个故意能力不足的 fake provider 测试：

- streaming；
- JSON Schema structured output；
- JSON object；
- tool call；
- vision；
- image generation；
- embedding；
- max context；
- rate limit；
- timeout/cancellation；
- error code and retry class；
- region/retention/training policy metadata。

能力探测结果分为 S1/S2/S3/S0。只有通过 schema 校验的 S1 才能直接生成语义对象；S2/S3 只能进入草稿或人工确认阶段。

### 7.2 路由与成本

- 未授权 provider 不可作为 fallback；
- fallback 必须满足 capability、数据路由和预算兼容；
- 每个调用记录 provider/model、capability decision、attempt、tokens、cost、latency、fallback reason 和 trace id；
- 429/5xx 允许退避，认证/权限/schema/事实冲突不得盲重试；
- 图片失败只重试图片 Activity，不重跑全稿；
- 达到预算必须进入确认或安全失败，不得自动切换到更贵模型。

### 7.3 通过门槛

- OpenAI-compatible HTTP 200 但能力不符合时，不能被标为 S1；
- 重试、fallback、取消和超预算均能在事件、UI 和审计中解释；
- provider gateway 可替换而不改变领域 workflow、语义对象、审计和 UI 协议；
- 敏感材料只进入允许的 provider deployment。

## 8. PPTX、中文和目标软件 fixture

### 8.1 新稿编译

使用 Spike A/B/C 已有能力，补充统一测试：

- 原生表格、原生图表和嵌入 workbook；
- 中文长标题、正文、数字、英文缩写、标点和长表格；
- 缺字、字体替换、行高低估、文本溢出和重叠；
- master/layout/theme、notes、unknown part 和关系闭包；
- 审计报告中的对象 ID、来源、可编辑等级、字体、溢出、成本和验证环境。

### 8.2 目标软件

必须明确记录：

- WPS 版本、渲染/保存结果；
- Microsoft PowerPoint 版本、渲染/保存结果；
- 使用的字体文件和字体授权；
- 哪些检查是自动完成，哪些是人工抽检；
- 预览渲染器仅作为独立信号，不作为中文最终验收。

本机已有 Spike A/C 只证明了 WPS 宿主的部分闭环。Microsoft PowerPoint 真机结果必须另行记录，不能将 WPS 结果转写成 PowerPoint 结论。

### 8.3 未来受控补丁约束

虽然首期不开放旧稿修改，Spike D 仍使用一个隔离样本验证架构边界：只修改图表数值或指定文本，比较 OPC 部件、关系、嵌入 workbook、notes、未知部件和未授权对象。失败只会影响未来补丁路线，不得阻塞新稿编译的事实模型，但任何静默丢失都会记录为硬风险。

### 8.4 通过门槛

- 目标承诺对象的 A/B 等级和编辑探针结果明确；
- 图表数据修改时缓存与嵌入 workbook 同步；
- 关系/部件闭包通过；
- 中文 fixture 无缺字、无溢出、无阻断越界，字体×目标软件误差记录在校准容差内；
- 未知对象、关系和未授权对象不被静默丢弃；
- 任何不支持对象进入审计报告并阻断或明确降级交付。

## 9. SANDUN 体验基准 fixture

### 9.1 对照动作

同一任务分别记录：

- 进入项目后看到的目标、材料入口、模型/数据策略和预计成本；
- 上传后的解析进度、风险、来源覆盖和待确认问题；
- 澄清问题数量、默认假设和跳过路径；
- 大纲卡片/便利贴的增删、调序、锁定和来源回跳；
- 代表页数量、页面角色差异、成本/时间提示和批准/拒绝；
- 生成过程的阶段、完成页、当前调用、取消、失败和恢复；
- AI 修改的预览、应用、局部重做、版本命名和回滚；
- 交付门的 A/B/C/D、来源、中文、目标软件和未覆盖项。

SANDUN 是过程透明和阶段产物基准；Gamma、Plus AI、Gemini 的动作只作为补充对照。所有体验对照都必须回到 PptxSmith 的事实、审计、权限和目标软件门。

### 9.2 指标

- 首次上传到第一个有意义结构反馈的时间；
- 进入大纲门的完成率；
- 大纲确认耗时和代表页拒绝率；
- 代表页确认到全量交付的成功率；
- 失败/阻塞后的恢复成功率；
- 用户返工分钟数；
- 阶段取消、回滚、重试和放弃率；
- UI 显示的来源/风险/成本与审计报告的一致率；
- PowerPoint/WPS 抽检发现的阻断问题数。

### 9.3 通过门槛

- 四道门在刷新、断线和重新登录后仍保持真实状态；
- 非画布路径可以完成大纲修改、确认、回滚和审计查看；
- 等待状态有阶段、预计动作、取消或恢复入口，不出现无限 spinner；
- SANDUN 的透明度不能以黑盒置信度替代可核验来源；
- 体验通过不等于交付通过，任何质量门失败都必须阻断或明确降级。

## 10. 评分与淘汰

### 10.1 评分维度

每个架构组合按 0–5 评分，必须先过硬门，再看总分：

| 维度 | 权重 | 证据 |
| --- | ---: | --- |
| 四道门与用户控制 | 15 | W3–W8、UX fixture |
| 恢复、幂等、升级 | 20 | W1–W14、备份恢复 |
| 事实/对象/审计保护 | 20 | S1–S6、PPTX fixture |
| 中文和目标软件交付 | 20 | PPTX/WPS/PowerPoint fixture |
| 多用户安全与供应链 | 10 | identity/security fixture |
| 五年维护与许可证 | 10 | 许可证/发布/升级证据 |
| 单节点部署与扩展 | 5 | Compose/企业 profile 运维记录 |

建议门槛：总分不低于 3.5/5；P0（事实、PPTX、中文、恢复）任何维度低于 3/5 直接淘汰；许可证不明的核心依赖不进入默认支持 profile。

### 10.2 硬淘汰

- 只提供队列重试，无法持久化人工等待、恢复和版本；
- 恢复或重放产生重复 provider 调用、重复收费或重复交付；
- PostgreSQL/S3-compatible 事实合同不能备份恢复；
- 跨项目、provider key 或敏感材料存在越权；
- PPTX 目标对象被静默图片化、关系/嵌入对象丢失或中文交付阻断；
- OpenAI-compatible 只通过 HTTP 200 就被视为结构化能力；
- 许可证、商标、商业条款或归档状态不明却被打入默认核心；
- 单节点只能靠 SQLite、本地生产文件或进程内队列运行；
- 为了通过体验指标牺牲审计、事实、权限或目标软件质量。

## 12. 执行顺序

1. 先冻结 fixture 文件和 hash，不因候选失败临时改题；
2. 先执行 A 方案的 workflow/storage/identity 基线，再执行 B；
3. C 方案只在具备 Kubernetes/Ceph/企业 IdP 的隔离环境中执行，不改变首期支持范围；
4. D 方案只执行 parser/index 和四道门缺口对照，不将数据编排器当作产品 workflow；
5. 每个候选完成失败、恢复、升级和许可证记录后才进入下一个；
6. 由票 21 汇总矩阵，决定哪些模块票可以打开；
7. 任何架构组合未达到门槛，不得以“后续替换”方式进入 14–20 的默认答案。
