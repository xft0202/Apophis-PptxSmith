# 实验记录：Spike C（.NET 路线同题验证）

*2026-09-24 | 本项目实测 | 背景：所有者对 ADR-0003（TS 全栈选型）明确不满意，要求换位重估*

## 方法

在 `mcr.microsoft.com/dotnet/sdk:8.0` 容器（与目标部署形态一致）内，用 DocumentFormat.OpenXml 3.1（MIT，微软官方）+ SkiaSharp 2.88 完成三项同题任务。脚本位于 `E:\tmp\pptx_spike_c\`（可丢弃 spike）。

## 结果

| 任务 | 内容 | 结果 |
| --- | --- | --- |
| C1 受控补丁（TS 路线根本做不到的事） | 打开 Spike A（PptxGenJS 产物），把图表 Q2 营收 15.1→88.8，**同步修改图表缓存值与嵌入工作簿**，不触碰其他部件 | ✅ 保存后 WPS 复检：工作簿 B3=88.8、系列缓存值 12.4,88.8,18.6,21.3、渲染随数据更新——**补丁闭环成立** |
| C2 量字对等 | SkiaSharp 度量同一段中文 14pt @6in | ✅ 与 fontkit **完全一致**：5 行、行高 0.257in、预测 1.283in（HarfBuzz 级整形，理论上比 fontkit 更贴近真实排版引擎） |
| C3 生成手感 | 以模板为底新增 1 页文本页 | ✅ 克隆路线成立；**从零建包（presentation/theme/master/layout 骨架）没有现成的"hello world"，需要自建脚手架封装**——SDK 是忠实 schema 层，不是电池included 的生成库 |

## 对三个候选路线的实测结论

| 维度 | TS + PptxGenJS | .NET + Open XML SDK | Rust 核心引擎 |
| --- | --- | --- | --- |
| 生成新稿 | 成熟、电池included | 可行但需自建脚手架库（C3 证实工作量集中在包装层） | 无现成库，一切自建 |
| **读/补丁/审计既有稿** | **基本不能** | **SDK 原生能力（C1 实测）**，自带 schema 校验（pptx-validate 免自研） | 需自建 |
| OOXML 覆盖深度 | 库暴露的子集 | 全 schema 强类型，微软官方持续维护 | 取决于自建进度 |
| 中文量字 | fontkit ✅（已实测） | SkiaSharp ✅（已实测，与 fontkit 一致） | 有 cosmic-text 等候选，未验证 |
| 与未来 Rust 客户端的关系 | 引擎到时整体重写 | 引擎留服务端，客户端=壳（Tauri+Web），**不需要重写** | 语言统一但风险前置 |
| 维护风险 | PptxGenJS 单维护者、footgun 多 | 微软官方、企业级 | 自担 |
| 贡献者生态（华语开源圈） | 大 | 中 | 小 |
| Docker/部署 | 轻 | SDK 镜像 ~800MB（运行时 ~210MB）， Alpine 可再瘦 | 轻 |

## 结论

**ADR-0003 的 TS 全栈选择被实测证伪了其核心假设**（"PptxGenJS 足以支撑编译基线"对生成成立，但它把读/补丁/审计/校验的全部重担留给了不存在的 JS 生态）。Spike C 证明 .NET 路线在三件关键事上同题及格，其中"受控补丁"是只有它过得去的科目。详细取舍与推荐见调研文档第十四节与 ADR-0009（待定）。
