# PPTX 主宿主与最终真相契约（研究阶段）

- 日期：2026-09-26
- 性质：纯研究与决策前审查，不是 ADR，不授权实现
- 当前状态：未选择引擎，未选择主宿主

## 1. 要先解决的问题

PPTX 不是“写入一次、所有软件都等价读取”的纯数据格式。最终交付至少涉及：

1. 逻辑内容和来源模型；
2. 生成/编辑引擎；
3. 模板、母版、版式和字体；
4. 目标软件及其精确版本；
5. 打开、编辑、保存、重开的行为；
6. 视觉渲染和对象级结构。

因此，“主宿主”不是部署细节，而是产物语义的一部分。

## 2. 四种不同的“真相”

### 2.1 逻辑真相

内容、事实来源、数据集、图表规划、页面角色和审计信息应由 PptxSmith 自己的中间模型负责。它不应等同于任意办公软件的当前显示结果。

### 2.2 作者真相

作者真相是生成或修改 PPTX 时使用的对象模型和保存引擎。例如：

- PowerPoint Desktop COM/VBA/VSTO；
- Aspose.Slides；
- Syncfusion Presentation；
- GemBox.Presentation；
- 模板加 OPC 包级局部编辑。

作者真相决定哪些对象能被创建、修改和保存，但不能自动证明目标软件重开后的行为。

### 2.3 主验收宿主真相

主验收宿主是产品承诺“最终可交付”的首要软件和版本。它必须拥有最高优先级的打开、编辑、保存、重开和视觉验收结果。

主验收宿主必须精确到：

- 软件名称和版本/build；
- 操作系统和架构；
- 32/64 位；
- 区域、语言和默认字体环境；
- 模板、主题、字体包和图表数据版本。

### 2.4 次级兼容宿主真相

次级宿主用于交叉兼容门禁，例如 WPS 或 PowerPoint 的另一方。它不是“主验收宿主的近似替代”。如果次级宿主保存了文件，产物可能已经进入另一套语义，必须重新做完整验收。

## 3. 为什么不能默认双宿主等价

### 3.1 PowerPoint 自身也不是单一运行环境

微软的 PowerPoint JavaScript API 以 requirement set 组织能力，客户端需要通过运行时检查或清单声明确认 API 是否可用。这说明“PowerPoint”不能只写成一个不带版本的名称。

PowerPoint Desktop、PowerPoint for Mac、PowerPoint for the web 的对象模型、自动化入口和能力范围也不应未经证据就视为相同。

### 3.2 PowerPoint 兼容模式承认版本之间可能有能力损失

微软官方兼容模式资料明确提供兼容性检查，并提醒保存到旧格式时某些功能可能丢失或降低。这不能直接证明所有 PPTX 版本都会发生同样问题，但足以说明版本/格式契约必须显式记录。

### 3.3 PowerPoint 与 WPS 不是同一个保存引擎

WPS 官方材料把跨软件差异归因于字体、版本、母版、嵌入对象、复杂动画和特殊效果等因素，并建议在最终指定软件中检查。该材料是用户指导，不是完整对象级 API 规范；但它支持一个保守结论：

> “都能打开 PPTX”不能推出“都以相同方式解释、编辑和保存 PPTX”。

### 3.4 独立 SDK 不是办公软件的透明代理

- Aspose 的官方资料声明可加载/保存多种 PowerPoint 格式，同时提醒不支持或特殊内容可能被规范化、遗漏或显示不同；
- GemBox 明确提供 unsupported feature preservation，但这是 GemBox 自己的读写机制声明；
- Syncfusion 的资料覆盖大量演示对象和转换能力，但对象 API 覆盖不等于 PowerPoint/WPS 保存结果等价。

所以，独立 SDK 的“支持 PPTX”应拆为：对象 API、序列化、未支持内容保留、图表工作簿、目标宿主重开五个独立问题。

## 4. 主宿主策略矩阵

| 策略 | 作者真相 | 主验收真相 | 强项 | 不能自动宣称 |
| --- | --- | --- | --- | --- |
| PowerPoint-first | PowerPoint Desktop | 指定 PowerPoint Desktop | 宿主对象模型和保存保真潜力最高 | WPS 等价、适合无人值守服务 |
| 独立 SDK-first | Aspose/Syncfusion/GemBox 等 | 指定 PowerPoint 或 WPS | 服务端/跨平台和可锁版本路线更自然 | 等同办公软件原生保存 |
| WPS-first | WPS 自动化或 WPS 相关接口 | 指定 WPS | 贴近既有 WPS 交付环境 | 已具备完整图表工作簿、备注、母版和未知关系契约 |
| Dual-primary | 两套作者/保存路径或一套作者加两套验收 | PowerPoint 与 WPS 同等必需 | 交付范围最宽 | 用单一宿主证据代表另一宿主 |
| Template/OPC-first | 模板和包级策略 | 由项目另行指定 | 未修改结构理论上更可控 | 自由生成、关系安全和跨软件保真天然解决 |

## 5. “双宿主”应如何解释

如果业务确实要求 PowerPoint 和 WPS 都能编辑交付，必须在需求层明确以下三种含义中的哪一种：

### A. PowerPoint 主宿主，WPS 只读/预览门禁

- PowerPoint 的对象和保存结果是唯一主真相；
- WPS 只负责打开、预览和报告明显兼容问题；
- WPS 保存后的文件不能直接回流为新的基线。

### B. PowerPoint 与 WPS 都是可编辑主宿主

- 两者都是主验收宿主；
- 每个对象语义必须有双向保存/重开证据；
- 任何只在一方可编辑、另一方图片化或丢失的对象必须被阻断、降级或隔离；
- “一份 PPTX 同时完美满足双方”只能作为测试结论，不能作为先验假设。

### C. 独立 SDK 是作者，PowerPoint/WPS 分别是验收宿主

- SDK 保存输出是作者基线；
- PowerPoint 和 WPS 分别作为交叉验收宿主；
- 任一宿主发生静默图片化、关系变化、字体漂移、工作簿丢失或备注/母版变化，都必须记录为该版本组合的兼容边界。

## 6. 版本契约的最小字段

在任何最终引擎选型前，版本矩阵至少要包含：

| 字段 | 示例含义 |
| --- | --- |
| 作者引擎 | 名称、精确版本、构建号、运行时 |
| 作者宿主 | PowerPoint/WPS/独立 SDK，以及是否需要 Office 安装 |
| 主验收宿主 | 名称、版本、build、位数、操作系统 |
| 次级验收宿主 | 名称、版本、build、位数、操作系统 |
| 模板 | 模板 hash、母版/版式版本、主题版本 |
| 字体 | 文件清单、版本、替代字体规则 |
| 输入 | 内容、数据、图表规划和来源快照 |
| 保存方式 | 直接保存、另存、格式转换、宿主重存 |
| 环境 | 区域、语言、默认打印机/渲染依赖、网络/外链条件 |
| 结果 | 包部件、关系、对象清单、视觉快照、宿主日志 |
| 变更规则 | 哪些升级触发重新验收、如何回滚 |

## 7. 选型的硬性顺序

研究阶段按以下顺序推进：

1. 声明逻辑真相与 P0/P2 最低语义；
2. 声明作者候选、精确版本和运行时边界；
3. 声明主/次级验收宿主、版本及是否允许保存回流；
4. 再比较 PowerPoint 原生作者与独立 SDK 作者；
5. 最后决定是否授权真实产物验证。

主验收宿主是验收矩阵的必要字段，但不是把作者路线预先锁死的锚点。

## 8. 吸收分类

| 对象/机制 | 吸收分类 | 边界 |
| --- | --- | --- |
| SANDUN 阶段、确认节点、页面级重排 | **适合二开** | 只进入产品流程和状态模型 |
| SANDUN `chart_plan` | **可直接复用** | 进入图表规划和审计契约，不决定最终 OOXML 实现 |
| PowerPoint 兼容性检查的思想 | **适合二开** | 作为版本/功能风险报告，不把它当跨宿主保真证明 |
| PowerPoint Desktop 对象模型 | **仅可借鉴** | PowerPoint-first 候选，尚未定案 |
| GemBox preservation 声明 | **仅可借鉴** | 必须区分官方声明与项目夹具实测 |
| WPS 用户指导中的跨软件差异提示 | **仅可借鉴** | 不是完整对象级 API 证据 |
| 不绑定验收矩阵就宣称“普适最优引擎” | **应当淘汰** | 研究可以先比较作者能力，交付结论必须绑定宿主与版本 |
| SANDUN 形状展平/整页 SVG 导出 | **应当淘汰** | 与原生可编辑产物目标冲突 |

## 9. 当前结论

本轮研究不选择 PowerPoint、WPS、Aspose、Syncfusion、GemBox 或 OPC 作为最终答案。

当前可以冻结的研究结论是：

> **PptxSmith 先按 P0/P2 语义研究作者路线；任何最终选型和交付声明，必须绑定“逻辑真相—作者引擎—主验收宿主—次级宿主—版本契约”五元组和真实产物证据。**

作者与验收宿主是正交轴。冻结验收矩阵是实际比较与发布的必要条件，不是研究作者路线的先决锚点。

如果项目坚持 PowerPoint/WPS 双编辑交付，那么双宿主交集，而不是任一宿主的单方能力，才是实际产品上限。
