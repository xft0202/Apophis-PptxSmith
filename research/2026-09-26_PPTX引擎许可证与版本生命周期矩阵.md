# PPTX 引擎许可证、版本生命周期与回滚矩阵（研究阶段）

- 日期：2026-09-26
- 性质：路线研究，不是 ADR，不是采购决定，不授权实现或 benchmark
- 目标：比较主宿主候选和独立 SDK 的许可、版本、部署、支持、回滚与产物风险
- 证据规则：官方条款可以证明“供应商如何声明”；不能证明本项目固定模板和目标宿主已经通过

## 1. 研究结论先行

本矩阵不产生唯一排名。它只能说明：

1. 许可证不是“免费/商业”二元判断，还包括开发者数、收入、融资、政府项目、维护期、版本权利和部署权利；
2. 版本可复现不仅是锁定 NuGet/package，还包括字体、模板、渲染依赖、Office build、宿主更新通道和授权 key；
3. 回滚能力必须区分“可以恢复软件版本”和“恢复后仍然保持同一 PPTX 语义”；前者不自动推出后者；
4. WPS 当前缺少同等级的公开授权、版本支持和演示对象语义资料，因此不能在许可/生命周期维度与其他候选并列定案。

## 3. 逐路线证据与解释

### 3.1 PowerPoint Desktop / Office LTSC

Microsoft 的 Office LTSC 2024 官方页面明确：

- Office LTSC 2024 通过批量许可提供；
- 它面向不能接受持续功能更新的受监管或受限环境；
- 发布后不接收功能更新；
- Mainstream Support 为五年，之后没有 Extended Support；
- 与 Microsoft 365 Apps 不是同一产品。

这给 PowerPoint-first 路线提供了一个可锁版本的方向，但不改变 Microsoft 对无人值守服务端 Office 自动化“不推荐且不支持”的边界。PowerPoint-first 必须因此被理解为受控 Windows 作者/验收环境，而不是普通 Linux API 服务。

Microsoft 365 Apps 的 Cloud Update 文档还明确：暂停和回滚只对由 Monthly Enterprise profile 管理的设备可用，并且回滚到有限的先前 Monthly Enterprise 版本。不能把它泛化成所有 Office 安装都有任意版本回滚能力。

### 3.2 Aspose.Slides

官方许可页明确：

- 未授权评估会产生水印等限制；
- 许可证在本地验证，不要求联网；
- 订阅结束后仍可继续使用订阅结束前发布的版本；
- 要使用更新版本需要续订。

官方支持页还明确：

- 可以继续使用旧版本；
- 修复只提供给当前 release；
- 不为 legacy versions 发布补丁。

因此 Aspose 的运营策略必须是：保留已验证的包和运行时，不能把“以后发现问题再等旧版本补丁”当作计划。升级必须是新版本、新产物和目标宿主矩阵重新验收。

### 3.3 Syncfusion Presentation

官方 Community License 页面明确资格条件包括：

- 年总收入低于 100 万美元；
- 开发者不超过 5 人；
- 总员工不超过 10 人；
- 外部融资累计不超过 300 万美元；
- 政府相关组织通常不符合，部分非纳税资金组织需另行审查。

官方协议还把维护/支持订阅、修改后的二进制、升级和持续开发权利联系起来。因本项目未来规模、组织身份和交付对象可能变化，不能现在把 Community License 当作长期商业成本结论。

Syncfusion 文档显示 .NET 支持范围会随版本演进，当前文档示例涉及 .NET 8/9/10。项目若采用它，必须锁定确切 SDK、runtime 和 license key 规则，而不能只锁定一个大版本名称。

### 3.4 GemBox.Presentation

官方 FAQ 和价格页明确：

- 授权按开发者计算；
- 不需要额外 server/OEM license；
- 可无限部署；
- 许可证是永久的；
- 支持期结束后可以继续使用有权使用的最新版本；
- 只有续订后才能使用支持结束后发布的新版本。

官方发布页采用日期版本号，并记录跨平台渲染、字体 fallback、关系修复等变化。这对复现有利，因为版本边界清晰；但也说明升级可能改变渲染或部件行为，必须把日期版本纳入产物契约。

### 3.5 WPS

当前研究没有获得同等级的官方资料来确认：

- 演示对象模型的完整版本支持；
- 图表和嵌入工作簿的授权 API；
- 备注、母版、未知关系的保存契约；
- 服务端/自动化许可边界；
- 旧版本维护、安装包回滚和精确 build 支持。

因此 WPS 的正确落位仍是“证据不足、继续研究”，而不是“免费所以优先”或“历史验收版本所以最优”。

## 4. 版本回滚的正确含义

| 层级 | 能回答的问题 | 不能回答的问题 |
| --- | --- | --- |
| 包管理回滚 | 能否恢复某个 SDK/DLL/NuGet 版本 | 该版本生成的 PPTX 是否满足目标软件 |
| 运行时回滚 | 能否恢复 .NET/JVM/Windows/Office build | 字体、模板和系统渲染是否一致 |
| 模板回滚 | 能否恢复母版、版式、主题和初始部件 | 宿主保存后是否仍保留关系与缓存 |
| 宿主回滚 | 能否回到某个 PowerPoint/WPS 版本 | 另一宿主是否具有相同语义 |
| 产物回滚 | 能否恢复曾交付的 PPTX 和审计清单 | 新版本是否能够重新生成同样字节和视觉结果 |

项目需要的不是“能回滚”口号，而是可组合的版本坐标：

```text
作者引擎版本
+ 运行时版本
+ 主宿主版本/build
+ 次级宿主版本/build
+ 模板/母版/字体 hash
+ 输入数据/来源快照
+ 许可证/授权 key 适用范围
+ 产物对象和视觉验收记录
```

## 5. 对选型的实际影响

### 可以接受的情况

- 供应商允许长期使用一个固定版本；
- 项目能够保存对应的安装包、许可证证明和运行环境；
- 目标宿主版本可以固定；
- 升级前后能够重新进行对象级、视觉级和双宿主验收；
- 旧版本发生问题时，项目不依赖供应商为 legacy version 发布补丁。

### 必须降级或隔离的情况

- Community License 的组织资格可能在产品生命周期内变化；
- 只能获得试用授权，正式产物带水印或抽取受限；
- 供应商不维护旧版本，而项目又无法自持修复和回滚；
- Office/WPS 更新由用户环境自行发生且无法锁定；
- 模板、字体、图形依赖或 license key 未纳入版本坐标；
- 回滚只能恢复代码版本，不能恢复目标 PPTX 的对象和视觉语义。

## 6. 吸收分类

| 对象/机制 | 吸收分类 | 当前边界 |
| --- | --- | --- |
| Aspose 的固定版本 + 本地离线许可思路 | **可直接复用** | 只复用版本和许可留档原则，不预判采用 Aspose |
| GemBox 的开发者授权、无限部署和日期版本记录 | **仅可借鉴** | 作为供应商合同/版本审查样例，不代表项目采购结论 |
| Syncfusion Community License 资格模型 | **仅可借鉴** | 用于商业资格审查，不能作为长期免费前提 |
| Office LTSC 的固定版本和固定生命周期思路 | **适合二开** | 进入宿主版本契约；不等于允许服务端无人值守自动化 |
| Microsoft 365 Cloud Update 的暂停/回滚概念 | **适合二开** | 可借鉴运维门禁，但适用范围有限 |
| WPS 当前未形成的版本/许可矩阵 | **必须隔离** | 在证据补齐前，不得作为主宿主或主引擎结论 |
| 无版本坐标的“永远兼容”承诺 | **应当淘汰** | 与可复现交付和审计冲突 |
| 只记录 SDK 名称、不记录模板/字体/宿主 build | **应当淘汰** | 不足以解释产物差异 |

## 7. 当前结论

这张矩阵没有选出最终引擎，但把下一步的证据门槛收紧为：

1. 许可证必须允许项目实际的开发、构建、部署、客户交付和长期维护；
2. 版本必须可锁定，且供应商的旧版支持策略不能成为隐性单点风险；
3. 回滚必须能恢复作者环境、主宿主环境和产物审计坐标，而不只是恢复一个依赖包；
4. 任何候选仍需通过固定模板、固定数据和固定 PowerPoint/WPS 版本的真实产物验证；
5. 在这些条件满足前，PowerPoint、Aspose、Syncfusion、GemBox 和 WPS 仍是条件性路线，而不是最终答案。
