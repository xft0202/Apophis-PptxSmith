# SANDUN 全流程实测报告：内部数据结构与产物真相

- 实测日期：2026-09-25
- 实测方法：**发现其公开回放数据端点 → 拉取 4 份官方案例的完整内部数据 → 逐层解构**
- 数据规模：4 份 × 约 800KB = 3.3MB 原始 JSON
- 证据级别：**本项目实测**（抓取到的原始内部数据，可复查、可复现）
- 抓取产物：`research/experiments/sandun-raw/replay-data/*.json`、`slides-svg/*.svg`

> **本文档的价值**：此前所有 SANDUN 研究都是**二手推断**（看界面、看文档、看截图）。
> 本报告是**第一次拿到它内部数据结构**，可以对它的技术路线做**结论性判断**，不再依赖推测。

## 2. 阶段序列（实测，非文档推断）

从 `timeline` 事件中提取出阶段推进顺序。**四份案例的阶段序列并不相同**，
取决于输入通道（一句话 / 需求文档 / 参考资料 PDF）——这是比"统一流水线"更准确的观察：

| 案例 | 输入通道 | 阶段序列 | slides | timeline |
| --- | --- | --- | ---: | ---: |
| 正泰电器企业介绍 | 一句话 | `init → preliminary_research → content_requirements → outline → search_list_generation → deep_research → drafting → design → completed` | 13 | 269 |
| 北京五日游攻略 | 一句话 | `init → content_requirements → preliminary_research → outline → search_list_generation → deep_research → drafting → design → completed`（阶段有反复） | 14 | 208 |
| Dify 产品技术架构 | 一句话 | `init → content_requirements → preliminary_research → outline → search_list_generation → deep_research → drafting → design → completed`（阶段有反复） | 12 | 190 |
| 小米 2025Q3 业绩 | **上传参考资料 PDF** | `init → **pdf_parsing** → outline → drafting → design → completed` | 23 | 305 |

**三条关键差异**：

1. **PDF 通道是更短的路径**：`pdf_parsing` 替代了「背景调研 + 内容需求单 + 搜索清单 + 深度检索」四个阶段；且该案例多出 `pdfOutlineSurveyForm` 字段（对应其文档说的"生成大纲前先确认三个偏好"问卷）。
2. **一句话通道的阶段会反复**：北京五日游与 Dify 两条都出现 `content_requirements → preliminary_research → content_requirements` 这类回跳，说明它的阶段机**允许重入**，不是单向流水线。正泰那条则是干净的单向推进。
3. **"八阶段"是并集**：一致出现的核心阶段是 `init / outline / drafting / design / completed`，
   其余（`preliminary_research`、`content_requirements`、`search_list_generation`、
   `deep_research`、`pdf_parsing`）按输入通道与是否联网而增减。

事件类型分布（正泰电器案例，269 条）：

| event_type | 条数 |
| --- | ---: |

| `search_page_progress` | 22 |
| `step_status_update` | 18 |

| `search_plan_ready` / `style_recommendations_ready` / `style_selected` | 各 1 |

| --- | ---: |

## 3. 决定性证据：图表是 SVG 自绘，不是原生图表部件

### 3.1 图表槽位统计（四份案例全量）

| 案例 | 页数 | 图表槽位 | 类型分布 |
| --- | ---: | ---: | --- |
| Dify 产品技术架构 | 12 | 2 | progress ×1, horizontal-bar ×1 |
| 北京五日游攻略 | 14 | 3 | donut ×2, horizontal-bar ×1 |
| 小米 2025Q3 业绩 | 23 | 19 | bar ×14, line ×3, pie ×2 |
| 正泰电器企业介绍 | 13 | 6 | bar ×6 |

> **勘误（2026-09-25）**：本节初版把两个 replayId 与案例名对错了，
> 导致「小米」与「正泰」两行的页数与图表数互换。现已按
> `project.title` 校正，并在抓取器中加入 `project.title` 自校验，
> 防止再次错配。结论方向不变（四份案例的 `chartPlans`/`imagePlans`/
> `diagramPlans` 全部为空、图表均为 SVG 自绘），受影响的只是按案例的计数。

**`chartPlans`、`imagePlans`、`diagramPlans` 四份案例全部为空 `{}`。**

### 3.2 图表的真实实现（原始 SVG 片段）

```svg
<!-- Chart Slot 1 -->
<g data-chart-slot-id="chart-1" data-chart-type="bar" transform="translate(30, 220)">
  <rect x="0" y="0" width="530" height="130" rx="8" fill="#F8F9FA"/>
  <line x1="50" y1="90" x2="510" y2="90" stroke="#EEEEEE"/>
  <text x="38" y="94" text-anchor="end" font-size="10" fill="#64748B">0</text>
  <text x="38" y="82" ...>50</text>
  ...（7 条网格线 + 刻度文本）
  <path d="M 56 90 L 56 77.29 A 4 4 0 0 1 60 73.29 L 270 73.29 A 4 4 0 0 1 274 77.29 L 274 90 Z" fill="#FF6700"/>
  <text x="165" y="65.29" text-anchor="middle" font-size="14">69.6亿元</text>
  <text x="165" y="114" font-size="12">2024前三季度</text>
  <path d="M 286 90 L 286 62.8 ..." fill="#333333"/>
  <text x="395" y="50.8">130亿元</text>
  <text x="395" y="114">2025前三季度</text>
  <line x1="42" y1="90" x2="510" y2="90" stroke="#CCCCCC"/>
</g>
```

**结论性判断**：

1. 图表**不是** OOXML 的 `<c:chartSpace>` 原生图表部件，而是**用 SVG 图元手工绘制的**——坐标轴是 `<line>`、刻度是 `<text>`、柱子是**带圆角的 `<path>` 路径**、数值标签是 `<text>`。
2. 数值是**烤进 text 的字符串**（`69.6亿元`），几何位置是**预先算好的绝对坐标**（`y=73.29`）。**数据与图形之间没有可分离的绑定关系。**
3. 存在 `data-chart-slot-id` / `data-chart-type` 元数据标记，说明导出时它是**靠这些标记逆向重建**成 PPTX 图表的——这是**从渲染结果反推语义**，不是保留语义。

**这条把此前的"推断"升级为"实测结论"**：它的图表数据在生成管线内部就是**渲染产物**，而非数据模型。因此：

- 在画布内改图表数据"实时刷新"是**重绘 SVG**，不是改数据源；
- 导出到 PPTX 时的图表重建，**保真度取决于逆向解析的完备性**；
- 一旦用户在 PPTX 里改了数据，**没有任何机制同步回其内部表示**（因为内部根本不存在可编辑的数据模型）。

### 3.3 SVG 元素规模（四份案例）

| 案例 | 页数 | SVG 总长 | rect | path | circle | text |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Dify 产品技术架构 | 12 | 94,902 | 149 | 41 | 59 | 263 |
| 北京五日游攻略 | 14 | 114,574 | 209 | 51 | 50 | 351 |
| 小米 2025Q3 业绩 | 23 | 179,529 | 297 | 79 | 50 | 568 |
| 正泰电器企业介绍 | 13 | 98,800 | 136 | 46 | 80 | 317 |

（元素计数为整份演示文稿的 SVG 源码统计，由抓取器按案例重新汇总。）

**全部零 `<chart>` 标签**，纯图元堆砌。单页 SVG 约 6–12KB。导出到 PPTX 时这些图元会被整体**"转换为形状"**，这正是"形状级可编辑"（B 级）的技术根源——**文字能改，图表语义改不了**。

## 4. 字体依赖：外部 OSS + 运行时 CSS @import

每份案例的每页 SVG 都带 3 个**外部字体 @import**：

```text
https://content-sandunppt.oss-cn-guangzhou.aliyuncs.com/fonts/HarmonyOS_Sans_SC_Regular/result.css
https://content-sandunppt.oss-cn-guangzhou.aliyuncs.com/fonts/HarmonyOS_Sans_SC_Bold/result.css
https://content-sandunppt.oss-cn-guangzhou.aliyuncs.com/fonts/SourceHanSerifCN-Bold/result.css
```

**技术含义**：

- SVG 通过**阿里云 OSS 上托管的字体 CSS** 渲染中文，`class="ppt-font-cn-heading"` / `ppt-font-cn-body` 是自定义字体类名；
- 这意味着**预览渲染依赖外网**——断网或 OSS 不可达时，中文渲染会回退；
- 这也解释了它为什么要求用户**导出后自行安装字体**：字体没有嵌入产物，只存在于其 OSS。

**这正是 PptxSmith 的正面差异点**：我们的中文量字 + 溢出审计是**离线可算、产物自包含**的。ADR-0004 的自托管承诺在这里得到实证支撑——**它的架构决定了它无法自托管**。

## 5. 风格系统的内部结构（完整设计令牌）

`styleConfig` 字段揭示其风格规范的真实结构：

```json
{
  "aiRecommendations": [ 4 套推荐风格 ],
  "chartTheme": { 21 个字段 },
  "globalBackgroundSVG": "<g id='bg'>...</g>",
  "globalHeaderSVG": "<g id='header'>...</g>",
  "keywords": [...],
  "colorRequirement": "free",
  "backgroundRequirement": "custom"
}
```

`chartTheme` 的 21 个字段（实测）：

```text
areaOpacity, axisColor, axisWidth, backgroundColor, barRadius,
donutInnerRatio, frameColor, frameRadius, frameWidth, gridColor,
gridDasharray, labelColor, labelFontSize, legendFontSize, ...
```

AI 推荐风格的结构：

```json
{
  "style_name": "寰宇蓝图 (Industrial Tech)",
  "style_reason": "专为正泰电器作为行业领航者的身份设计。采用理性的'正泰蓝'结合精密工业网格，体现电力行业的严谨与智慧能源的科技感。",
  "keywords": [...],
  "chart_theme": {...},
  "global_background_svg": "<g id='bg'>...</g>",
  "global_header_svg": "<g id='header'>...</g>",
  "preview_svg": "<svg viewBox='0 0 320 180'>...</svg>"
}
```

**值得吸收的设计**：

- **风格 = 设计令牌 + 全局 SVG 片段**（背景层、页眉层）+ 图表主题，三件套；
- **`style_reason`**：每套推荐都带一段"为什么这样设计"的说明，直接面向用户；
- **`preview_svg`**：风格卡预览是真实 SVG，不是截图；
- **`global_background_svg` / `global_header_svg` 是 SVG 代码而非参数** —— 灵活但不利于跨引擎复用。

**我们的补强点**：这些令牌与 SVG 片段是**绑死在它的 SVG 渲染器上**的。我们的风格包必须做成**引擎无关**的开放结构（ADR-0005），并且能**从既有 PPTX 提取**（它只能从图片提取）。

## 6. 检索数据的真实结构

`searchResults` 是逐页组织的：

```json
[{
  "keyword": "正泰电器 昆仑系列 低压电器 产品参数 应用场景",
  "page_key": "page-frq7s2km",
  "results": [{
    "title": "昆仑系列 - 正泰新品 - 产品中心  正泰电器",
    "url": "http://www.chint.net/kunlun/news/news_det.php?id=1010162",
    "snippet": "...",
    "summary": "...",
    "authInfoDes": "",
    "rankScore": null
  }]
}]
```

**关键观察**：

1. **检索词是按页生成的**（`keyword` + `page_key` 绑定），不是全局一个查询——这与我们"逐页来源定位"的设计一致；
2. **有原始 URL 与标题**——来源是真实的，可追溯；
3. **`authInfoDes` 与 `rankScore` 字段存在但为空** —— 说明它有预留权威性/排序评分的位置，但**未启用**；
4. **这正是"置信度"那个黑盒数字的来源**：界面上显示的置信度是**前端计算或额外字段**，而底层检索数据里没有可核验的评分依据。

**对我们的启示**：我们做事实保真时，**不要发明一个新数字，要把这些字段填实**——来源 URL、原文片段、以及**材料内冲突标记**。

## 7. 成本数据结构（仅供技术参考）

`cost_update` 事件记录了项目累计消耗与账户余量，形如：

```json
{ "project_cost": 6,   "total_available": 21831 }
{ "project_cost": 336, "total_available": 21501 }
```

正泰（13 页，269 条 timeline）有 **48 次** `cost_update`；
小米（23 页，305 条 timeline）有 **63 次**，累计到 1032。

**这里只关心技术形态，不涉及定价**：消耗是**实时流式上报**的（每步都更新），
不是结束时结算；且**阶段推进与计量共用同一个事件流**在驱动。这对我们有两点参考：

1. **成本可理解性要靠事件流实现**（质量属性 P1），不能事后再算；
2. 阶段状态与资源计量**同源**，意味着我们的事件模型应把二者设计在一起，
   而不是让成本统计成为独立旁路。

## 8. 对本项目决策的修正与确认

### 8.1 从"推断"升级为"实测"（3 条）

| 此前推断 | 现在实测结论 |
| --- | --- |
| 它的"完全可编辑"是形状级（B 级） | **确认**：图表是 SVG 图元 + 文本标签，零原生图表部件，无数据模型 |
| 图表在画布内改数据是自绘重绘 | **确认**：数值烤进 `<text>`，坐标预先算好 |
| 视觉同质化（配色单一） | **推翻**：配色有差异且能套品牌色；**真正一致的是版式骨架** |

### 8.2 新增发现（此前完全不知道）

1. **8 阶段事件模型**，`awaiting_confirm` / `search_plan_ready` / `style_recommendations_ready` 是**一等服务端事件**——阶段门是真实持久状态；
2. **字体走外部 OSS + 运行时 CSS @import**——这是它**无法自托管**的架构级原因，直接印证 ADR-0004；
3. **`chartTheme` 21 字段 + `global_*_svg` 片段 + `style_reason` + `preview_svg`** 是一份完整可借鉴的风格包结构；
4. **检索数据里 `authInfoDes` / `rankScore` 字段存在但未启用**——"置信度"没有可核验依据；
5. **成本实时流式上报**，与阶段推进同源。

### 8.3 反超清单更新（第 1 条已实证）

原第 1 条"SVG 形状级 / 位图，图表导出后语义不明"——现在可以说得更硬：

> **SANDUN 的图表在管线内部就是渲染产物，不存在可编辑的数据模型。**
> 导出 PPTX 时的图表重建是**从渲染结果逆推语义**。
> 用户一旦在 PowerPoint/WPS 里改了数据，**没有任何机制能同步回其内部表示**。
>
> PptxSmith 的 A 级语义（SPC C1 已实测：图表带嵌入工作簿、改数值同步缓存与 xlsx 部件）
> 在这个维度上是**结构性领先，不是程度领先**。
