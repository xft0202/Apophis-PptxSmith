# 从零重审 PPTX 技术路线：SANDUN 参考与版本稳定性简报

- 日期：2026-09-26
- 性质：研究简报，不是架构决策，不是实现规格，不冻结语言、SDK、部署或许可证
- 研究目标：只寻找「最适合把高质量、原生可编辑 PPTX 做出来」的整体路线
- 重要边界：现有文档、既有候选、既有 G1-G5、用户曾提到的技术名称，都只是历史证据或线索，不是选型边界

---

## 1. SANDUN 必须参考，但参考对象要分层

SANDUN 不是本项目要复制的技术底座，而是**产品交互和生成流程的参考样本**。
本项目已经有真实流程和产物实证，因此不能再把「参考 SANDUN」误读成「采用 SANDUN 的导出路线」。

### 1.1 可吸收：产品与流程层

| SANDUN 观察 | 吸收分类 | 可吸收内容 | 边界 |
| --- | --- | --- | --- |
| 分阶段推进：需求、大纲、搜索/研究、策划、初稿、风格、正式设计、导出 | **适合二开** | 将生成任务拆成用户可理解的阶段；每阶段有状态、进度和可恢复边界 | 不复制它的接口字段、视觉细节或文案 |
| `awaiting_confirm`、搜索计划就绪、风格推荐就绪等事件 | **可直接复用**（概念） | 把等待人工确认、研究完成、风格确认设为真正的业务状态，而不是 UI 临时状态 | 事件模型需要按本项目的材料/事实/审计流程重新设计 |
| 可在阶段间发送「继续」或确认 | **适合二开** | 长任务不强迫用户一次性提交所有决策；允许在关键节点继续、修改、拒绝或回退 | 不接受无边界自动推进 |
| 页面级重新设计/重排的交互 | **适合二开** | 将“整稿重做”和“单页重做”区分；保留版本和原因 | 单页重排不能破坏其他页的原生对象和来源链 |
| 风格选择与模板/主题分离 | **适合二开** | 风格作为独立选择对象，不把内容、布局和模型输出硬编码为一个黑盒 | 风格包必须能映射到真正的母版、版式、字体和图表样式 |
| 导出过程分段进度 | **适合二开** | 整理页面、素材处理、页面生成、导出上传等阶段可观测 | 每一步必须能报告失败对象和降级范围 |
| `chart_plan` 中的 `chart_type`、数据、单位、标签、理由、slot 等结构化字段 | **可直接复用**（概念） | 图表规划应保留语义数据和“为什么使用此图表”的审计理由 | 规划层数据必须进入最终原生图表和嵌入工作簿，不能止于 SVG |
| 设计令牌、页面角色、内容密度、图片位置等设计规划 | **适合二开** | 把内容规划与视觉布局规划分开，形成可审阅中间产物 | 不把 SVG 页面当最终 PPTX 语义 |

### 1.2 必须拒绝：SANDUN 的产物与导出缺陷

真实导出产物为 15 页、69,830 B，解包和 WPS 实开结果显示：

- 原生图表部件：0；
- 嵌入工作簿：0；
- 原生表格 `<a:tbl>`：0；
- 原生图片：0；
- 产物主要是 411 个形状和 307 个文本 run；
- `system-ui` CSS 字体族名进入 PPTX 45 次；
- 规划层有结构化 `chart_plans`，但导出层没有把它还原为 OOXML 原生图表。

因此：

| 观察 | 吸收分类 | 结论 |
| --- | --- | --- |
| SVG/浏览器渲染作为页面中间表示 | **仅可借鉴** | 可用于预览或视觉探索，但不能作为最终交付表示 |
| 形状级“可编辑” | **应当淘汰** | 不等于图表、表格和嵌入工作簿的原生可编辑 |
| CSS 字体族名直接进入 PPTX | **应当淘汰** | 不能作为中文商务 PPTX 的字体策略 |
| 规划层结构化图表数据 | **可直接复用** | 这是 SANDUN 的真正可吸收价值，必须在导出层保留语义 |
| 页面级设计与图表计划 | **适合二开** | 作为 PptxSmith 的内容/设计中间契约 |

**结论**：SANDUN 应成为产品流程和交互体验的参考，不应成为 PPTX 产物引擎的参考。它的规划层值得吸收，导出层正是本项目需要超越的对象。

## 2. “版本纠纷”不等于一律淘汰

版本差异必须分成两类。

### 2.1 可接受：可冻结、可重现的版本边界

以下情况不必直接淘汰：

- 明确指定 PowerPoint/WPS 版本；
- 明确指定生成引擎或 SDK 版本；
- 明确指定模板版本和字体包版本；
- 通过版本探测或能力探测选择路径；
- 同一支持矩阵下，打开、编辑、保存、重开行为稳定；
- 不支持的对象有明确阻断或降级，不静默变形。

这属于正常的产品支持矩阵，而不是“版本纠纷”。

### 2.2 必须淘汰或隔离：关键语义随版本漂移且无法控制

以下情况才构成真正的选型否决：

1. 同一输入在支持范围内的不同版本中，图表、表格、备注、母版或字体布局发生不可解释的语义变化；
2. SDK 声称支持某功能，但不同版本会静默图片化、丢失嵌入工作簿或改变关系闭包；
3. PowerPoint 生成的文件在 WPS 中、或 WPS 生成的文件在 PowerPoint 中无法稳定打开/保存/重开；
4. 必须依赖未锁定的 Office.js requirement set、未声明的 WPS 版本或不可控字体环境；
5. 版本升级后无法重现同一个交付结果，也没有检测、回滚和重新生成路径；
6. 供应商只给“支持 PPTX”这一句，而没有对象级能力、版本范围和保存边界。

**规则**：版本差异可以管理；版本导致的核心产物不确定性不能接受。

### 2.3 版本矩阵必须至少包含

| 维度 | 必须记录 |
| --- | --- |
| 生产引擎 | PowerPoint / WPS / 商业 SDK / OOXML 包级方案及精确版本 |
| 消费软件 | PowerPoint 版本、WPS 版本、必要时 LibreOffice/ONLYOFFICE 版本 |
| API 层 | COM/VSTO/Office.js/UNO/SDK API 版本及 requirement set |
| 模板 | 模板文件 hash、母版/版式版本、主题版本 |
| 字体 | 字体文件 hash、字体查找路径、替换策略 |
| 产物 | PPTX hash、部件清单、关系闭包、图表工作簿关系 |
| 行为 | 打开、编辑、保存、重开、目标软件展示结果 |
| 变化 | 哪些差异允许，哪些差异阻断交付 |

Microsoft 的 Office.js 文档明确采用 requirement set 与最低版本/Build 矩阵管理 API 能力；Aspose 文档也按支持的 PowerPoint/PPTX 格式和版本范围声明能力。这说明“版本矩阵”是正常工程对象，但不能用厂商支持列表替代项目自己的对象级证据。

## 3. 当前路线比较：还不能直接宣布唯一引擎

### 路线 A：PowerPoint 原生自动化

**优势**：由真正的 PowerPoint 对象模型创建和保存，理论上最接近 PowerPoint 原生语义和最终排版；官方对象模型直接覆盖图表、图表工作簿、幻灯片、形状、布局和母版。

**问题**：微软明确不支持无人值守服务端 Office 自动化；PowerPoint 依赖交互式桌面、用户配置和稳定的 Office 版本。PowerPoint 原生保真不等于 WPS 保真。

**当前状态**：PowerPoint 目标下的最高保真候选；不是跨软件通用答案。

### 路线 B：成熟商业 PPTX SDK

重点候选包括 Aspose.Slides、Syncfusion Presentation、GemBox.Presentation。

**共同优势**：不需要 PowerPoint，官方资料覆盖图表、表格、母版、版式、备注、OLE、渲染和服务端使用。

**共同未证实项**：

- 每个原生图表是否都有可编辑嵌入工作簿；
- 未知部件/关系是否完整保留；
- WPS 与 PowerPoint 的保存重开是否一致；
- 中文字体和行高是否达到本项目目标；
- 不同 SDK 版本是否在关键对象上保持稳定。

**当前状态**：独立服务端路线的主要竞争区，不能仅凭官方功能清单决定。需要同一模板、同一数据、同一版本矩阵的产物比较。

### 路线 C：模板优先 + 包级局部编辑

**优势**：可以最大限度保留既有模板中没有被修改的部件、关系、主题、版式和品牌细节；适合受控模板和局部数据更新。

**问题**：关系、内容类型、图表工作簿和布局变化需要精确维护；从零生成任意页面结构的能力弱；工程复杂度高。

**当前状态**：不是独立“引擎”，而是可能与 PowerPoint 或商业 SDK 组合的产物策略。

### 路线 D：Open XML / Apache POI / python-pptx / PptxGenJS

**优势**：成本低、控制面清晰、可做原生 OOXML 生成的一部分。

**问题**：需要自己承担图表工作簿、缓存、备注、母版继承、关系闭包、中文布局和跨软件保存的复杂度；当前资料不足以证明它们是综合最优。

**当前状态**：适合作为包级工具、局部补丁或研究参照，不能仅因熟悉或开源而成为主引擎。

### 路线 E：LibreOffice / ONLYOFFICE / HTML/SVG 转换

**优势**：服务化、编辑器集成或视觉生成能力较强。

**问题**：拥有自己的文档引擎；支持导入/导出 PPTX 不等于 PowerPoint 语义等价；HTML/SVG 路线尤其容易丢失原生图表和嵌入工作簿。

**当前状态**：可作替代编辑器、预览器或对照引擎，不应凭“兼容 PPTX”直接成为最终产物引擎。

## 4. 阶段性判断

目前能诚实给出的不是“马上选某个库”，而是以下整体方向：

> **产品层参考 SANDUN 的阶段式生成体验；产物层坚持原生 PPTX 语义；引擎层在 PowerPoint 原生自动化与成熟商业 PPTX SDK之间按版本矩阵和真实产物能力决胜；模板优先作为两者都可以采用的产物策略。**

PowerPoint 原生自动化在“PowerPoint 单一目标环境的极限保真”上领先；商业 SDK 在“独立运行和服务化”上领先。两者谁是整个产品的唯一最优解，不能靠文档宣称或语言偏好决定。

### 吸收分类汇总

| 对象/路线 | 吸收分类 | 说明 |
| --- | --- | --- |
| SANDUN 阶段式交互与状态 | **适合二开** | 借鉴流程、事件和确认节点，不复制视觉和实现 |
| SANDUN `chart_plan` 语义模型 | **可直接复用** | 吸收数据、单位、标签、图表理由和槽位概念 |
| SANDUN SVG/形状展平导出 | **应当淘汰** | 与原生图表、表格、工作簿目标冲突 |
| PowerPoint 原生对象模型 | **仅可借鉴 / 重要候选** | PowerPoint 目标下保真潜力最高，但版本和无人值守风险未解 |
| Aspose / Syncfusion / GemBox | **仅可借鉴 / 重要候选** | 独立服务端候选，必须做同题产物比较 |
| 模板优先 | **可直接复用**（策略） | 与具体引擎无关，适合作为统一产物方法 |
| HTML/SVG 首选导出 | **应当淘汰** | 不能证明 A 级原生语义 |
| Open XML 低层操作 | **适合二开** | 作为局部缺口和包级保护工具，不自动承担整稿生成 |

### 6.1 矩阵解读

1. **“原生图表”与“图表带嵌入工作簿”是两个不同能力。**
   Syncfusion 的官方资料明确支持从 Excel 数据创建图表，也明确支持嵌入 Excel OLE；但这不能直接证明它生成的每个 PowerPoint 原生图表都具备本项目要求的 `chart*.xml + embedded workbook + valid relationship` 三件套。

2. **GemBox 的未知内容保留声明有价值，但不能直接等价为 D2 通过。**
   官方“preserve unsupported features”说明它有保留机制；仍需确认本项目未知部件、未知关系和内容类型是否原样保留。

3. **Aspose 的 chart workbook 资料最完整。**
   官方资料明确区分内部 workbook、外部 workbook、缓存恢复和 workbook stream；这使它在独立服务路线中暂时拥有最完整的公开证据，但仍不是本项目实测通过。

4. **PowerPoint 原生自动化的优势是保存者本身就是 PowerPoint。**
   这使它在 PowerPoint 单一宿主下的保真推断最强；但微软明确不支持无人值守服务端自动化，且这不能推导出 WPS 兼容性。

5. **模板优先不是第四个库。**
   它是产物策略：把母版、版式、图表样式和部分未知部件放进模板，再让真正的引擎只修改授权内容。它可能与 PowerPoint、Aspose、Syncfusion 或包级操作组合。

### 6.2 当前最小候选集

在不引入任何预设限制的前提下，研究范围收敛为：

- **PowerPoint 原生自动化**：最高 PowerPoint 宿主保真候选；
- **Aspose.Slides**：公开 chart workbook 和独立渲染证据最完整的商业候选；
- **Syncfusion Presentation**：图表、Excel/OLE、备注、母版和渲染均有官方资料，workbook 关系待确认；
- **GemBox.Presentation**：模板/既有内容保留能力有明确官方声明，图表 workbook 语义待确认；
- **模板优先 + 包级局部编辑**：作为上述路线的组合策略；
- **WPS 原生路线**：只有在 WPS 官方演示对象模型和版本边界被查清后，才可进入同等级比较。

这不是最终排名。下一步应先补齐 WPS 官方证据和商业 SDK 的版本/许可资料，再决定是否需要真实产物验证。

## 7. 许可、运行平台和升级风险（研究层）

### 9.1 Aspose.Slides

官方资料明确：

- 可在不安装 PowerPoint 的情况下创建、编辑、转换和渲染演示文稿；
- 支持 .NET、Linux/Docker 等运行形态；
- .NET 6 路线有独立的跨平台图形组件；
- 评估版会加水印并有功能限制，生产需要许可证；
- 官方支持通常集中在当前版本，旧版本不会持续获得同等级修复。

因此它的主要风险不是“不能服务端运行”，而是：

- 专有商业许可证；
- 版本升级和 API 变更需要锁定；
- 字体、图形依赖和容器镜像需要一起锁定；
- 官方能力声明仍然不能替代本项目的 WPS/PowerPoint 产物证据。

### 9.2 Syncfusion Presentation

官方资料明确：

- 有跨平台 .NET Core/ASP.NET Core 路线，不依赖 Microsoft PowerPoint/Interop；
- 支持图表、Excel 数据来源、OLE、备注、母版、版式、PDF/图像转换；
- 使用 NuGet/程序集和许可证 key；
- Community License 有明确的企业规模、开发者人数、融资等资格条件；不满足条件时需要商业许可证；
- 官方文档和发布说明会出现 .NET 版本支持变化，例如停止对旧 .NET 版本的支持。

因此它的主要风险是：

- 许可证资格不能凭“开源项目”身份推定；
- 运行时和目标 .NET 版本要锁定；
- 图表的 embedded workbook 关系、未知部件保留和 WPS 重开仍未被本项目验证；
- 图表渲染可能依赖额外的 ChartToImageConverter 配置。

### 9.3 GemBox.Presentation

官方资料明确：

- 支持 PPT/PPTX/PPSX 读写、转换和渲染；
- 支持母版、版式、备注、表格、图表等常见对象；
- 明确提供 preservation 机制，以保留不支持的输入内容；
- 创建/修改图表需要结合 GemBox.Presentation 与 GemBox.Spreadsheet；
- 采用开发者许可证/商业授权模式。

因此它的主要风险是：

- preservation 声明仍不是本项目未知部件/未知关系夹具的通过结论；
- 图表 workbook 关系需要单独查证；
- 商业授权、版本和字体/渲染环境需要锁定。

### 9.4 PowerPoint 原生自动化

微软官方资料明确：

- 原生 PowerPoint 对象模型和图表工作簿对象能力存在；
- 但 Office 是交互式桌面软件；
- 微软不建议、不支持无人值守服务端自动化；
- 可能遇到用户配置、模态对话框、并发、死锁、数据损坏和许可证问题。

因此它的主要风险不是 PPTX 语义不足，而是：

- 运行环境和 Office 版本必须严格锁定；
- 不能把它当成普通 Linux 服务端库；
- PowerPoint 的高保真不等于 WPS 高保真；
- 任何跨宿主交付都必须把保存/重开矩阵纳入产品边界。

### 9.5 对路线的影响

| 维度 | PowerPoint 原生 | Aspose | Syncfusion | GemBox |
| --- | --- | --- | --- | --- |
| 原生宿主保真 | 理论最高（PowerPoint） | 独立实现 | 独立实现 | 独立实现 |
| 无 Office 服务运行 | **不适合** | 明确支持 | 明确支持 | 明确支持 |
| Linux/Docker | 不适合作为普通服务 | 有官方路线 | 有官方路线 | 有官方路线/需查具体版本 |
| 许可证复杂度 | Office 许可/部署约束 | 商业许可证 | Community/商业资格 | 商业许可证 |
| 旧版本持续修复 | 受 Office 生命周期影响 | 官方资料提示旧版修复有限 | 随发布版本管理 | 需按供应商支持政策确认 |
| 目标软件交叉保真 | PowerPoint 强，WPS 未证 | WPS/PowerPoint 未证 | WPS/PowerPoint 未证 | WPS/PowerPoint 未证 |
| 当前证据状态 | 高宿主保真推断，高运行风险 | 独立路线证据较完整 | API 面广，关键语义待证 | preservation 有亮点，chart workbook 待证 |

**重要**：本节只改变候选的风险画像，不改变“尚未定案”的状态。

## 8. 模板优先与局部保留：不是引擎，而是产物策略

### 10.1 为什么模板策略重要

高质量商务 PPTX 很少真正从空白包开始。现实工作流通常先拥有：

- 品牌母版与主题；
- 多种页面版式；
- 字体和颜色规则；
- 图表皮肤；
- 页脚、Logo、页码和备注结构；
- 已验证过的目标软件兼容性。

因此，“模板优先”可能比“从零创建每一个 OOXML 部件”更接近真实交付质量。

### 10.2 模板策略的两种模式

| 模式 | 做法 | 优势 | 风险 |
| --- | --- | --- | --- |
| 模板 + 高层 SDK | 用商业 SDK/PowerPoint 读取模板，只修改授权对象 | 开发效率高；可复用母版、版式和品牌结构 | 高层 SDK 可能重写或规范化未支持部件 |
| 模板 + OPC 包级局部编辑 | 直接复制未修改部件，只更新授权 XML、关系、工作簿和内容类型 | 未修改内容理论上最可控 | 关系图、内容类型、图表缓存和合法性维护复杂；自由生成能力弱 |

### 10.3 供应商声明不能互相替代

- **GemBox** 明确提供 preservation 机制，用于保留不支持的输入内容。这是有价值的官方能力声明，但仍需在本项目未知部件/未知关系夹具上验证。
- **Aspose** 的官方资料一方面描述了丰富的对象和形状支持，另一方面明确提醒不支持或特殊内容可能被规范化、遗漏或以不同方式显示。不能把“支持很多对象”当成“未知内容原样保留”。
- **Syncfusion** 的官方资料覆盖对象编辑和转换，并在转换流程中提供 unsupported element 警告；这说明它有风险提示机制，但不等于未修改部件完整保留。
- **PowerPoint 原生模板**由 PowerPoint 自身读取和保存，宿主保真推断最强；但无人值守和跨 WPS 运行风险仍然存在。

### 10.4 模板策略的验收问题

任何模板路线都必须回答：

1. 未修改的 master/layout/theme 是否保留？
2. 未授权的 slide、chart、embedded workbook、notes 和 custom XML 是否保留？
3. 模板中的未知关系是否保留？
4. 替换一个图表数据集时，是否只改变目标 chart、workbook 和缓存？
5. 新增页面时，是否继续使用正确的 master/layout 继承？
6. 模板在 PowerPoint 与 WPS 中分别保存重开后，哪些部件发生变化？
7. 模板版本升级后，历史产物能否复现或明确迁移？

### 10.5 当前落位

> **模板优先应保留为跨路线的首选产物策略，但不能替代引擎选型。**

它可以和 PowerPoint 原生自动化、Aspose、Syncfusion、GemBox 或 OPC 包级工具组合。最终选型要看哪种组合能在版本矩阵下，同时满足：原生对象、嵌入工作簿、中文排版、未知内容边界和目标软件保存重开。

## 9. WPS 路线的证据边界（更新）

本轮从 WPS 官方开放平台 `open.wps.cn` 的 WPP JSAPI 文档中确认了一组真实的演示对象入口。WPS 不应再被描述为“完全没有演示对象模型”。更准确的结论是：

> **WPS 的演示对象模型和常见编辑入口已有一手 API 证据；但原生图表关联嵌入工作簿、备注页可写语义、未知关系保留、版本支持和保存重开契约仍未达到本项目要求的证据等级。**

### 9.1 已确认的官方对象入口

官方页面明确提供：

- `Presentations.Add/Open/Item`，以及 `Presentation.SaveAs`；
- `Slides.AddSlide/InsertFromFile/Paste/Item`；
- `Slide.Layout`、`Slide.Master`、`Slide.NotesPage`、`Slide.Shapes`；
- `Presentation.SlideMaster`、`Presentation.NotesMaster`、`Presentation.CustomXMLParts`、`Presentation.Fonts`；
- `Shape.Chart`、`Chart.SeriesCollection`、`Chart.SetSourceData`、`Chart.DataTable`、`Chart.Refresh`。

这些条目说明 WPS WPP API 已经公开了演示文稿、幻灯片、版式、母版、备注入口、字体、自定义 XML 和图表对象，而不只是 `wpp.execute` 的少量流程命令。

- 图表对象的完整数据模型；
- 图表关联的嵌入工作簿读写；
- 备注页对象；
- 母版/版式继承的完整控制；
- 未知部件和未知关系保留；
- 目标版本之间的保存重开一致性。

### 9.2 仍未证实的核心语义与冲突性线索

官方 `Chart` 对象页没有给出与 PowerPoint `ChartData.Workbook` 或 Aspose `IChartDataWorkbook` 同等级的嵌入 Excel 工作簿、worksheet/cell、公式引用和缓存同步对象。`SetSourceData` 只能证明数据源范围 API 存在，不能证明 PPTX 包具有合法 embedded workbook 关系。

`Slide.NotesPage` 和 `Presentation.NotesMaster` 证明备注入口存在，但备注文本写入、关系闭包、WPS/PowerPoint 重开和未知部件保留仍未证实。

WPS 相关公开材料中出现过“嵌入式 Excel 图表建议转为图片以确保一致性”的建议。该材料不是足以代表完整官方 API 契约的一手规范，因此不能据此断言 WPS 必然图片化；但它足以说明：

> **不能把“WPS 支持 PPTX/图表”直接解释成“WPS 能稳定满足原生图表 + 嵌入工作簿 + WPS 重开编辑”的项目要求。**

### 9.3 当前落位

| WPS 能力 | 官方一手证据 | 项目产物证据 | 当前落位 |
| --- | --- | --- | --- |
| 演示流程/版式/幻灯片操作 | WPP 官方对象页：`Presentations`、`Slides`、`Slide.Layout/Master` | 尚未用本轮夹具验证 | 官方 API 入口已确认 |
| 原生图表 | `Shape.Chart`、`Chart.SeriesCollection`、`Chart.SetSourceData`、`Chart.DataTable` | 尚未形成 WPS 对象级图表产物矩阵 | API 已确认，核心关系未证 |
| 嵌入工作簿 | 未找到 `ChartData.Workbook` 等级对象页 | 无有效项目证据 | 未证 |
| 备注页/备注母版 | `Slide.NotesPage`、`Presentation.NotesMaster` | 尚未验证备注内容和保存重开 | 对象入口已确认，写入语义未证 |
| 母版/版式/主题 | `Slide.Master/Layout`、`Presentation.SlideMaster`、`ApplyTheme` | 尚未完成关系闭包验证 | 对象入口已确认，继承未证 |
| 自定义 XML | `Presentation.CustomXMLParts` | 未知部件/关系夹具尚未用 WPS 保存重开验证 | API 已确认，保留未证 |
| 真文本/字体 | `Presentation.Fonts`、Shape/Text API 入口 | 中文零溢出尚未形成 WPS 专项矩阵 | API 部分确认，视觉未证 |
| 未知关系保留 | 未找到完整声明 | 无有效项目证据 | 未证 |
| PowerPoint/WPS 交叉保存 | 未找到完整版本矩阵 | 历史 Spike E 只覆盖特定夹具 | 未证 |
| WPS 版本与 API 门禁 | `Application.Version`、`Application.Build`、`canIUse` | 尚未映射到历史 11.8.2.8411 的核心对象契约 | 版本可识别，兼容性未证 |

**因此 WPS 目前不是“已淘汰”，也不是“对象模型完全缺失”；它是“部分对象能力已证实、核心产物语义待证”的条件性候选。**

官方入口：

- WPS WPP `Presentations`/`Presentation`/`Slides`/`Slide`：<https://open.wps.cn/documents/app-integration-dev/wps365/client/wpsoffice/jsapi/wpp/Presentations/obj>
- WPS WPP `Chart`：<https://open.wps.cn/documents/app-integration-dev/wps365/client/wpsoffice/jsapi/wpp/Chart/obj>
- WPS WPP `Shape`：<https://open.wps.cn/documents/app-integration-dev/wps365/client/wpsoffice/jsapi/wpp/Shape/obj>
- WPS 应用版本/Build：<https://open.wps.cn/documents/app-integration-dev/wps365/client/wpsoffice/jsapi/wps/Application/obj>

## 10. 当前研究结论（更新）

现在可以确定的是**决策结构**，还不能确定最终引擎：

1. **产品层**：参考 SANDUN 的阶段式生成、确认节点、页面级重排、风格选择、结构化图表计划和导出进度；
2. **产物层**：拒绝 SANDUN 的 SVG/形状展平导出，坚持原生图表、嵌入工作簿、原生表格、真文本、备注和母版/版式；
3. **引擎层**：保留 PowerPoint 原生自动化、Aspose.Slides、Syncfusion Presentation、GemBox.Presentation；
4. **策略层**：模板优先 + 必要时包级局部编辑，可以与上述引擎组合，不是单独的库选项；
5. **版本层**：可锁定、可复现的版本差异可以接受；无法冻结且会改变核心 PPTX 语义的版本差异必须淘汰或隔离；
6. **当前禁止动作**：不写代码、不搭 benchmark、不宣布唯一引擎。

本简报仍然是研究材料，不是 ADR，不是工程启动规格，也没有修改现有架构决策。

## 11. 无普适冠军：必须先声明主宿主

本轮研究可以排除一个危险假设：

> **不存在一个不区分主宿主、不区分版本，却能同时宣称 PowerPoint/WPS 原生保真最优的单一引擎。**

### 11.1 原因

- PowerPoint 原生自动化的优势来自 PowerPoint 自己的对象模型和保存引擎，因此它的最强结论只能绑定到 PowerPoint；
- WPS 已有部分公开对象模型，但仍缺 embedded workbook、备注写入、未知关系保留和版本契约证据；
- 商业 SDK 是独立实现，必须自己处理 PowerPoint/WPS 的兼容差异；
- GemBox 的 unsupported feature preservation 是它自己的读写能力声明，不是所有 SDK 的通用保证；
- Aspose/Syncfusion 的“支持 PPTX”是格式和 API 能力声明，不等于本项目对象级、版本级和目标软件级通过。

### 11.2 选型前必须先声明的主宿主

候选在进入最终排序前，必须明确：

| 主宿主策略 | 可得结论 | 不能宣称 |
| --- | --- | --- |
| PowerPoint 主宿主 | 可以追求 PowerPoint 原生对象和保存保真 | 不能自动宣称 WPS 等价 |
| WPS 主宿主 | 可以追求 WPS 实际交付保真 | 核心图表 workbook、备注写入、关系保留和版本证据未完成前不能宣称已经满足 |
| 双宿主同等主宿主 | 必须以两套保存/重开矩阵共同通过为准 | 不能用其中一个宿主的证据代表另一个 |
| 独立 SDK 主宿主 | 可以追求服务端、模板和跨平台一致性 | 不能自动宣称等同 PowerPoint/WPS 原生保存 |

### 11.3 当前最诚实的路线结论

> **先选“主宿主和版本契约”，再选引擎。**
>
> 如果主宿主是 PowerPoint，PowerPoint 原生自动化是最高保真候选；如果主宿主是独立服务，Aspose、Syncfusion、GemBox 进入真正的竞争；如果主宿主是 WPS，必须先补齐 embedded workbook、备注写入、关系保留和精确版本证据。

这不是回避选型，而是防止把一个宿主的“最优”误写成所有宿主的“最优”。

## 12. 许可证、版本生命周期与回滚（研究摘要）

本轮新增矩阵：`research/2026-09-26_PPTX引擎许可证与版本生命周期矩阵.md`。

关键事实：

- **Aspose.Slides**：许可证允许继续使用订阅结束前发布的版本；要使用更新版本需要续订；官方支持页明确旧版本可用但只为当前 release 提供修复，不为 legacy versions 发布补丁。
- **Syncfusion Presentation**：Community License 有明确资格条件：年总收入低于 100 万美元、开发者不超过 5 人、总员工不超过 10 人、外部融资不超过 300 万美元；政府相关组织通常不符合。不能把 Community License 当成长期商业成本前提。
- **GemBox.Presentation**：按开发者授权；官方声明可无限部署且不需要额外 server/OEM license；许可证永久，但支持结束后发布的新版本需要续订。日期版本号有利于锁定和审计，但升级仍可能改变渲染或对象行为。
- **PowerPoint/Office**：Office LTSC 2024 有五年 Mainstream Support、无 Extended Support，且发布后不接收功能更新；Microsoft 365 Cloud Update 的暂停/回滚只适用于 Monthly Enterprise profile，不能泛化到所有 Office 安装。
- **WPS**：WPP 对象模型已有部分官方证据，但许可、精确版本维护、回滚、embedded workbook、备注写入、未知关系保留和双宿主保存契约仍未补齐，不能把它写成已证实的最优路线。

因此“可回滚”必须拆成：依赖包回滚、运行时回滚、模板回滚、主宿主回滚和产物审计坐标回滚。只恢复 SDK 版本，不能证明 PPTX 对象和视觉语义恢复。

这一节只补充风险和证据边界，不改变尚未定案的状态。

## 13. 对象语义矩阵（研究摘要）

本轮新增矩阵：`research/2026-09-26_PPTX对象语义证据矩阵.md`。

当前最重要的拆分是：

- 原生图表 ≠ 有 `AddChart` API；还必须证明 chart part、嵌入 workbook、series/category 引用、缓存、目标宿主编辑和重存；
- 备注 ≠ 有一段文本；还必须证明 notes part、关系、notes master/style、宿主可见性和重存；
- 母版 ≠ 有模板文件；还必须证明 master/layout/theme/placeholder 的关系闭包和新增页继承；
- preservation 声明 ≠ 未知部件已经安全保留。

对象级画像：

- Aspose：`IChartDataWorkbook`、公式/单元格引用、notes slide、master/layout 的官方对象级证据最完整；项目 workbook、缓存、未知部件和双宿主重开仍未知；
- Syncfusion：图表、notes、master/layout 和富文本 API 公开证据较广；embedded workbook 和未知部件保留仍未证；
- GemBox：`NotesSlide` 和 unsupported feature preservation 有官方证据；本轮图表/母版页面抓取错配，不能夸大图表 workbook 或完整模板继承能力；
- PowerPoint：宿主原生对象概念最完整，但无人值守和 WPS 交叉保存风险不变；
- WPS：已确认部分 WPP 对象入口，但仍缺完整的图表 workbook、备注写入、未知关系保留和版本支持矩阵。

## 14. 中文真文本与零溢出（研究摘要）

本轮新增：`research/2026-09-27_中文真文本与零溢出质量证据.md`。

只核定中文排版这一项，不扩展路线范围。关键结论：

- OOXML 明确区分 `normAutofit`、`spAutoFit` 和 `noAutofit`；“开启自动适配”不是单一语义；
- PowerPoint 可以读取文本边界高度，但目标宿主仍需固定字体、模板、内边距、段落和版本校准；
- East Asian 字体必须单独审计，不能只记录 Latin 字体名；
- 字体替换会改变字宽、行高和换行；
- Aspose 的 fallback 配置在渲染时使用，不会写入 PPTX；
- 字体嵌入受 `fsType` 许可限制，`OnlyUsed` 不适合需要继续编辑的新文字；
- 行数预测本身不能证明无溢出，必须同时记录高度、行距、内边距和实际目标宿主渲染；
- Spike E 只证明固定 WPS 版本、固定 Noto Sans SC、固定内容和固定尺寸的一组通过，不能推广为所有字体或所有宿主通过。

新的不可退让契约是：

```text
字体文件/许可
+ Latin/East Asian 映射
+ 文本框尺寸/内边距
+ 段落行距
+ AutoFit 语义
+ 目标环境量字
+ 目标宿主实际渲染
+ 非静默降级
```

中文零溢出仍然需要目标软件回归，但本轮不再扩展到其他候选或宿主话题。

## 14. 质量优先整体路线重构（纠偏）

本轮新增研究文档：`research/2026-09-26_质量优先PPTX整体路线重构.md`。

研究轴线已从“继续补某个兼容宿主的 API”纠正为“比较整体架构形态与最终产物质量上限”：

- **目标宿主原生作者**：目标软件的对象模型和保存引擎提供宿主内最高保真潜力，但有桌面自动化和部署风险；
- **独立语义 PPTX 引擎**：服务化和版本锁定更自然，但不能把独立 SDK 等同于 PowerPoint 保存语义；
- **模板优先的受控变更**：最适合保留已验证的母版、版式、图表和品牌结构，但自由生成能力受限；
- **语义中间层 + 受控作者适配器**：最值得作为长期产品架构研究方向；
- **HTML/SVG**：只能作为预览和设计探索，不能作为最终作者。

因此当前最重要的研究结论是：

> **长期路线应优先研究“语义中间层 + 模板优先 + 受控作者适配器”，而不是继续让 WPS 或任何单一 SDK 主导路线判断。**

WPS 回到次级兼容宿主或待证作者适配器的位置；PowerPoint 原生代表单宿主质量上限，商业 SDK 代表独立服务质量上限。仍未选择最终引擎。

## 15. 质量优先条件性路线结论

本轮新增研究文档：`research/2026-09-27_PPTX质量优先条件性路线结论.md`。

当前最可能满足高质量、原生可编辑、可交付 PPTX 的整体组合是：

```text
语义中间层
+ 模板优先
+ 受控作者适配器
+ 包级对象/关系审计
+ 明确的作者版本与验收矩阵
```

当前只保留两条待证作者路线：

- **PowerPoint 原生作者**：PowerPoint 单宿主质量上限候选；
- **独立语义 PPTX 作者**：Aspose 优先研究，Syncfusion/GemBox 作为并列备选。

作者引擎与验收宿主是正交轴：作者负责创建/修改/保存，验收宿主负责打开、编辑、保存、重开和视觉验证。WPS 不主导作者路线判断；但若保留 `VISION.md` 的 PowerPoint/WPS 双编辑承诺，WPS 必须作为独立的可编辑验收门，不能仅按只读预览处理或用 PowerPoint 的结果替代。是否收缩该承诺须由所有者显式决定。

这不是最终 SDK 选择。最终判断仍必须由 S1-S5、P0/P2 和固定版本验收矩阵的真实产物证据决定。
