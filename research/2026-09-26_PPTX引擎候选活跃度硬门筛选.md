# PPTX 引擎候选：G1–G5 活跃度硬门筛选（实测）

- 筛选日期：2026-09-26
- 依据：票 13 的**入场硬门** G1–G5（活跃度是**入场资格**，不是评分项；不过门直接淘汰，不做能力评估）
- 数据来源：GitHub API 快照（仓库元数据、releases、contributors、commits）
- 规则：**先过门槛，再比能力**。本报告只做门槛判定，不做胜负结论。

## 1. 硬门标准（票 13）

| 编号 | 门槛 |
| --- | --- |
| G1 | 最近 **12 个月内**有正式发版 |

## 3. 逐个判定依据

### 3.1 Open XML SDK（`dotnet/Open-XML-SDK`）— 入场

| 项 | 实测值 |
| --- | --- |
| stars / forks | 4,608 / 607 |
| 许可 | **MIT** |
| 最近发版 | **v3.5.1（2026-03-18）** |
| 最近提交 | 2026-08-18 |
| 近 180 天提交 | 37 条，其中人类 20 条 / 机器人 17 条 |
| 近 100 条提交的人类分布 | twsouthwick 13、SimonCropp 12、mikeebowen 11、mkaszewiak 5、tomjebo 2 |
| 贡献者（前 30）总数 | 1,267 次提交 |
| open issues | 130 |

**G 判定**：

- **G1 ✅**：v3.5.1 在 12 个月内（2026-03），且 v3.4.1（2026-01）紧随其后，发版节奏稳定。
- **G2 ✅**：近 180 天 37 条提交，跨 2026-05 至 2026-08 连续分布，非偶发。
- **G3 ✅**：130 个 open issue 在维护（对比 python-pptx 的 537 堆积），且有持续 PR 合并。
- **G4 ⚠️ 有条件通过**：头号贡献者 twsouthwick 占 55%，**但**近期提交已分散到 5–6 位人类贡献者（SimonCropp、mikeebowen、mkaszewiak 等），且**背后是微软官方项目**（`dotnet` 组织），不是个人项目。单点风险由组织承担，可接受。
- **G5 ✅**：语义化版本（v3.x），微软官方支持周期。

**唯一保留意见**：近 180 天人类提交仅 20 条，绝对活跃度不算高。但它是**规范级实现**（Open XML 是 ECMA-376 标准），成熟度高、变更需求本身就少——这与"没人维护"是两回事（对比 PptxGenJS 的 0 提交）。属可接受。

## 4. 结论与影响

### 4.1 筛选后仍在场的候选

**10 个候选里只有 2 个通过入场硬门**：

| 过门候选 | 说明 |
| --- | --- |
| **Open XML SDK**（C#，MIT） | 官方维护、规范级实现、语义化版本 |
| **Apache POI**（Java，Apache-2.0） | 贡献者分布最健康、ASF 治理 |

这不是"提前锁定答案"，而是**门槛本来就会筛掉大部分**：

- 10 个候选里 **8 个被淘汰**；
- 淘汰原因集中在**同一处**：**单人维护 + 停更**。
  PptxGenJS（94% 单人、停更 15 个月）、python-pptx（96% 单人、停更两年）、
  ShapeCrawler（88%）、ppt-master（98%）、pptx-automizer（89%）、
  officegen（71% 且停更两年）、unioffice（63% + 商业许可）、
  gopptx/cjk-pptx-engine（无法定位）——
  **这正是所有者要求「只看热门活跃度高的」所指向的问题**。
- 值得注意的是 **ppt-master 星数 56,399**，比 PptxGenJS 还高——
  **单看星数会选中它，但它的贡献者集中度是 98%，全项目只有一个人在推**。
  这是「活跃度门槛不能用星数替代」的最好例证。

### 4.2 对既有决策的影响

| 既有决策 | 影响 |
| --- | --- |
| **ADR-0003**（TS 全栈 + PptxGenJS） | 其核心依赖 PptxGenJS **未过活跃度硬门**。该 ADR 已处于 `challenged`，现在有了新的实证理由 |
| **ADR-0009**（.NET + Open XML SDK 提案） | 其选定的引擎**是过门候选之一**。但**这不等于 ADR-0009 就该被接受**——还需能力对比（生成/读改/未知部件保留/目标软件验收），且**实现语言仍未定**；Apache POI 同样过门，实现语言不能由此锁定 |
| **票 02**（引擎基座复用盘点） | 范围应缩窄：候选从 6 个减到 1 个 |
| **票 18**（材料解析与渲染） | 其中 PPTX 编译器候选同样受此门槛约束 |

**必须避免的误读**：本报告只证明「这两个候选过了入场门槛」，**没有证明任何一个是最优解**。
它们仍需能力对比，并接受目标软件验收。过门只是**获得被比较的资格**。

### 4.3 下一步（仍只围绕 PPTX）

1. **扩充候选池**：本次只查了已知的 6 个。应再搜一轮「PPTX 生成/读改」的活跃项目
   （尤其 .NET / Rust / Go 生态与商业库的对照），避免"只剩一个"是**搜索不充分**造成的；
2. **对过门候选做能力对比**：生成原生图表/表格、读改既有包、未知部件保留、
   OOXML 校验、嵌入工作簿同步——这些是**产品承诺的判据**；
3. **不做实现语言决定**：直到能力对比完成。

## 4.4 吸收分类（博采众长原则的强制字段）

按地图 Notes 的强制要求，本轮的十个候选**逐项标注吸收分类**。
只有「入场/淘汰」二元判定视为未完成——以下是五分类落位。

| 候选 | 吸收分类 | 说明 |
| --- | --- | --- |
| **Open XML SDK** | **可直接复用**（待能力验证后确认） | MIT、微软官方、过 G1–G5。能力对比（票 23）通过后即可作依赖引入 |
| **Apache POI** | **可直接复用**（待能力验证后确认） | Apache-2.0、ASF 治理、贡献者分布最健康。同上 |
| ShapeCrawler | **仅可借鉴** | 未过 G4（头号 88%），**不进依赖树**。其「高层 API 包装 OOXML」的做法可学 |
| ppt-master | **仅可借鉴** | 未过 G4（头号 98%）。其「确定性转换 + postflight 质量报告」思路可学（首轮调研已记） |
| pptx-automizer | **仅可借鉴** | 未过 G4（头号 89%）。模板化修改的思路可看 |
| unioffice | **必须隔离** | 商业双许可（与 ADR-0002 冲突）。如需参照，只能进程隔离或读其文档 |
| **PptxGenJS** | **仅可借鉴** | 未过 4 项、已不具备候选资格。**但 Spike A 验证过生成原生图表/表格可行**——这个能力证明有效，代码不引 |
| **python-pptx** | **仅可借鉴** | 未过 4 项。其 API 设计（shape/text_frame/table 的对象模型）是清晰的中文可读参考 |
| officegen | **应当淘汰** | 停更两年、四项不达标，无可借鉴的独特价值 |
| gopptx / cjk-pptx-engine | **应当淘汰** | 仓库无法定位，无法评估 |

**重要区分**：本票的「入场/淘汰」是**活跃度门槛**判定；
「吸收分类」是**如何对待该样本**的决策。二者不同层：

- 「淘汰」只表示**不进候选池做能力对比**，不表示「什么都不能学」；
- 因此 ShapeCrawler / ppt-master / PptxGenJS 等被淘汰者，
  仍可标注为**仅可借鉴**——学其思路是允许的，**只是不许把它们变成依赖**。

**本轮已明确不进依赖树的**：ShapeCrawler、ppt-master、pptx-automizer、PptxGenJS、
python-pptx、unioffice、officegen、gopptx、cjk-pptx-engine（共 9 个）。
