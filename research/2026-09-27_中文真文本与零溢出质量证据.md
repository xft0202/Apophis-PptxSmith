# 中文真文本与零溢出：质量证据与排版契约（研究阶段）

- 日期：2026-09-27
- 性质：聚焦 P2 中文排版质量，不是实现规格，不选择引擎
- 研究边界：只讨论真文本、字体、混排、自动适配、行高和溢出；不扩展 WPS/引擎候选研究

## 1. 当前结论

中文零溢出不是“支持中文字体”一个开关，而是以下因素共同决定的结果：

```text
字体文件与许可
+ PPTX 中的字体声明
+ East Asian 字体映射
+ 实际字体度量
+ 文本框宽高与内边距
+ 换行与 AutoFit 模式
+ 行距/段前段后
+ 目标宿主的排版引擎
+ 目标宿主实际渲染回归
```

因此：

> **任何引擎只能证明它提供了字体、段落或 AutoFit API，不能仅凭 API 声明证明中文零溢出。**

## 2. 一手资料确认的对象层事实

### 2.1 OOXML 本身有三种不同文本适配语义

Microsoft Open XML 文档明确区分：

- `a:normAutofit`：在保持形状边界的前提下缩小字体或减少行距；包含 `fontScale` 和 `lnSpcReduction`；
- `a:spAutoFit`：随文本增大形状尺寸；
- `a:noAutofit`：不自动缩放字体，也不自动扩大形状。

这三种语义不是视觉等价物。对于商务 PPTX：

- `spAutoFit` 可能破坏页面结构；
- `normAutofit` 可能让字号悄悄变小；
- `noAutofit` 可能导致溢出。

项目必须把 AutoFit 模式作为可审计字段，不能只记录“开启自动适应”。

来源：

- <https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.normalautofit?view=openxml-3.0.1>
- <https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.shapeautofit?view=openxml-3.0.1>
- <https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.noautofit?view=openxml-3.0.1>

### 2.2 PowerPoint 原生对象可以测量和改变文本框，但仍需目标宿主校准

Microsoft PowerPoint VBA 文档明确：

- `TextFrame.AutoSize` 可以设置为 `ppAutoSizeShapeToFitText`，让形状适应文本；
- `TextRange.BoundHeight` 可以返回文本边界高度。

这说明 PowerPoint 原生作者可以读取目标宿主的文本边界信息，但它不自动给出“中文零溢出”的产品保证。仍需固定字体、模板、内边距、段落格式和目标版本。

来源：

- <https://learn.microsoft.com/en-us/office/vba/api/powerpoint.textframe.autosize>
- <https://learn.microsoft.com/en-us/office/vba/api/powerpoint.textrange.boundheight>

### 2.3 OOXML 有 East Asian 字体层

Open XML 文档说明 `EastAsianFont` 用于指定一段文本的东亚字体；若该字体在渲染系统中不可用，会触发替代字体选择。

这意味着中文字体策略不能只写 Latin 字体名。至少要审计：

- Latin 字体；
- East Asian 字体；
- Complex Script 字体；
- 每个 run 的实际 typeface；
- 目标机器/渲染容器是否安装或加载相同字体。

来源：

- <https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.eastasianfont?view=openxml-3.0.1>

## 3. 一手资料确认的字体与回退风险

### 3.1 字体替换会改变换行和高度

Aspose 官方文档明确：

- 缺失字体会被替换；
- 替代字体的字形度量可能不同；
- 不同系统上的段落尺寸计算和换行结果可能不同；
- 为获得一致结果，需要在环境中安装相同字体，或在运行时加载相同字体。

Aspose 的 AutoFit 文档进一步明确：字体替换会改变文字宽度/高度，进而改变字号和换行；替换后必须重新检查页面。

来源：

- <https://docs.aspose.com/slides/net/faqs/>
- <https://docs.aspose.com/slides/net/manage-autofit-settings/>

### 3.2 Fallback 与 substitution 不是一回事

Aspose 官方文档区分：

- fallback：主字体缺少某些字符时，按字符或 Unicode 范围补字体；
- substitution：整个 run 或 text portion 的字体不可用时替换整段字体。

更重要的是：Aspose 明确说明 fallback 配置位于处理/渲染时，不会序列化进 PPTX。也就是说：

> **作者进程里配置过 fallback，不代表交付 PPTX 在另一台机器、PowerPoint 或 WPS 中会自动复现同一 fallback。**

来源：

- <https://docs.aspose.com/slides/net/fallback-font/>

### 3.3 字体嵌入也不是无条件解决

Aspose 官方文档明确：

- `All` 适合接收者需要继续编辑并输入新文字的演示文稿；
- `OnlyUsed` 更适合主要用于查看的成品；
- 嵌入字体不能解决字体本身缺失的字符；
- 字体 embedding 权限来自字体文件，库不能替代许可证审查。

OpenType `fsType` 规范明确区分：

- Restricted License embedding；
- Preview & Print embedding；
- Editable embedding。

因此项目不能简单地“把所有字体都嵌入”。必须检查字体授权、`fsType`、目标软件支持和是否需要继续编辑。

来源：

- <https://docs.aspose.com/slides/net/embedded-font/>
- <https://learn.microsoft.com/en-us/typography/opentype/spec/os2#fstype>

## 4. 量字与零溢出的正确判据

Aspose 官方段落文档明确提醒：

- 预测行数会受字体可用性、字体替换、字号、内边距、缩进、换行和 AutoFit 影响；
- 行数本身不能证明文本没有溢出；
- 还必须考虑可用高度、行高、段落/行距和 AutoFit；
- 应使用目标环境的字体和布局设置检查模板。

因此项目 B1-B5 应改写为：

| 判据 | 必须记录 |
| --- | --- |
| 字体选择 | 字体文件 hash、Latin/East Asian/CS 字体、许可和 fallback 规则 |
| 文本框 | 宽、高、四边内边距、旋转、锚点和形状类型 |
| 段落 | 行距类型/数值、段前、段后、缩进、换行符 |
| AutoFit | `noAutofit`、`normAutofit` 或 `spAutoFit`，以及缩放/减距参数 |
| 预测 | 目标字体环境中的行数、边界宽高、最小安全余量 |
| 实际 | 目标宿主渲染后的行数、边界、溢出和裁切 |
| 交付 | PowerPoint/WPS 是否分别保存重开后仍满足判据 |

### 4.1 Spike E 的正确解释

Spike E 已证明：在固定 WPS 11.8.2.8411、固定 Noto Sans SC、固定文本和固定尺寸下：

- 预测 5 行；
- WPS 实际 5 行；
- 文本未溢出。

这是一条有效的固定组合证据，但不能推广为：

- 所有中文字体都稳定；
- PowerPoint 与 WPS 等价；
- 所有文本长度和页面角色都稳定；
- fallback 配置可随 PPTX 一起迁移。

Spike E 同时指出：微软雅黑/宋体的行高预测可能系统性低估，说明必须建立“字体 × 目标宿主”的校准表。

## 5. 对整体路线的直接影响

### 目标宿主原生作者

优点：可以直接读取目标宿主的边界和 AutoFit 行为。

仍需：固定字体、固定模板、固定版本和宿主渲染回归。

### 独立 SDK

优点：可以在生成阶段统一配置字体目录、fallback、段落和 AutoFit。

风险：

- fallback 可能只是 SDK 渲染时配置，不写入 PPTX；
- SDK 的 PDF/PNG 渲染不等于 PowerPoint/WPS 打开后的布局；
- 字体替换会改变 line count 和高度。

### 模板优先

优点：可以先把字体、段落、内边距、占位符和版式校准好。

风险：模板中的文本框 AutoFit、主题字体和占位符继承仍需在目标宿主验证。

## 6. 当前不可退让的中文质量契约

首期任何候选路线都必须最终提供：

1. 字体文件和许可清单；
2. Latin/East Asian 字体映射；
3. 固定字体环境或明确可审计的替换路径；
4. 文本框尺寸、内边距、段落行距和 AutoFit 的可解释记录；
5. 目标字体环境中的量字与实际渲染对照；
6. 中文、中英混排、数字、标点和图表标签样本；
7. PowerPoint/WPS 若都在交付范围内，分别记录结果；
8. 任何 fallback、substitution 或缩字号行为都不得静默发生。

## 7. 吸收分类

| 对象/机制 | 吸收分类 | 边界 |
| --- | --- | --- |
| OOXML `normAutofit`/`spAutoFit`/`noAutofit` 语义 | **可直接复用** | 进入文本框质量契约和审计字段 |
| East Asian 字体映射 | **可直接复用** | Latin/East Asian/CS 必须分别记录 |
| 目标字体 × 宿主量字校准 | **适合二开** | 作为中文排版回归资产，不抽象成通用常数 |
| Aspose/Syncfusion fallback API | **仅可借鉴** | fallback 可能只存在于渲染时，不能假设写入 PPTX |
| 字体嵌入策略 | **适合二开** | 受 `fsType`、目标软件和继续编辑需求约束 |
| CSS 字体名或整页图片替代真文本 | **应当淘汰** | 不满足中文真文本和可编辑性目标 |
| “预测 N 行所以一定不溢出” | **应当淘汰** | 必须同时检查字体、边界高度、行距和目标宿主渲染 |

## 8. 当前结论

> **中文零溢出不是候选 SDK 的宣传能力，而是“字体 × 文本框 × 段落 × AutoFit × 目标宿主”的版本化产物契约。**

因此本项目不应继续寻找“天然中文零溢出”的引擎；应寻找能够暴露这些控制面、允许固定字体环境、输出审计信息并接受目标宿主回归的整体路线。

本文件只核定中文排版质量证据，不改变最终引擎未定案状态。
