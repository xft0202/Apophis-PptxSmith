## 0. 为什么重做这轮调研

### 我此前的错误

1. **只搜「已知的库」**——把 SANDUN 或 Spike C 提到的东西当调研起点，
   结果候选池只有 6 个，漏掉整个 Rust 生态、模板引擎路线、HTML 转换路线；
2. **接受了所有者提到的名称当结论**——「Presenton / PPT Master / Kimi / Aspose」
   是所有者提的线索，不是我的调研结果。我把线索当成了候选池；
3. **只按语言分类，没按「技术路线」分类**——所以看不出「模板填充」和
   「原生生成」是两种根本不同的做法。

- **7 类技术形态**（不按语言分）；**8 种语言**；广度优先，不预设结论；
- 每个候选按**同一套需求编号**判断，不因语言或熟悉度加权。

## 1. 技术形态全景（7 类）

### 形态 1：原生 OOXML 引擎（自己读写包）

直接操作 OOXML 部件，掌握全部语义。

| 项目 | 语言 | 许可 | 活跃度 | 关键观察 |
| --- | --- | --- | --- | --- |
| **Open XML SDK** | C# | MIT | ✅ 活跃（v3.5.1 2026-03） | 微软官方，**规范级实现**，含 `OpenXmlValidator` |
| **Apache POI** | Java | Apache-2.0 | ✅ 最健康（头号 30%） | ASF 治理；对 PPTX 支持深度需实测 |
| **betteroffice** | **Rust** | Apache-2.0 | ⚠️ 新（2026-07 创建） | 「Native OOXML engines in Rust — DOCX/XLSX/PPTX **editing, rendering**」，编译到 WASM。**头号 71%** |
| **office_oxide** | **Rust** | Apache-2.0 | ⚠️ 新（2026-03） | 多语言绑定（Py/Rust/Go/JS/C#/WASM），宣称比 python-docx 快 100×。**头号 64%** |
| **ppt-rs** | **Rust** | Apache-2.0 | ❌ 单人 100% | 只做生成 |
| **unioffice** | Go | ⚠️ 商业 | ⚠️ | 商业双许可 |

**新发现的意义**：**Rust 生态在 2025-2026 密集出现原生 OOXML 引擎**
（betteroffice / office_oxide / ppt-rs / undoc / ooxml-rs 等），
且多数是 Apache-2.0。这对我此前「Rust 生态不成熟、等于先造引擎再造产品」的判断
（ADR-0009 的否决理由）**构成实质挑战**——需要重新评估。

**但均未过门槛**：betteroffice(71%)、office_oxide(64%)、ppt-rs(100%)
贡献者集中度都超 G4 红线；且创建时间短（最长 6 个月），无长期维护证据。

### 形态 2：模板填充（往现成 PPTX 里填数据）

**这是此轮最重要的发现——一条我此前完全没考虑的路线。**

| 项目 | 语言 | 许可 | 观察 |
| --- | --- | --- | --- |
| **pptx-automizer** | TS | MIT | 头号 89%；以既有 PPTX 为模板做批量修改 |
| **PPT-Templates** | Java | Apache-2.0 | 头号 93%，2024 后停更 |
| **pptx-template** | Python | Apache-2.0 | ★119 |
| **docxtemplater** | JS | ⚠️ NOASSERTION | ★3629，**Word 生态**的成熟模板引擎（PPTX 能力需查） |
| **yumdocs** | TS | MIT | 文档模板 |

**为什么值得重视**：本项目有**风格包**体系。若风格包本身就是一个
**预制的 .pptx 模板**（含母版/版式/主题/图表皮肤），那么生成就是
**「克隆版式 → 填数据 → 不改样式」**。这条路：

- 天然保真（母版、版式、主题由模板提供，不是代码拼的）；
- 天然规避「从零建包没有 hello world」的问题（Spike C3 的痛点）；
- 与 CONTEXT.md 的「风格包 = 颜色令牌 + **版式原型** + 字体清单 + 图表皮肤」**高度吻合**。

**但风险**：模板填充通常**弱于「生成任意新结构」**。
若页面结构需要 AI 自由生成，模板只能提供版式骨架，内容仍需原生对象写入。
**这可能是「两者组合」而不是「二选一」。**

### 形态 3：HTML/CSS → PPTX 转换

| 项目 | 语言 | 许可 | 观察 |
| --- | --- | --- | --- |
| **html2pptx** | JS | ⚠️ 无许可 | ★24 |
| **Hasasasa/html-to-editable-pptx** | Python | MIT | ★71，主打「可编辑」 |
| **dom-to-pptx** | JS | MIT | ★366 |
| **pptx-compose** | TS | ⚠️ | 停更 2023 |

**与本项目关系**：这是 SANDUN 路线的变体（HTML/SVG → 转形状）。
**A9「零图片化」很可能直接判死**——转换路线的产物通常是形状或图片。
但「html-to-**editable**-pptx」这类声称可编辑的，值得解包验证。

### 形态 5：解析路线（PPTX → JSON/Markdown）

| 项目 | 语言 | 许可 | 价值 |
| --- | --- | --- | --- |
| **pptxtojson** | JS | MIT | ★456，**可看它如何把 PPTX 解析成结构化 JSON** |
| **pptx2md** | Python | Apache-2.0 | ★1278 |
| **undoc** | Rust | MIT | ★36，**含 CJK 支持** |

**对本项目的价值**：**这两条不是竞争者，是参照物**。
解析路线的代码告诉我们 **OOXML 里到底有哪些语义可被读出**——
这直接服务 C1–C4（对象清单、可编辑分级、关系闭包）。
**尤其 undoc 明确写「with CJK support」**，值得细看。

### 形态 6：预览/渲染路线（不生成，只显示）

### 8.2 ⚠️ 门槛规则缺陷（本轮发现的自身问题）

第一轮扫描时，我给 G1–G5 加了一条**附加规则**：

> 「创建不足 1 年 → 无长期维护证据 → 淘汰」

**这条规则有缺陷**：它把**「新项目」与「无人维护」混为一谈**。
本轮数据暴露了误杀：

| 被误杀者 | 创建时间 | 近 180 天提交 | 最后提交 | 实际情况 |
| --- | --- | --- | --- | --- |
| betteroffice | 2026-07 | **100 条** | 本周 | 极活跃，只是年轻 |
| office_oxide | 2026-03 | **91 条** | 本周 | 极活跃，只是年轻 |
| genoffice | 2026-07 | **100 条** | 本周 | 极活跃，只是年轻 |

而同期真正该淘汰的 `pptx-template` 是**近 180 天 0 提交**——
**「新而活跃」与「老而停更」是相反的情况，却被同一条规则一刀切。**

**背景**：PPTX 生态正处在新项目密集出现的窗口期——
Rust 原生 OOXML 引擎（betteroffice / office_oxide / ppt-rs / undoc）
几乎全是 2025-Q4 至 2026 年内冒出来的。
用「年龄」当淘汰线，在这个窗口期会**系统性误杀最相关的新方案**。

### 8.3 规则修订建议

「维护性」应由**活跃度指标**判断，而非**年龄**：

| 旧规则 | 建议新规则 |
| --- | --- |
| 创建不足 1 年 → 淘汰 | **不发版 + 无提交** → 淘汰 |
| — | 新项目须补「维护承诺证据」：① 发版节奏（≥2 次）；② 近 90 天有提交；③ issue 有响应；④ 有组织/团队背书而非纯个人 |

**判定分层**：

- **过门**：发版节奏稳定 + 近 90 天活跃 + 头号贡献者 <80%
- **观察**：新但极活跃（如 genoffice）——**不淘汰，但需持续观察**，并明确「若 6 个月内仍无第二个稳定维护者，降级」
- **淘汰**：停更、无发版、头号 ≥80% 且无组织背书

**修订后，betteroffice / office_oxide / genoffice 应从「淘汰」改为「观察」。**

修订规则后，原生引擎候选集变为：

| 候选 | 状态 |
| --- | --- |
| Open XML SDK（C#） | 过门 |
| Apache POI（Java） | 过门 |
| **betteroffice（Rust）** | **观察**（新但极活跃；Apache-2.0；声称含 rendering） |
