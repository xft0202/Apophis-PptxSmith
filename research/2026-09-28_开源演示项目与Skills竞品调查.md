# 开源演示项目与 PPT/Slides Skills 竞品调查

访问日期：2026-09-28。范围：六项指定对象的第一方 README、SKILL.md、相关脚本及许可证；已读项目《当前需求与工作约定》。没有安装、执行项目代码、调用生成 API、生成演示稿或开展效果 benchmark，也未亲看成品，因此不评价视觉美丑。以下是文档声明与静态源码证据，不是实测结论。未独立核验热度、提交频率及采用量，维护快照由父报告补充；整仓星数不能代表单个 skill 的采用量。

## 简洁结论

最强差异不是“能否生成 PPT”，而是**编辑发生在哪里、交付保留什么对象**：Presenton 是带编辑器的完整产品；banana-slides 是整页图像生成与编辑产品，另有 Beta 可编辑重建路径；PPTAgent 当前主分支已转向 HTML 作者流程与 PPTX 审核工具链。三种 skill 则分别强调直接操作 PPTX、浏览器演示、图像页编排，不能混为同类成品平台。

建议优先深入 Presenton 的生成—人工修改衔接、PPTAgent 的导出前后检查，以及 banana-slides 的图像重建成本；从 frontend-slides 借鉴视觉预览决策，从 baoyu 借鉴逐页提示词与局部重生成。Anthropic pptx 可作为能力机制对照，但子目录专有许可不应被整仓印象覆盖。这是进一步研究建议，不是采用授权或技术选型。

## 四维比较

### 交互流程与视觉机制

| 对象与性质 | ①交互与生成流程 | ②页面设计与视觉表现机制 |
|---|---|---|
| Presenton：完整应用/API | 提示词、文档或既有 PPT 设计起步；模板选择后生成，提供拖拽手工编辑。[P1] | HTML/Tailwind 模板、主题和自定义设计；README 列出图表、图标等素材能力。“全可编辑”是官方声明。[P1] |
| PPTAgent：研究项目，当前主分支提供 skill | 宿主 agent 编写 HTML，CLI 渲染、记录逐页审核，转换后再审核 PPTX；保留源稿供追改。〔A1、A2〕 | 静态 HTML/CSS；检查源页与导出页，修改共享素材会使旧审核失效。是流程规定，不代表自动证明质量。[A2] |
| Anionex/banana-slides：完整应用 | 想法、大纲、页面描述三种入口；自然语言修改、框选编辑、整页重绘。[B1] | 图像模型联合生成文字与画面；参考图及逐页模板约束风格。核心不是传统对象布局编辑器。[B1] |
| Anthropic pptx：文档处理 skill | 新稿使用 PptxGenJS；旧稿/模板采用解包、修改 XML、重打包；另提供读取和缩略图工具。[H1] | 提示词规定配色、层次、布局；要求内容检查、结构校验和渲染目检。未证明这些规则必然带来高质量。〔H1、H2〕 |
| frontend-slides：coding-agent skill | 新建、PPTX 转网页、增强 HTML；默认先展示三种真实首页预览，再扩展全稿。[F1] | 固定 1920×1080 舞台等比缩放；CSS 动画、风格预设和密度模式；手机端不重排正文。[F1] |
| baoyu-slide-deck：图像编排 skill | 内容分析→确认→大纲→逐页提示词→批量生图→合并；支持指定页重生成。[Y1] | 纹理、情绪、字体、密度组合风格；参考图参与生成。默认面向阅读分享而非现场讲述，这是该 skill 的假设。[Y1] |

### 材料处理与输出修改

| 对象 | ③内容与材料处理、依赖 | ④输出格式、对象与后续修改 |
|---|---|---|
| Presenton | 文档上传、既有 PPT 设计转模板；文本模型与图片服务可分别配置，也列出本地模型选项。不能把“本地运行”理解为所有配置都无外部调用。[P1] | PPTX/PDF；网页拖拽编辑与导出后编辑是两层。导出入口调用独立 `@presenton/export-core`；本轮未读到完整对象映射，不能确认每类图表、形状均为原生对象。[P2] |
| PPTAgent | 宿主负责研究和材料综合；MinerU、搜索可选；文本宿主需要外部视觉模型，图像能力宿主可自行审核。[A2] | HTML 源稿、官方称可编辑的 PPTX、预览与审核报告；CLI 引用 HTML→PPTX 转换器。字体度量可能改变换行，完整对象支持矩阵未知。〔A2、A3〕 |
| banana-slides | PDF/Docx/MD/Txt 解析及图片入库；需文本/图像模型；可编辑导出还涉及 MinerU、百度 OCR 或背景修复等选项。〔B1、B2〕 | 普通 PPTX 每页铺整图；Beta 路径重建文字和图像等元素，部分表格处理失败退回图片。另列 PDF/MP4。应用内框选重绘不等于导出后逐对象编辑。[B2] |
| Anthropic pptx | 读取 PPTX/POTX、模板、备注等；依赖宿主模型，以及 PptxGenJS、MarkItDown、LibreOffice、Poppler 等工具。[H1] | 直接生成或修改结构化 PPTX，而非默认图片页；指引强调原生图表，特殊图可为图片。复制页仍可能共享图表等部件，不能视为无损通用编辑。[H1] |
| frontend-slides | PPTX 提取脚本读取文本框、图片和备注；未见图表、表格及分组对象的完整保真转换。生成依赖宿主 agent；字体可来自外站。[F2] | HTML/CSS/JS，可浏览器内改字；PDF 脚本逐页截图再合成，丢失动画和文字对象。所读路径未提供 PPTX 导出，不能反推网页可编辑即 PowerPoint 可编辑。〔F1、F3〕 |
| baoyu-slide-deck | 文本、参考图、风格提示词；依赖运行环境可用的生图后端与相应凭据，合并使用 Bun/Node 生态工具。[Y1] | PNG、PDF、图片页 PPTX。合并脚本每页 `addImage` 全铺，并可把提示词写入备注；改字需改提示词重生成，不是编辑幻灯片文字对象。[Y2] |

## 各项借鉴与限制

1. **Presenton**：优势是把模板、模型配置、生成、手工修改和导出接在同一产品内。值得研究用户如何从自动稿接手修改；不能照搬“全可编辑”宣传，需要补查独立导出引擎及不同对象的退化规则。〔P1、P2〕
2. **PPTAgent**：优势是明确区分“渲染了”与“审核通过”，并追踪修改后的证据时效；可借鉴导出前后都检查。限制是转换器、浏览器、LibreOffice 与视觉模型组成较长依赖链；不能把审核通过等同于跨软件保证，也不应照搬其强制交付流程为本项目需求。〔A2、A3〕
3. **banana-slides**：归属已由 `Anionex/banana-slides` README 的克隆地址、作者链接及文档入口交叉确认，不是搜索中出现的 `Anionex/PPTAgent`。优势是整页创作和局部重绘连贯；值得研究“先做画面，再重建编辑对象”的交互。限制是 OCR、背景修复、表格回退引入额外误差和调用成本，不能直接将重建解释为原稿语义恢复。〔B1、B2〕
4. **Anthropic pptx**：优势在既有稿处理、模板复用及结构校验的细致故障知识；可借鉴检查类别和变更后复核思想。限制包括部件共享、字体替代及环境依赖；其设计规则不宜固化为所有演示的审美标准，更不能在未获授权时复制专有实现。〔H1、H2、L4〕
5. **frontend-slides**：优势是先看具体预览再谈风格，值得借鉴低成本方向确认；HTML 动效和浏览器修改是独立价值。限制是转换脚本覆盖有限、PDF 为截图、固定舞台在小屏只缩放；不能把它当作保真 PPT 往返工具。[F1–F3]
6. **baoyu-slide-deck**：优势是源内容、大纲、逐页提示词、图片分开保存，支持单页重做；值得借鉴生成记录和失败项局部重试。限制是错字通常需重新生图；默认阅读型密度与禁止位图文字覆盖属于其流程选择，不应照搬成我们的人群或任务限制。〔Y1、Y2〕

## 许可、版本与证据冲突

许可证本体核对：Presenton 根目录为 Apache-2.0；PPTAgent、frontend-slides、baoyu-skills 根目录为 MIT；banana-slides 为 AGPL-3.0；Anthropic `skills/pptx/LICENSE.txt` 为专有条款，涵盖代码、提示词与资产等，并列出复制、派生和分发限制。前述根目录结果不是全部依赖/素材许可审计，开源也不等于项目已决定采用。[L1–L6]

banana-slides README 用“非商业用途”“闭源商业授权”说明使用方式，而 LICENSE 为 AGPL 正文；两者表述范围不能直接等同，本报告不自行归纳为“禁止商用”，复用前应澄清适用条件。〔B1、L3〕

PPTAgent README 明确区分当前 skill 与历史研究复现：EMNLP 2025 对应 `v0.2.0`，DeepPresenter 对应 `v1.1.38`。当前 HTML 工具链不能替代旧版论文结果，旧论文优势也不能自动证明当前 skill。[A1]

frontend-slides 的“零依赖单文件”指演示运行形态；同一指引使用外部字体，PDF 导出需 Playwright/Chromium，部署另有工具。应区别浏览器展示、生成和导出三个环节。〔F1、F3〕

## 优先深入建议与关键未知

**建议顺序**：先补 Presenton 的对象导出边界与人工修改链，再补 PPTAgent 的审核实际检出率，接着研究 banana-slides 图片重建的可控性；三者分别回答产品接手、质量控制、图像自由度与修改成本。frontend-slides 和 baoyu 的交互机制可并行吸收，不需要先选定引擎。

决定质量或成本的五个未知：
- **导出对象**：复杂图表、公式、表格、分组与字体分别保留到什么程度，何时栅格化或拆散？
- **修改代价**：小改字、小改数据能否只重做局部，还是触发全页/全稿重生成与复核？
- **实际成本**：模型、生图、OCR、修复、视觉审核及重试的总调用量与等待时间，尚无可比实测。
- **材料忠实度**：扫描文档、中文密集资料、数字和引用在提取—生成—导出间的错误率未知。
- **质量判断**：自动结构检查和视觉审核能检出多少用户可见问题，漏检与人工返工负担未知。
