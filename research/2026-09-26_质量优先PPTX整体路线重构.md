# 质量优先的 PPTX 整体路线重构（研究阶段）

- 日期：2026-09-26
- 性质：路线研究，不是 ADR，不是实现规格，不授权 benchmark
- 纠偏目的：把研究重心从某个兼容宿主或候选 SDK，拉回最终 PPTX 质量和交付适用性

## 1. 先纠正研究对象

此前的路线比较容易滑向“哪个库的 API 最多”或“哪个历史验收宿主最熟悉”。这两个问题都不是最终目标。

真正要比较的是整体架构形态：

```text
内容/事实模型
    -> 页面与图表规划
    -> 模板/母版/版式选择
    -> 作者引擎
    -> PPTX 部件与关系
    -> 目标宿主打开/编辑/保存/重开
    -> 对象级、视觉级和审计级验收
```

WPS、PowerPoint、Aspose、Syncfusion 和 GemBox 都只是这个链条中的某个宿主或作者引擎，不应单独成为研究中心。

## 2. 最终质量的优先级

### P0：语义完整性

必须优先保证：

- 原生图表部件；
- 图表关联的嵌入工作簿；
- workbook、series/category、缓存和关系一致；
- 原生表格；
- 真文本和富文本；
- 备注页；
- 母版、版式、主题和占位符继承；
- 未授权部件不被静默删除、图片化或改写。

### P1：目标宿主保真

在指定目标软件中：

- 打开成功；
- 图表可编辑；
- 工作簿可编辑；
- 表格仍是表格；
- 备注仍是备注；
- 母版和版式继承正常；
- 保存、关闭、重开后语义不漂移。

### P2：中文排版质量

必须控制：

- 字体文件和 fallback；
- 中西文混排；
- 行高、字距和换行；
- 标题和正文零溢出；
- 表格、图表标签和备注的中文可读性；
- 不把浏览器 CSS 字体名直接泄漏为 PPTX 字体策略。

### P3：模板和品牌保留

必须保留或明确迁移：

- theme；
- master/layout；
- placeholder；
- 品牌色和字体；
- 页脚、Logo、页码；
- 图表皮肤；
- 未修改模板部件。

### P4：可审计和可复现

每份产物都应能解释：

- 内容事实来自哪里；
- 为什么选择某种页面角色和图表；
- 哪个作者引擎和版本生成；
- 使用了哪个模板、母版和字体；
- 哪些部件被新增、修改或保留；
- 目标宿主如何打开、编辑、保存和重开；
- 哪些对象被阻断或降级。

### P5：部署和成本

只有在 P0-P4 有证据后，才比较：

- Linux/Docker；
- Windows/Office 桌面依赖；
- 许可证；
- 并发和队列；
- 运行时维护；
- 升级和回滚；
- 供应商支持。

**原则**：工程便利和部署便利不能抵消 P0-P2 的产物失败。

## 3. 五种整体架构形态

### 3.1 形态 A：目标宿主原生作者

作者引擎就是最终主宿主，例如 PowerPoint Desktop 自动化。

**质量上限**：

- 目标宿主自己的对象模型和保存引擎；
- 目标宿主的图表、工作簿、备注、母版和字体语义；
- 对该宿主的保存保真推断最强。

**结构性风险**：

- 交互式桌面依赖；
- 无人值守服务端不受供应商支持；
- 用户配置、模态对话框、并发和死锁；
- 不能自动推导其他宿主兼容。

**适用判断**：

- 如果唯一最高优先级目标是 PowerPoint 交付，它是质量上限候选；
- 如果需要普通 Linux 服务或多宿主等价，它不是无条件最优。

### 3.2 形态 B：独立语义 PPTX 引擎

使用 Aspose.Slides、Syncfusion Presentation、GemBox.Presentation 等独立 SDK 直接创建/编辑 PPTX。

**质量上限**：

- 可以服务端运行；
- 可以锁定 SDK、运行时、模板和字体；
- 适合把内容模型、页面规划和对象生成拆开；
- 能在没有 Office 的环境中生成和渲染。

**结构性风险**：

- 独立引擎不等于 PowerPoint 保存引擎；
- “支持图表”不等于“带合法可编辑嵌入工作簿”；
- 未知部件保留可能随 SDK 版本变化；
- 目标宿主重开仍必须单独验收。

**适用判断**：

- 如果产品优先考虑可控服务化，这组路线最值得比较；
- 最终质量取决于对象语义和模板保留证据，而不是 API 数量。

### 3.3 形态 C：模板优先的受控变更

以已经验证过的模板、母版、版式和原生图表为基线，只修改授权内容。

**质量上限**：

- 未修改的模板结构理论上最容易保留；
- 品牌视觉、版式和字体可以先由人工验证；
- 适合经营汇报、月报、季度汇报等受控页面集合。

**结构性风险**：

- 自由生成能力较弱；
- 图表、工作簿、关系和缓存更新复杂；
- 模板自身的版本、字体和授权成为产品依赖；
- 不同作者 SDK 仍可能重写未授权部件。

**适用判断**：

- 它不是独立引擎，而是质量策略；
- 适合与形态 A、B 或 OPC 局部工具组合；
- 对首期“商务汇报新稿编译”可能比空白生成更接近交付质量。

### 3.4 形态 D：语义中间层 + 多作者适配器

先建立与宿主无关的逻辑真相和 PPTX 语义中间模型，再连接不同作者引擎。

中间层至少应表达：

- 页面角色和版式选择；
- 真文本、表格、图表和备注；
- 图表数据、单位、标签和 workbook 关系；
- 模板、母版、主题和字体要求；
- 来源、审计和阻断规则；
- 对象级和视觉级验收结果。

**质量上限**：

- 内容与作者引擎解耦；
- 可以针对 PowerPoint、独立 SDK 或模板策略选择不同适配器；
- 单页重排不会被迫重建整稿；
- 能把“无法原生实现”的对象提前阻断。

**结构性风险**：

- 中间模型设计过宽会掩盖不同引擎的语义差异；
- 适配器不能凭抽象接口制造不存在的 workbook/notes/preservation 能力；
- 每个适配器都需要自己的版本和产物证据。

**适用判断**：

- 这是最有希望成为长期产品架构的形态；
- 但它不等于已经选择某个具体引擎；
- 首期应先覆盖真实需要的语义子集，不应追求万能格式抽象。

### 3.5 形态 E：浏览器/HTML/SVG 视觉导出

**可吸收部分**：

- 视觉草稿；
- 页面级预览；
- 设计探索；
- 非最终素材的布局试算。

**必须拒绝作为最终作者**：

- 无法可靠表达原生图表和嵌入工作簿；
- 形状拼图不等于对象语义；
- CSS 字体、浏览器布局和 PPTX 排版不是同一系统；
- 整页位图直接违反原生可编辑目标。

## 4. 质量优先的路线判断

当前不应问：

> 哪个 SDK 的功能清单最长？

应问：

> 在指定交付场景下，哪种架构能以最少不可控转换，稳定保留 P0-P4 的语义和证据？

按这个问题，当前研究结论是：

1. **长期产品架构优先研究形态 D**：语义中间层 + 受控作者适配器；
2. **产物策略优先研究形态 C**：模板优先、只改授权内容；
3. **PowerPoint 单宿主质量上限研究形态 A**；
4. **服务化质量上限研究形态 B**；
5. **形态 E 只能作为预览/设计辅助，不能进入最终作者候选**；
6. **WPS 只是次级兼容宿主或待证作者适配器，不再作为主路线研究轴**。

这仍然不是引擎选型。它只是把“整体路线”从候选名称中解耦出来。

## 5. 研究决策门

只有以下问题都能回答，才值得进入真实产物比较：

| 决策门 | 必须回答的问题 |
| --- | --- |
| 目标门 | 首期最终交付主要由哪个软件打开、编辑和保存？ |
| 语义门 | P0 语义的最小不可退让集合是什么？ |
| 模板门 | 采用空白生成、模板新稿，还是模板受控变更？ |
| 作者门 | 哪个作者形态能直接产生目标对象，而不是先生成图片再包装？ |
| 保存门 | 谁负责最终保存：目标宿主、独立 SDK，还是包级操作器？ |
| 审计门 | 能否输出部件、关系、对象和来源清单？ |
| 失败门 | 不支持对象是否阻断，而不是静默降级？ |
| 版本门 | 能否锁定作者、宿主、模板、字体和运行时？ |

## 6. 当前结论

> **最值得继续推进的不是 WPS API 深挖，也不是立即选择某个 SDK，而是“语义中间层 + 模板优先 + 受控作者适配器”的整体路线研究。**

其中：

- PowerPoint 原生自动化代表 PowerPoint 单宿主的质量上限；
- 商业 SDK 代表独立服务的质量上限；
- 模板优先代表保留既有高质量结构的策略；
- OPC 包级工具代表局部保护和审计工具；
- WPS 只在明确业务要求时作为兼容宿主或待证适配器进入矩阵。

本文件不授权实现、不授权 benchmark、不宣布最终引擎。

## 7. 吸收分类

| 对象/机制 | 吸收分类 | 边界 |
| --- | --- | --- |
| 语义中间层中的页面、图表、来源和审计契约 | **适合二开** | 只覆盖项目真实需要的语义，不做万能 PPTX 抽象 |
| 模板优先和授权对象变更 | **可直接复用** | 作为首期产物策略，不保证模板自由生成 |
| PowerPoint 原生作者适配器 | **仅可借鉴** | 绑定 PowerPoint 版本和受控 Windows 环境 |
| 独立 SDK 作者适配器 | **仅可借鉴** | 每个 SDK 必须独立通过对象和宿主验收 |
| OPC 包级局部保护 | **适合二开** | 用于未修改部件、关系和审计，不承担自由排版 |
| HTML/SVG 最终导出 | **应当淘汰** | 不满足原生对象和嵌入工作簿目标 |
| 把 WPS 兼容性当作整体路线目标 | **应当淘汰** | 兼容宿主不应反向决定作者架构 |
