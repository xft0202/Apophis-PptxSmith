# 终决文档引擎与总技术栈

Type: grilling
Status: open
Blocked by: 02, 03, 04, 13, 14, 15, 16, 17, 18, 19, 20

## Question

在引擎基座复用盘点、QA 工具盘点和字体校准方案完成后，终决五年维护视角下的技术栈，并更新/替代 ADR-0003 与 ADR-0009。

必须明确：

- 文档引擎、后端、前端、量字、校验、渲染、模型接入各自的责任边界；
- 复用、二开、自建三者的边界与排序原则；
- .NET/Open XML SDK、ShapeCrawler、OfficeCLI、其他方案的最终取舍；
- 未来 Rust 客户端如何复用服务端能力，避免不必要的引擎重写；
- 维护、替换、贡献者进入和 Docker 部署成本。

## Decision standard (must pass before any stack is accepted)

技术选型服务于以下核心目标，不能反过来让目标迁就语言或库：

1. **用户交付目标**：用户拿到的 PPTX 能在 Microsoft PowerPoint/WPS 中打开、继续编辑并用于正式汇报；文本、表格和图表不能被图片化替代。
2. **保真目标**：未来受控补丁必须能只改授权对象；未知部件、关系、备注、嵌入对象和未触及页面不得静默丢失或改变。
3. **中文质量目标**：同一套确定性的 shaping/量字规则支撑折行、行高、溢出和审计；WPS 与 PowerPoint 的差异必须可测量、可报告。
4. **长期维护目标**：核心能力必须建立在可验证的成熟方案或可控二开上；不能把 alpha 库、单作者库或未经语料验证的宣传能力当作基础；项目要能持续吸收贡献者。
5. **开源部署目标**：Linux Docker、多用户、自配模型、MIT 项目依赖政策、可替换 provider 和未来 Rust 客户端 API 边界不能被技术选型破坏。
6. **产品体验目标**：技术栈必须支持四道门、可回滚、来源/成本/审计可见，而不是只让开发者“能生成文件”。

候选必须依次通过四道门：

- **证据门**：许可证、维护状态、源码/API、平台和限制可核验；
- **语料门**：同一批真实/构造 PPTX 上通过打开保存、文字/表格/图表修改、嵌入工作簿、未知部件和关系保留测试；
- **交付门**：PowerPoint/WPS 重开、编辑、渲染和审计结果通过；
- **维护门**：二开边界、上游替换、贡献者进入、故障回退和未来 Rust 客户端路径清楚。

最终结果可以是“一个核心引擎 + 若干适配器”，不要求为了形式统一把所有能力塞进一种语言；但任何额外引擎都会增加测试矩阵，必须证明其收益大于复杂度。

在上述证据完成前，本票不接受“看起来最合理”的最终选型，也不直接确认 ADR-0009。
