# 评估材料解析与渲染服务体系

Type: research
Status: open
Blocked by: 13, 21

## Question

调查材料解析、图片/图表提取、生图、PPTX 预览、PDF/PNG 渲染和目标软件验收之间的服务边界。

必须比较：

- DOCX/PDF/XLSX/Markdown/TXT 解析方案及保留来源的能力；
- 图片、表格、图表、备注和附件的抽取策略；
- LibreOffice、OnlyOffice、原生渲染器、PowerPoint/WPS 抽检的职责边界；
- 生图 provider 的可替换接口、版权/来源记录和失败降级；
- 预览格式与 PPTX 语义事实源的关系；
- 容器隔离、资源限制、超时、崩溃恢复和缓存。

目标是建立可替换的材料/渲染适配层，不把某个转换器当作全部产品能力。

## Reopened

本票原有答案已撤回为研究记录。Docling、MinerU、LibreOffice、ONLYOFFICE 和 .NET compiler 等都只是候选证据，不能在全景架构和许可证/维护调查完成前写成强候选或默认组合。需要重新比较更多解析、渲染、办公兼容和数据平面方案。

> **当前状态警告**：下方原有解析器、渲染器和编译器候选结论均为全景调查前的历史研究记录，已撤回，不得作为当前技术或 ADR 依据。全景票 21 关闭后必须按统一材料、PPTX、目标软件、许可证、恢复和替换夹具重新评分。

### 1. 结论

材料解析、PPTX 编译、预览渲染和目标软件验收必须是四个可替换层：

```text
原始材料 Blob
  -> 安全预检/隔离
  -> Parser Adapter
       -> Canonical Source Document + stable locators + provenance
  -> Content/Fact pipeline
       -> Semantic Object Model
  -> PPTX Compiler (.NET/Open XML candidate)
       -> OPC/package/semantic/font QA
  -> Preview Renderer (LibreOffice or other isolated renderer)
       -> PNG/PDF preview + diff signal
  -> Target Software Gate (PowerPoint/WPS)
       -> final audit and delivery
```

没有任何解析器或渲染器可以单独证明“事实正确、中文无溢出、PPTX 原生可编辑、PowerPoint/WPS 可交付”。

**初步方案**：

- `Docling` 作为 MIT、可本地运行的通用材料解析强候选，重点评估 PDF/DOCX/PPTX/XLSX/图片的结构化输出、表格/布局/OCR 和来源定位；
- `Apache Tika` 作为轻量格式检测、metadata/text fallback，不承担复杂版面和表格事实抽取；
- `MinerU` 作为高质量 PDF/复杂版面实验候选，但其当前许可证/AGPL 组件/模型依赖边界不进入 MIT 核心默认；若使用，隔离为用户自行部署或单独许可审查的 parser service；
- `Unstructured` 作为 Apache-2.0 的通用 partitioning/chunking 对照，不能假定它对中文商务 PPTX 的图表语义和原始定位自动满足要求；
- `LibreOffice headless` 作为 Linux 预览、批量 PDF/PNG 和独立转换失败信号；不作为中文最终验收或 PPTX 事实源；
- `ONLYOFFICE` 作为外部兼容性/编辑器对照选项；DocumentServer 仓库为 AGPL-3.0，不能默认嵌入 MIT 核心；
- PowerPoint/WPS 目标软件抽检是最终交付门，不能由 LibreOffice/ONLYOFFICE 替代。

### 2. 解析候选矩阵

| 候选 | 主要价值 | 保留边界 | 许可证/运维 | 分类 |
| --- | --- | --- | --- | --- |
| Docling | MIT；多格式、PDF layout、表格、OCR、图片、统一 `DoclingDocument`、本地/air-gap 能力 | 必须验证中文、PPTX/XLSX 图表、稳定 locators、表格数值和版本输出；解析结果不是 PPTX 事实源 | Python/native/模型依赖，需要 worker 资源隔离 | **强候选/适合二开** |
| MinerU | PDF/Office 转 Markdown/JSON；复杂版面、公式、表格、图片和 OCR 能力强 | 需验证许可证、YOLO/模型/依赖逐项边界；不把 Markdown 当原始事实 | Docker/GPU/模型和 AGPL/非商业组件风险 | **必须隔离/实验候选** |
| Unstructured | Apache-2.0；多格式 partition、chunk、embedding/RAG 生态 | 需自己补来源 locator、中文版面、表格/图表语义和包级保真 | Python 依赖与 enterprise platform 边界需锁版本 | **可选适配/对照** |
| Apache Tika | Apache-2.0；格式检测、metadata、通用文本抽取范围广 | 不承担复杂 layout、视觉结构、图表数据和中文字形 | Java 服务/进程可独立 | **fallback/可直接复用边界** |
| PyMuPDF | PDF 高性能抽取/渲染 | 当前仓库 AGPL-3.0；若采用需双许可或隔离审查 | native 依赖和许可证风险 | **隔离/不进 MIT 默认** |
| python-docx/openpyxl 等 | 针对 DOCX/XLSX 的局部结构读取 | 只处理所支持的对象，不宣称完整 Office round-trip | 单库边界清晰但需补来源定位 | **按格式适配** |

GitHub API 快照显示 Docling、MinerU、Unstructured 活跃，但 stars/forks 不是解析正确性的证据。Context7 官方资料确认 Docling 的统一文档模型、布局/表格/OCR和多格式能力，MinerU 的 PDF/Markdown/JSON/表格/公式能力，Tika 的 metadata/text extraction 能力；这些能力都必须在本项目中文材料 fixture 上重新验证。

### 3. 规范化材料合同

所有 parser adapter 输出统一的 `CanonicalSourceDocument`，而不是直接输出 prompt 字符串：

```text
Document
  - source_id / source_version / content_hash
  - source_type / parser_id / parser_version
  - pages / sheets / slides / sections
  - blocks: text | table | image | chart | formula | attachment | note
  - locator: page/slide/sheet/row/column/bounding_box/paragraph
  - reading_order / language / confidence
  - original_fragment_ref
  - warnings / unsupported_features
```

合同要求：

- 原始 blob 永远保留；规范化文档是可重建派生物；
- 每个数字、单位、表格单元格和结论都能回指 source locator；
- 解析不确定性、OCR 置信度、图表识别失败和缺字必须显式记录；
- 解析器不能自行改写用户事实；摘要和事实抽取属于后续受控步骤；
- parser 版本、模型版本、字体/语言包和参数进入派生 hash，换版本自动产生新解析版本；
- “无法解析”优先生成结构化阻塞，而不是静默丢弃内容。

### 4. 图片、表格、图表、备注和附件

- **文本**：保留段落/运行级 locators；中英文数字和标点不要在 parser 阶段合并到不可回溯字符串；
- **表格**：保留行列、合并单元格、显示文本、原始数值、单位、公式/缓存和来源位置；任何 OCR 表格都标识为低置信度并要求审计；
- **图表**：优先读取原生 chart XML 与嵌入 workbook；图片图表只能生成“待识别图表”候选，不能自动承诺 A 级可编辑；
- **图片**：保留原始 blob、尺寸、色彩、页/框位置、来源/版权信息和处理链；OCR 文本与图片原件都保留；
- **备注/附件**：作为独立 block，不能默认丢弃；未支持对象进入 unsupported inventory；
- **公式**：保留原文、结构化形式和渲染/转换状态；不能把截图公式默认为可编辑 OMML；
- **外链/OLE/宏**：记录存在性和风险，不执行、不自动下载、不自动跟随链接。

### 5. 渲染与验收职责

| 层 | 工具/实现 | 可以证明 | 不能证明 |
| --- | --- | --- | --- |
| 包/schema | Open XML SDK validator + 关系/部件闭包检查 | OPC/XML/关系合法、目标存在、结构化规则通过 | PowerPoint/WPS 视觉和编辑体验 |
| 语义 QA | 对象清单、A/B/C/D、数值/来源/授权范围探针 | 语义对象和事实合同是否满足 | 目标软件字体替换和最终显示 |
| 几何/字体 | HarfBuzz-backed shaping/measurement + overflow/overlap | 预测排版、边界、中文溢出风险 | 真实 Office renderer 完全一致 |
| 预览转换 | LibreOffice headless PDF/PNG；必要时其他隔离 renderer | 批量预览、转换失败、第二渲染信号、视觉 diff 候选 | PowerPoint/WPS 最终真相，尤其中文行高/字体 |
| 外部编辑对照 | ONLYOFFICE 或用户自有办公服务 | 额外兼容性信号和人工编辑体验 | MIT 默认可嵌入；不替代目标软件 |
| 目标软件 | Microsoft PowerPoint/WPS Windows 抽检/自动化夹具 | 打开、编辑、保存、重开、汇报前可用性 | Linux CI 单独完成全部覆盖 |

LibreOffice 的 GPL-3.0 代码作为外部进程/用户自装工具，需要单独处理再分发边界；本项目可以把它作为可选 QA 容器或用户提供的验证环境，不把其内部代码链接进 MIT 核心。ONLYOFFICE DocumentServer 的 AGPL-3.0 许可同理且更严格。

### 6. 预览与 PPTX 事实源

- 浏览器预览、SVG、PNG、PDF 都是 preview artifact，不得反向覆盖语义对象或原始包；
- 预览 artifact 绑定 `artifact_id`、source/version hash、compiler/parser/renderer/font versions 和生成时间；
- 视觉 diff 只能发现“可能不一致”，修复必须回到语义对象/样式/字体/编译器层；
- PPTX 交付必须同时具有源对象清单、包闭包、编辑探针、中文几何和目标软件抽检记录；
- 如果预览器与目标软件矛盾，报告两者差异并以目标软件门为交付决策，不让预览器静默覆盖。

### 7. 生图 provider 边界

生图是独立 provider 类型，不和 LLM 或材料 parser 共用假接口：

- `ImageProvider` 声明尺寸、透明度、风格参考、seed、编辑/变体、超时、内容策略和输出格式能力；
- 每个结果保存 provider/model/request hash、prompt policy、seed、输入图 hash、生成时间、版权/来源声明、用户授权和成本；
- 图片嵌入 PPTX 前做 MIME/尺寸/解码/恶意载荷/色彩和版权来源检查；
- provider 失败时优先使用用户素材、明确占位符或无图布局，不静默生成不相关图片；
- 不把网络图片抓取当作默认生图；联网检索和外部图片必须显式开启并记录来源；
- 商用素材/字体/图片许可证与代码许可证分开审计，不能因为 provider API 可调用就默认允许再分发。

### 8. 隔离、资源和缓存

解析、渲染和生图均运行在受控 worker：

- 非 root、只读基础文件系统、仅授予任务临时目录、无默认网络出口；
- CPU、内存、临时盘、进程数、文件 descriptors、超时和输出大小上限；
- 每个任务使用独立工作目录和 correlation id，异常退出后清理；
- 解析缓存 key = blob hash + parser/version + config/model/font；渲染缓存 key = source/artifact hash + renderer/version + font/theme；
- 缓存不可改变权限；跨成员相同 hash 共享时只能共享不可变字节，读取仍经过授权；
- 失败缓存保留有限诊断和输入 hash，不保留完整敏感原文/密钥；
- renderer 崩溃、超时和不支持格式进入结构化错误，不由 API 进程重启自身。

### 9. 最小方案与扩展方案

**v0.1**：

- Docling/适配器做材料抽取实验，Tika 做格式/metadata fallback；
- .NET/Open XML 作为 PPTX compiler/QA 强候选；
- LibreOffice headless 作为可选预览/第二信号 worker；
- PowerPoint/WPS 通过固定 Windows 夹具进行目标软件门；
- 生图使用 provider registry，默认允许用户素材/占位符降级；
- 所有 worker 通过票 15/17 的任务、BlobStore 和审计合同接入。

**扩展**：

- GPU/复杂 PDF parser 独立 worker；
- MinerU 用户自部署隔离服务（许可和模型逐项通过后）；
- ONLYOFFICE 用户自有服务作为可选协作/兼容性集成；
- 多 renderer/版本矩阵和视觉 diff farm；
- provider-specific OCR/vision fallback，但必须保持 canonical source contract。

### 10. 硬淘汰条件

- 解析器输出无法回到原始材料定位，或会静默改写数字、单位、结论；
- 将 PDF/图片/HTML/SVG 直接作为 PPTX 交付，承诺“可编辑”却没有原生对象探针；
- renderer 只能在请求进程内运行，无法限制资源、网络、临时目录和超时；
- 把 LibreOffice/ONLYOFFICE/浏览器截图当作 PowerPoint/WPS 最终验收；
- 许可证、模型权重、字体或图片资产边界不清却进入默认 MIT 发布包；
- 不支持的宏/OLE/外链/未知部件被静默执行、下载、删除或转换；
- 缓存跨项目/成员泄露，或缓存命中后跳过权限和版本校验；
- 生图失败导致整稿自动重复、成本失控或引入无来源资产；
- 解析/渲染过程没有结构化失败类别和可恢复/人工复核路径。

### 11. 最小验证计划

1. **材料同题集**：中文 PDF/DOCX/XLSX/PPTX/图片/扫描件，含表格、原生图表、图片图表、备注、公式、附件、混排和数字单位；比较 Docling、MinerU、Unstructured、Tika/专用 adapter 的 block、locator、事实和失败边界。
2. **来源保真**：随机抽取数字、单位、表格单元格和结论，验证每项可回指页/页框/段落/表格坐标，并验证 parser 版本变化产生新派生版本。
3. **PPTX 目标对象**：原生 chart/workbook、表格、文本、备注、未知部件、外链/OLE；检查 Open XML、关系闭包、编辑探针和 WPS/PowerPoint 重开。
4. **渲染对照**：LibreOffice PDF/PNG 与目标软件截图建立差异报告，确认差异只作信号，不把 LO 结果作为交付结论。
5. **恶意输入**：压缩炸弹、路径穿越、XXE/外链、超大图片、坏字体、损坏 PDF、宏/OLE、renderer 崩溃；验证隔离和 cleanup。
6. **缓存**：同 hash 重跑命中；parser/compiler/font/renderer 版本变化不误命中；不同 project/member 无法越权读取缓存。
7. **生图**：成功、超时、内容拒绝、错误格式、来源缺失和 provider 断线；验证占位符/用户素材降级、成本和审计。
8. **真实目标软件门**：至少在 Microsoft PowerPoint 与 WPS 各抽检打开、编辑、保存、重开和展示，记录具体版本/字体/环境。
