# 引擎能力对比：Open XML SDK vs Apache POI（同题实测）

Type: research
Status: open
Blocked by: 02

## Question

**活跃度门槛已筛完，只剩 2 个过门候选。哪个在我们的产品承诺上更强？**

- **Open XML SDK**（C#，MIT，`dotnet/Open-XML-SDK`）
- **Apache POI**（Java，Apache-2.0，`apache/poi`）

判据**只能是 PPTX 交付本身**，不是语言偏好、生态熟悉度或单项性能。
必须在**同一组同题材料**上比较，并接受**同一套目标软件验收**（WPS 11.8.2.8411，
Microsoft PowerPoint 侧按 ADR-0013 方案 A 记为未验证）。

## 必须回答的能力项（按产品承诺排序）

### P0：决定成败的三项

1. **读改既有包（受控补丁能力）**
   - 能否打开既有 PPTX 并只重写授权部件？
   - 未触及部件的字节是否原样保留？
   - Spike C1 已实测 Open XML SDK 通过（改图表 Q2 营收 15.1→88.8，
     并**同步图表缓存与嵌入工作簿**，WPS 复检通过）。**Apache POI 需同题实测。**
2. **未知部件 / 关系保留**
   - 含 master/layout/theme、notes、custom XML、未知扩展部件与未知关系的包，
     处理后是否原样保留？
   - 票 02 已注明：「未知部件『可保留』需**用回归夹具验证**，不能由文档直接推导」。
   - 夹具已就绪：`research/experiments/spike-D-fixtures/` 的 `品牌参考.pptx`
     含未知部件 `ppt/unknown/pptXsmithFixture.xml` + 未知关系，且生成器有三处路径一致性自检。
3. **嵌入工作簿与图表缓存同步**
   - 改图表数据时，`ppt/embeddings/*.xlsx` 与 `<c:cache>` 是否同步更新？
   - 这是 A 级语义的核心判据，也是 SANDUN 导出产物**完全缺失**的一项
     （实测其产物 0 个 chart part、0 个嵌入工作簿）。

### P1：决定可用性

4. **生成原生对象**：图表（带嵌入工作簿）、表格、文本框，是否均为原生部件？
5. **OOXML 校验**：是否有内建 validator（Open XML SDK 有 `OpenXmlValidator`）？
6. **中文排版承载**：能否精确控制字体、字号、行距、文本框尺寸，以配合量字引擎？
7. **备注页 / 母版 / 版式**：增删改能力如何？
8. **大文件内存行为**：票 02 记「.NET ZIP 包存在大文件内存风险」，需实测规模。

### P2：工程与长期

9. **许可证**：MIT / Apache-2.0 均在 ADR-0002 允许范围，但需核验**依赖树**
   （Apache POI 的传递依赖是否全为宽松许可）。
10. **部署形态**：是否能在单机 Docker 内运行（不引入超出单机规模的组件）？
11. **运行时成本**：镜像体积、内存占用、冷启动（对照 ADR-0007 单机前提）。
12. **上游替换路径**：若该候选后续出问题，替换成本如何（票 13 要求写明）。

## 方法要求

- **同题**：使用 `research/experiments/spike-D-fixtures/` 的固定材料
  （DOCX 含与 XLSX 冲突的 15.0、PDF 含提示注入文本、PPTX 含未知部件），
  材料字节可复现（三轮 hash 一致），**不得因候选不同而改题或降门槛**。
- **同一目标软件**：WPS 11.8.2.8411，**32 位宿主探针**（见验收矩阵 2.1），
  脚本须显式断言宿主为 `wpp.exe`。
- **同一判据**：A/B/C/D 可编辑性等级；不通过即淘汰，不得降级解释。
- **证据分级**：官方声称 / 第三方实测 / 本项目实测，逐条标注。

## 输出

1. **能力对比矩阵**：上列 12 项的逐项实测结果，两候选并列；
2. **同一兼容性语料库上的实测记录**：输入 hash、版本、命令、产物 hash、
   目标软件结果、失败对象清单；
3. **淘汰结论或并列结论**：若出现「只有一项过 P0」，必须明说；
   若两者都能过，则给出**非语言偏好**的取舍理由（或明确「不足以决定」）；
4. **实现语言的边界说明**：本票**只比引擎能力**。
   「引擎用哪个」与「控制面/worker 用什么写」是**两个决定**，
   后者不在本票范围（票 22 的「文档引擎与应用运行时解耦」合同正是为此存在）；
5. **许可证与依赖树核查报告**。

## 边界与前置事实（不得重复争论）

- 本票**不重新回答**活跃度门槛（票 02 已关闭）；
- 本票**不预判实现语言**：ADR-0003 仍 challenged，ADR-0009 仍 proposed；
- 本票**只围绕 PPTX**：任何与 PPTX 交付无关的比较项（前端、UI、平台类）
  不进入本票；
- 只做**决策与最小验证**，不建生产脚手架；验证原型放 `research/experiments/`
  并标注「可丢弃」（地图 Notes 的研究实验物豁免）。

## 与「以 SANDUN 为基线」的关系（所有者 2026-09-26）

所有者已定：**以 SANDUN 为基线建设**。本票与之的分工如下，**不得混为一谈**：

| 层 | 决定 | 状态 |
| --- | --- | --- |
| **产品形态与流程编排** | 采用 SANDUN 的分阶段流水线、阶段产物分离、逐页来源、风格库、项目连续性 | ✅ 已定（SANDUN 为基线） |
| **导出路线** | **不采用** SANDUN 的形状展平路线 | ✅ 已定（与其冲突，见下） |
| **导出引擎实现** | Open XML SDK 还是 Apache POI | ⬅ **本票回答** |

**为什么不能连导出路线一起照搬**：实测 SANDUN 导出产物为
0 个原生图表部件、0 个嵌入工作簿、0 个原生表格、0 个备注页，
411 个形状 + 307 个文本 run，图表被展平成形状拼图。
这与本项目两项核心承诺直接冲突：

1. **A 级原生语义**（图表可改数据、表格可增行）——展平后**做不到**；
2. **中文零溢出**——它把 CSS 字体族名 `system-ui` 带进 PPTX，目标机器无此字体，
   会被静默替换，版式走样。

**所以：吸收它的流程与交互，替换它的导出。** 本票正是为「替换后的导出该用哪个引擎」服务。

> 若所有者其实希望**连同导出路线一起照搬**，那不是本票能回答的问题——
> 那等于放弃 A 级语义与中文零溢出两项承诺，需先改 `## Destination`、
> VISION.md 与票 13 的质量属性，属于**重新画地图**，不是继续走这张票。

## Hard constraints

- 不得因为「Spike C1 已经证明 Open XML SDK 能过」就跳过 Apache POI 的同题实测——
  **一轮证据只能确定一件事**，POI 未测就是未测；
- 不得用「.NET/Java 生态更大」这类理由替代 PPTX 交付证据；
- 不得在未通过 P0 三项时给出选型结论；
- 不得把「官方文档声称支持」写成「本项目实测通过」。
