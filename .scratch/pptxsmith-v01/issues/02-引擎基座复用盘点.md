# 引擎基座复用盘点

Type: research
Status: resolved
Blocked by: 13
Claimed: 2026-09-26

## Answer

研究结论：**DocumentFormat.OpenXml / Open XML SDK 是保真优先的基础候选**。官方 README 明确提供 OPC/部件关系、强类型 API、LINQ-to-XML，并支持生成、修改、拆分/合并，以及图表缓存和嵌入工作簿更新。它的代价是低层、需要 OOXML 专业知识，且 .NET ZIP 包存在大文件内存风险；未知部件“可保留”需要用回归夹具验证，不能由文档直接推导为保证。

**ShapeCrawler 是优先评估的高层加速层**：官方 README 覆盖文本、图片、表格、线条和图表操作，基于 Open XML SDK、MIT、跨平台。但没有证据证明它对未知部件、关系和未触及 XML 有保留承诺；必须置于包级回归测试之后，保留 SDK 逃生通道。

**PptxGenJS 保留为新稿生成候选，不作为唯一文档引擎**：官方能力适合文本、表格、形状、图表和母版生成，但没有审查到读取既有 PPTX、对象级补丁或未知关系保留的第一类 API。

**OfficeCLI**：Apache-2.0、单二进制、DOM/原始 XML/校验/渲染等能力由 README 声称，但项目成熟度、未知部件保留、图表工作簿和关系保真均未独立验证；先作为可选 CLI 对照，不作为核心基础。

**GenOffice**：本轮没有拿到足够权威资料证明稳定的读/写/补丁、许可证和维护状态，只保留在候选清单，不作基础决策。

建议的复用原则：原始 OPC 包是事实源；只修改授权部件；已知对象用 SDK/ShapeCrawler；未知对象走原始 XML/ZIP 保留路径；新建与旧稿补丁分成两条能力轨。下一步由“终决文档引擎与总技术栈”票基于本研究和其余研究票做最终选择。

## Follow-up: 技术终决不可提前盖章

所有者强调技术选型是长期维护的核心决策，不能因为某条路线“看起来合理”就确认。候选比较必须围绕用户交付、PPTX 保真、中文质量、长期开源维护、Linux Docker、未来 Rust 客户端和产品体验六类目标，先通过证据门、语料门、交付门、维护门；Go/gopptx 的新候选已经证明原结论需要重新审查。
2026-09-24：补查发现 Apache-2.0 的 `djinn-soul/gopptx`（v0.2.0-alpha.5）可能比纯 Open XML SDK 包装层更接近项目目标：覆盖读写、图表嵌入工作簿、SmartArt、校验/修复、Go/Python/JSON bridge；Docker 中 `go test ./...` 在补齐字体后通过，自己的图表生成→更新回路通过。

但用同一份本项目 Spike A 的 PptxGenJS 产物做图表更新时失败，关系目标被解析为 `ppt/slides/ppt/charts/chart1.xml`，说明跨生成器兼容仍有真实问题；alpha、单一作者和未知部件保留也未证实。

本票需要补充 Go 候选比较：gopptx、puppt、UniOffice、相关 Rust/Go OOXML 项目，并把 Go 与 .NET/Open XML SDK 放入同一兼容性矩阵。当前不应关闭技术终决，也不应把 .NET 直接视为最终答案。

## Resolution (2026-09-26)：先过活跃度硬门，再谈能力

### 对本票此前结论的直接影响

1. **「ShapeCrawler 是优先评估的高层加速层」——撤回。**
   它因 G4（头号贡献者 88%）**未过入场门**。按票 13 规则，
   未过门者**不做能力评估**；可作隔离参考（读其实现思路），但不进主线依赖。
2. **「PptxGenJS 保留为新稿生成候选」——撤回。**
   它四项不达标（停更 15 个月、单人 94%）。Spike A/C 的实验价值不受影响
   （那验证的是产品承诺），但**它不再具备候选资格**。
3. **「本票需要补充 Go 候选比较」——已做，结论是淘汰。**
   `lixin9311/gopptx` 与 `evanwinterbourne/cjk-pptx-engine` **均返回 404，无法定位**；
   搜索命中的同名项目（1–3 star、无发版、单人）全部未过门。
   本票此前的 `djinn-soul/gopptx`（Apache-2.0、alpha）同样未过门。
   → **Go 侧无过门候选**，这条比较路径关闭，不必再花时间做能力验证。
4. **`OfficeCLI` / `GenOffice`：本票此前已标「未独立验证」。**
   本轮未纳入门槛筛选（未列入候选池），**保持未决**，不得据现有描述作出选型结论。
5. **Apache POI 是新增的过门候选。** 本票此前未列它。
   注：ADR-0003 曾否决「Java + Apache POI」，那是基于**能力边界**（对 PPTX 支持深度）
   的判定；本票只做**活跃度门槛**判定，**不推翻该否决**，两者性质不同。

### 本票结论（活跃度维度）

- **PPTX 读改生态本身很薄**：扩池搜了 55 个仓库，扩池后仍只有 2 个过门。
  大部分项目是「生成器」或单人项目。
- **过门候选**：`Open XML SDK`、`Apache POI`。
  它们只是**获得被比较的资格**，**不是最终答案**。
- **实现语言仍未被锁定**：两个过门候选分属 C# 与 Java，票 22 的「文档引擎与
  应用运行时解耦」合同正是为此存在。ADR-0003 仍 challenged，ADR-0009 仍 proposed。

### 遗留（转入能力对比票，不在本票解决）

门槛筛完，下一步才是本票原本关心的**能力**问题，且判据必须是产品承诺：
生成原生图表/表格、**读改既有包**、**未知部件保留**（本票已注明「需回归夹具验证，
不能由文档推导为保证」）、**嵌入工作簿同步**、OOXML 校验、中文排版、WPS 验收。

Spike C1 已实测 Open XML SDK 能做「受控补丁 + 同步嵌入工作簿」——这是**唯一
通过该科的**。Apache POI 需同题实测。**本票不承担该比较，转出。**

  未逐条抽样 issue 响应时间，进入能力对比前须补齐；
