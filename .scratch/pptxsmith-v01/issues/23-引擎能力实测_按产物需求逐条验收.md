# 引擎能力实测：按产物技术需求逐条验收（含商业 SDK 能力基线）

Type: research
Status: open
Blocked by: 02

## Question

**按 `docs/产物技术需求.md` 的判据，哪个技术能满足本项目的产物承诺？**

本票**不是**「Open XML SDK 还是 Apache POI」的二选一——
那个问法的前提（候选池已完整、能力验证已充分）都不成立。

### 重画理由（所有者 2026-09-26 指出方法错误）

此前的方法错误是**从候选出发**：哪个库活跃 → 哪个能过门 → 二选一。
正确顺序是**从产品出发**：要做成什么 → 需要什么能力 → 哪些技术能满足 → 谁最强。

具体缺口：

1. **主候选实测深度远远不够**：Open XML SDK 只有 Spike C 的 3 个任务，
   其中 C3 自己写道「从零建包没有现成的 hello world，需要自建脚手架」；
   **从未端到端造过一份完整稿**。
2. **被淘汰者未做能力实测**：活跃度只管入场资格，**不证明能力**。
   若某候选能力明显更强，正确做法是评估**二开/接管**可行性，而非简单淘汰。
3. **候选池可能不完整**：只搜了 GitHub 公开仓库；
   **商业 SDK（如 Aspose.Slides）从未真正评估**——
   许可证不合规，但**能力上限是判断「自研要做到什么程度」的参照**。
4. **夹具从未被使用**：含未知部件的 PPTX 早已生成，**没有任何候选引擎跑过**。

## 判据

**唯一判据是 `docs/产物技术需求.md`。** 逐条对编号验收：

- **A1–A9**（A 级原生语义）——硬否决项，尤其 **A9 零图片化**
- **B1–B5**（中文零溢出）
- **C1–C5**（事实保真与审计）
- **D1–D3**（未知部件保留，当前不作否决，但**必须实测记录**）
- **E1–E6**（工程与交付门槛）

优先级（冲突时）：**A 级语义与中文零溢出优先于一切工程便利**；
E 项是门槛不是评分；D 项不作否决但必须记录。

## 必须产出的参照物（不是验证片）

**造一份 10–20 页的中文商务汇报完整稿**，规格见需求文档第 1 节：
封面/目录/章节页/内容页/结束页、原生图表带嵌入工作簿、原生表格、
插图素材、备注页、主题母版版式、长段中文与中英混排。

**明确禁止**：3 页验证片。验证片掩盖真实问题——Spike E 用 python-pptx 做的
3 页稿通过了 17/17 探针，但那**不能证明候选引擎能造出 15 页可交付稿**。

## 参与实测的对象

| 对象 | 性质 | 说明 |
| --- | --- | --- |
| **Open XML SDK**（C#） | 过门候选 | 唯一有部分实测的；须补端到端 |
| **Apache POI**（Java） | 过门候选 | **零实测** |
| **商业 SDK（Aspose.Slides 类）** | **能力基线参照** | 吸收分类为**必须隔离**（商业许可，不得进 MIT 主线）， 但**必须先评估能力**——「必须隔离」不等于「不必评估」。它的能力上限告诉我们自研要做到什么程度 |
| 其它在本轮搜索中新发现的 | 待定 | 若能力证据指向更优，须按 G1–G5 补门槛判定 |

**特别要求**：不得因商业 SDK 许可证不合规就跳过能力评估。
它的**能力结论**是判据的一部分，只是**不能进依赖树**。

## 方法与纪律

- **同题**：复用 `research/experiments/spike-D-fixtures/`（字节可复现，三轮 hash 一致）
  与 `research/experiments/spike-E/` 的固定事实集；
- **同一目标软件**：WPS 11.8.2.8411，**32 位宿主探针**（见 `docs/目标软件验收矩阵.md` 2.1），
  脚本须显式断言宿主为 `wpp.exe`；
- **同一判据**：逐条对需求编号，不降门槛、不换题；
- **证据分级**：官方声称 / 第三方实测 / 本项目实测，逐条标注；
- **容器内运行**：按地图 Notes，.NET 与 Java 都在 Docker Desktop 内跑，
  不在 Windows 宿主机验证。

## 输出

1. **逐条能力矩阵**：对象 × 需求编号（A1–A9 / B1–B5 / C1–C5 / D1–D3 / E1–E6），
   每格填实测结果与证据级别；
2. **端到端实测记录**：输入 hash、引擎版本、命令、产物 hash、WPS 结果、失败对象清单；
3. **未知部件保留实测**（D2）：夹具的未知部件与未知关系是否原样保留——
   **这是从未跑过的一项**，且票 02 已注明不能由文档推导；
4. **吸收分类落位**（五分类，见地图 Notes 强制条款）：
   可直接复用 / 适合二开 / 仅可借鉴 / 必须隔离 / 应当淘汰，
   **逐对象分层判定**，不得只剩「胜负」二字；
5. **结论**：若出现「只有一项过 A9」，必须明说；
   若多者都能过，给出**非语言偏好**的取舍理由，或明确「不足以决定」；
6. **未决与下一步**：哪些项本票没能验、卡在哪。

## 边界声明

- 本票**不预判实现语言**：ADR-0003 仍 challenged，ADR-0009 仍 proposed。
  「引擎用哪个」与「控制面/worker 用什么写」是**两个决定**
  （票 22 的「文档引擎与应用运行时解耦」合同正是为此存在）；
- 本票**只围绕 PPTX**，任何与 PPTX 交付无关的比较项不进入；
- 只做**决策与最小验证**，不建生产脚手架；验证原型放 `research/experiments/`
  并标注「可丢弃」（地图 Notes 的研究实验物豁免）；
- 活跃度门槛**不在本票重开**（票 02 已关闭）；若引入新候选，按票 13 的 G1–G5 单独判定。

## Hard constraints

- **不得用 3 页验证片代替完整稿**——必须 10–20 页、含全部页面角色；
- 不得因为「Spike C1 已证明 Open XML SDK 能过受控补丁」就跳过其它项与其它候选；
  **一轮证据只能确定一件事**；
- **不得因许可证不合规跳过商业 SDK 的能力评估**——能力结论是判据，
  只有**依赖引入**被许可证排除；
- 不得把「官方文档声称支持」写成「本项目实测通过」；
- 不得在未逐条验收 A1–A9 时给出选型结论；
- 不得用「生态更大」「语言更熟」替代 PPTX 交付证据。
