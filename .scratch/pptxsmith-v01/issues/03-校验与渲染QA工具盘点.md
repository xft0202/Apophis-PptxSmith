# 校验与渲染 QA 工具盘点

Type: research
Status: resolved

## Answer

交付 QA 不应寻找一个“万能渲染器”，而应组合不同证据层：

1. **包与 Schema 层**：复用 `DocumentFormat.OpenXml.Validation.OpenXmlValidator`。Microsoft API 文档明确它可以对 `OpenXmlPackage`、`OpenXmlPart` 或元素执行验证，并按目标 FileFormatVersions 检查。它证明的是 OOXML 包/schema/元素合法性，不证明 PowerPoint/WPS 的视觉和交互等价。
2. **关系与部件层**：额外检查 `[Content_Types].xml`、`.rels`、slide/master/layout/chart/media/embedded workbook 的引用闭包、目标存在性、循环或悬空关系、宏/外链/嵌入对象策略。这部分应由 PptxSmith 的审计层补充，不能只依赖 schema validator。
3. **独立导入/转换层**：Linux 容器可复用 LibreOffice headless。官方 filter 文档明确支持 Impress 的 PPTX 输入/输出和 PDF 导出。它适合提供第二种导入/渲染信号、批量截图和转换失败检测，但不证明 Microsoft PowerPoint 等价；实验已证明字体和行高可能不同。
4. **ONLYOFFICE**：官方仓库声称支持 OOXML 演示文稿编辑和 Docker/自托管，但 Community Edition 是 AGPLv3，Enterprise/Developer 是专有许可。它可以作为外部兼容性对照或用户自行部署的可选集成，不应直接嵌入 MIT 核心，除非未来单独完成许可决策。
5. **目标软件层**：Microsoft PowerPoint Windows 与 WPS Windows 必须作为单独的人工/受控自动化验收目标。它们是最终用户看到和编辑的事实来源，不能由 LibreOffice/ONLYOFFICE 替代。

推荐的最小交付闸门组合：

- Open XML SDK validator：包/schema；
- 自研关系/部件闭包检查：关系、内容类型、嵌入工作簿、外链和宏策略；
- 语义检查：对象清单、A/B/C/D 等级、来源、数字零改写、图表/表格编辑探针；
- 字体/几何检查：统一 HarfBuzz-backed 量字、溢出、越界、重叠；
- LibreOffice headless：Linux 批量转换和独立渲染信号；
- Microsoft PowerPoint + WPS：目标版本抽检、重新打开、改图表/表格/段落并保存；
- 所有层输出审计报告，明确每层证明了什么、没证明什么。

核心结论：**校验器不是渲染器，渲染器不是 PowerPoint，PowerPoint/WPS 也不能替代语义校验**。交付门必须是证据组合，而不是单项 PASS。

来源：

- ONLYOFFICE DocumentServer README/license: https://github.com/ONLYOFFICE/DocumentServer
