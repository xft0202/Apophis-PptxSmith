# 跨项目长期架构全景与反锚定调查

Type: research
Status: claimed

## Scope narrowed twice (2026-09-25 第二次收窄，所有者明示)

**第一次收窄**：家族级形态已由 **[当前架构假设](22-当前架构假设_单机自托管与PPTX专用流水线.md)**（票 22）承接，
本票不再回答「该用哪种架构形态」。

**第二次收窄（本次，所有者纠正）**：本票此前的范围**过宽且方向偏移**——它把大量
「平台工程」组件拉进了首期调查（事件总线、K8s/Argo、Cept/OpenSearch、企业 IdP、
provider gateway 矩阵、durable runtime 横评），这些都不是「把 PPTX 做好」的组成部分，
属于**面子工程与过度工程**。现按两条所有者明示的硬前提重写范围：

1. **单机部署是唯一形态，与人数无关。** 一人自用或多人共用，**都是单机 Docker Compose**。
   「多人使用」不构成上集群、上分布式存储、上消息总线的理由。
2. **专一目标**：只把 PPTX 这件事做到彻底。任何不能回答「它让 PPTX 做得更彻底吗」
   的组件，不进首期调查。

### 本票保留的范围（全部围绕 PPTX 核心链路）

| 类别 | 要回答的问题 | 候选方向 |
| --- | --- | --- |
| **PPTX 生成与读改引擎** | 哪个引擎能同时做到：生成原生图表/表格、读改既有包、保留未知部件、校验 OOXML | Open XML SDK 系 / PptxGenJS / gopptx / python-pptx / ShapeCrawler 等，须过 G1–G5 门槛 |
| **中文量字与折行** | 哪个 shaping + 度量路线在两目标软件下最准、可审计、可校准 | HarfBuzz-backed 方案，按字体×目标软件校准 |
| **材料解析与取数保真** | 哪个 parser 中文/表格/来源定位最好，且能追溯 locator | Docling / MinerU / Unstructured / Tika，须过 G1–G5 |
| **图表与嵌入工作簿同步** | 改图表数据时如何同步缓存与 xlsx 部件且不破坏其他部件 | 由引擎能力决定 |
| **轻量数据与任务基础** | 单机够用的最小持久化与任务恢复：**PostgreSQL + S3-compatible**（具体实现过 G1–G5） | 不为将来「可能的规模」提前上分布式 |
| **实现语言/运行时** | 控制面与 worker 用什么写（语言本身不预判） | ADR-0003 仍 challenged，ADR-0009 仍 proposed |

### 本票**移出范围**（不进首期调查；理由：与单机 + 专一 PPTX 无关）

- **durable workflow runtime 横评**（Temporal / Restate / Hatchet / Camunda / DBOS / Inngest）：
  单机场景下先证明 PPTX 链路真的需要它；先用最少的机制表达阶段门与恢复，
  证据不成立就不引入。**取消原「必须横评」的要求**。
- **事件总线 / 消息中间件**（Kafka / NATS JetStream / RabbitMQ）：超单机规模，出局。
- **Kubernetes / Argo / Helm / GitOps / Camunda 企业流程平台**：出局（见票 22 第 1.1 节）。
- **分布式存储与搜索**（Ceph / CockroachDB / OpenSearch）：出局。
- **企业 IdP 全家桶**（Keycloak 集群 / SCIM / LDAP 联邦 / 多租户运营）：出局；
  首期只需应用内账号 + OIDC 接入边界。
- **provider gateway 产品矩阵**（LiteLLM / Bifrost / Kong / Higress / Envoy / Portkey）：
  降级为「直接 adapter + capability registry」这一条路线先做，产品级网关**不进首期**。
- **前端框架横评**：降为次要（用户任务优先，框架不定义产品），不作为阻塞项。

### 本票**不再重新回答**的（已由票 22 与 ADR-0006/0007/0013 承接）

单机部署形态、耐久语义必须存在、事实源分层、引擎与运行时解耦、provider 与业务解耦、
预览不是交付真相、身份与隔离第一天到位、观测与供应链、SQLite/本地生产文件硬淘汰。
若证据指向这些需要改变，**必须回票 22 重新评审，不得在本票内静默改合同**。

### 关闭条件

本票范围内每个类别**各有证据与淘汰理由**即可关闭；不再要求「四套架构全部跑通」。
证据可以是：官方文档 + 源码 + 许可证 + 本项目最小实测 + G1–G5 活跃度判定。

## Question

在重新评估前端、后端、任务编排、数据文件、解析渲染、安全和发布体系前，建立一份不受既有 React/.NET/Temporal、TypeScript/Go/Rust 等路线锚定的长期架构全景调查。

本票不是继续给已有候选打分，而是先回答：什么样的架构组合能够在五年以上维护周期内，同时满足中文商务 PPTX 的原生语义交付、PowerPoint/WPS 验收、多人自托管、BYOK、数据隔离、审计、回滚和社区贡献？

必须覆盖并横向比较至少以下架构家族：

- 模块化单体 + 专用执行 worker；
- 控制面/数据面分离 + durable workflow；
- 事件驱动/消息总线 + 可重放事件；
- 文档编译流水线 + 解析/渲染/编译适配器；
- 插件/provider 平台 + 外部模型网关；
- local-first/桌面壳 + 自托管服务；
- 企业平台型方案（身份、对象存储、观测、升级完整）与轻量自托管方案的长期差异。

候选搜索不得只围绕已知项目。至少扩展调查：

- 工作流/耐久执行：Temporal、Camunda/Zeebe、Netflix Conductor、Restate、DBOS、Hatchet、Inngest、Prefect、Dagster、Argo Workflows、NATS JetStream、RabbitMQ、Kafka；
- 数据/对象/检索：PostgreSQL、CockroachDB、SQLite（只作为被淘汰对照，不得作为支持方案）、S3-compatible、SeaweedFS、Garage、Ceph、OpenDAL、pgvector、Qdrant、OpenSearch、Meilisearch、Tantivy；
- 身份/权限：应用内 Identity、Keycloak、Ory、ZITADEL、Authentik、企业 OIDC/LDAP/SAML/SCIM；
- 模型接入：直接 provider adapters、LiteLLM、Bifrost、Kong AI Gateway、Envoy AI Gateway、Higress、Portkey 等；
- 材料/办公：Open XML SDK、ShapeCrawler、PptxGenJS、gopptx、Docling、MinerU、Unstructured、Tika、LibreOffice、ONLYOFFICE、PDFium/Skia/HarfBuzz；
- 前端/工作台：React/Vite、Next.js、Vue/Nuxt、SvelteKit，以及 LibreChat、Open WebUI、PPTist、Presenton、PPT Master、Dify、Flowise 等真实产品的架构经验。

每个候选必须记录：官方文档/源码证据、许可证与例外、维护活跃度、贡献者/单点风险、部署拓扑、数据一致性、故障恢复、升级/迁移、可观测性、中文/PPTX 适配价值、供应链风险、可直接复用/二开/借鉴/隔离/淘汰分类。

## Answer

### 1. “长解、无忧解”的判定标准

本项目的长期解不是组件最少，而是 **生产地基一次到位、用户体验持续可用、局部替换不触发数据和交付返工**。因此必须满足：

- 生产关系库、对象存储、备份恢复、权限、任务状态、审计和供应链从第一天进入受支持路径；
- 单节点 Docker 只是第一种部署拓扑，不能使用临时数据库、临时文件目录、进程内后台任务或未经验证的 provider 伪装简单；
- “部署简单”由同一生产组件的 Compose/profile/安装向导/健康检查/备份脚本实现；扩容是增加副本或外部服务，不是替换数据模型；
- 原始材料、PPTX OPC 包、版本、来源、审计和工作流历史都有明确事实源；缓存、向量库、预览器、Agent 图和模型网关都只能是可重建投影或适配层；
- 任何组件进入主线前都要有五年维护、许可证、升级、恢复、替换和贡献者接手路径；
- 用户体验必须达到 SANDUN 的透明流水线和阶段产物标准，同时补上 A 级语义、中文质量、事实证据、回滚和自托管。

### 2. 架构家族比较

| 架构家族 | 能解决的真实问题 | 长期优点 | 长期风险 | 当前判断 |
| --- | --- | --- | --- | --- |
| 模块化单体 + 专用 worker | 一人部署、多用户控制面、PPTX/解析隔离 | 领域边界清楚，单节点易运行，贡献者容易进入 | 若没有 durable workflow，长任务/人工门会逐渐变成隐式状态机 | 可作为应用形态，但不能偷掉耐久执行层 |
| 控制面/数据面 + durable workflow | 四道门、暂停确认、恢复、回滚、长任务和 worker 崩溃 | 最符合“可控、可审计、可恢复” | 服务、事件历史、升级和运维复杂度更高 | **首要架构形态候选** |
| 事件驱动 + 可重放事件 | 多 worker、集成、事件审计、异步扩展 | 解耦和观测能力强，NATS/Kafka/JetStream 生态成熟 | 最终一致性、重复消费、事件 schema 演进和排障成本高 | 作为工作流/审计的内部机制候选，不自动全系统事件化 |
| BPMN/企业流程引擎 | 人工任务、审批、可视化流程和合规审计 | Camunda 等对流程治理、人工任务和运营界面成熟 | BPMN/Java/引擎部署模型重，和页面编译领域不完全匹配 | 企业部署候选，不能因“有审批”直接选入 v0.1 |
| Durable service runtime | Restate/Hatchet/Inngest 一类把重试、状态、定时下沉 | 开发者体验好，虚拟对象/持久 promise 很适合阶段等待 | 服务端许可/成熟度/生态/运维边界差异大，需要真实恢复演练 | **必须纳入全景评估，不再只看 Temporal** |
| Kubernetes 工作流 | Argo 这类容器级并行、artifact、暂停和重试 | 适合大规模计算、GPU、平台团队 | 与当前 Linux Docker 单机支持范围冲突，运维地基过重 | 不作为 v0.1 默认；企业平台可选隔离 |
| 数据资产/ETL 编排 | Prefect/Dagster 这类解析、索引、批处理和 lineage | 对材料批处理、索引、观察和数据版本有优势 | 不是面向用户四道门的交互工作流 | 用于解析/索引类 worker 候选，不拥有产品任务事实 |
| 事件总线/消息中间件 | NATS JetStream、RabbitMQ、Kafka | 可靠投递、重放、跨服务和扩展能力 | 不是 workflow；需要幂等、顺序、schema 和观测治理 | 按需引入，不能以“有消息总线”代替领域状态 |
| Local-first/桌面壳 | 未来 Windows/macOS Rust 客户端、离线和本地敏感材料 | 用户信任和本地体验强，服务端故障影响小 | 同步、冲突、字体/渲染、离线模型和跨端版本复杂 | 作为未来约束；v0.1 先冻结 API/事件/文件协议，不提前做客户端 |

### 3. 跨项目候选地图

#### 3.1 工作流与耐久执行

- **Temporal**：MIT 服务与多语言 SDK 生态，官方能力覆盖 deterministic replay、Activity、Signal/Query、人工等待、重试、worker versioning；运维组件和 event history 学习成本高。分类：**强候选，必须与 Restate/Hatchet/Camunda 对照 Spike**。
- **Restate**：Rust runtime，SDK/文档展示 durable promises、virtual objects、stateful handlers、idempotency 和跨失败恢复；GitHub 主仓库 license metadata 需锁版本核验。分类：**长期架构候选，不得因 Rust 预期直接淘汰**。
- **Hatchet**：Go、MIT、durable task queue/workflow，官方资料覆盖 DAG、重试、并发、取消、版本和“approval/agent loop 更适合 durable tasks 而非静态 DAG”。分类：**强候选**。
- **Camunda 8**：BPMN/DMN/流程运营能力强，有 Java/Zeebe/Tasklist/Operate 生态；许可证、self-managed 版本边界和单节点成本必须核验。分类：**企业流程候选/隔离验证**。
- **Netflix Conductor**：Netflix 开源的 JSON/DAG workflow 传统路线，适合任务编排、异步依赖和 worker；其开源项目与 Orkes 商业生态、版本/社区边界必须分开核验。分类：**架构对照/隔离验证**。
- **DBOS**：以 PostgreSQL/SQL 作为 durable execution 基础的架构方向；官方资料和 `dbos-inc/dbos-transact-py/ts` 仓库展示 workflow/step、队列和恢复，GitHub API 快照的 Python/TypeScript Transact 仓库为 MIT 且未归档。仍需验证长流程人工等待、事件历史、版本升级、备份恢复和多语言边界。分类：**强研究候选，不提前进入基线**。
- **Inngest**：事件驱动 durable functions，开发体验和多语言 SDK 值得研究，但自托管、许可证和产品控制边界需锁定。分类：**候选**。
- **Prefect/Dagster**：Apache-2.0、Python 数据编排/资产 lineage/重试/观察成熟。分类：**材料解析、索引、批处理候选，不是用户门控事实源**。
- **Argo Workflows**：Apache-2.0、Kubernetes CRD、DAG、artifact、suspend、retry 强；但 K8s 是硬前提。分类：**企业计算平台隔离候选**。
- **NATS JetStream/RabbitMQ/Kafka**：是消息/事件基础设施，不是领域 workflow；NATS JetStream 支持持久化、ack、重投和 exactly-once 组合，Kafka 适合事件流，RabbitMQ 适合队列/路由。分类：**按需要复用，不能直接充当业务状态机**。

#### 3.2 数据、对象和检索

- **PostgreSQL**：仍是关系事实库强候选，适合成员/项目/版本/审计/来源/任务事务；不是因为“简单”而选，而是因为长期 SQL、事务、备份、权限和生态最稳定。
- **CockroachDB**：分布式 SQL、serializable、跨地域和灾难恢复能力强，但 license metadata/运营成本/兼容边界和单节点部署复杂度需要独立评审；不能为了未来规模提前引入。
- **Garage**：S3-compatible 分布式对象存储方向；官方仓库 GitHub API 快照为 AGPL-3.0，适合研究小规模自托管和多节点对象复制，但不能进入 MIT 默认核心；恢复、升级和 S3 语义仍需验证。分类：**隔离验证**。
- **pgvector/Qdrant/OpenSearch/Meilisearch/Tantivy**：都只能是可重建投影；pgvector 适合同库 metadata filter，Qdrant 适合规模化向量，OpenSearch 适合企业已有搜索平台，Meilisearch/Tantivy 的搜索体验或嵌入式能力值得借鉴。没有任何一个可以替代 `source_fact + source_locator`。
- **SQLite**：从所有受支持部署和迁移路径中淘汰。它可作为外部项目对照，但不作为本项目产品 profile、生产数据库或“先做以后换”的演练方案。

#### 3.3 身份与权限

- **应用内本地账号 + OIDC-ready 契约**：可满足一人部署和基础多成员，但必须把身份、session、密码、MFA、恢复和审计写成长期安全边界，不能只做临时 cookie。
- **Keycloak**：Apache-2.0、成熟 OIDC/SAML/LDAP/用户联邦/RBAC，但 Java 和运维较重；适合企业部署 profile，不一定作为默认内置服务。
- **Ory Kratos/Hydra**：Apache-2.0、headless、Go、OIDC/OAuth/身份流程分离，适合 API-first；需要评估组件数量和用户体验实现成本。
- **ZITADEL**：能力强但 AGPL-3.0，不能直接进入 MIT 核心默认；可作为外部企业 IdP。
- **Authentik**：产品体验和协议支持值得研究，但 license metadata/部署升级边界必须锁定版本。分类：**外部身份候选/许可证审查**。

#### 3.4 模型网关与 provider

- **直接 adapters**：控制力和数据路由最好，但要承担 provider 协议变化；必须由内部 capability registry 保护。
- **LiteLLM**：Python、多 provider、routing/fallback/budget/virtual key/observability 经验丰富；enterprise 目录和版本许可证边界要审查，结构化输出兼容性不能假设。
- **Bifrost**：Go、Apache-2.0、路由/治理/virtual key/模型目录方向有价值；性能声明需实测，不能取代语义兼容测试。
- **Kong/Higress/Envoy AI Gateway**：更接近企业 API gateway/控制面，适合已有 Kubernetes/网关平台；Higress 官方资料显示 Wasm plugin、AI proxy、token rate limit、observability 等能力，Envoy 方向还需区分官方 AI Gateway 站点与 Kubernetes Gateway API Inference Extension。当前 GitHub API 对 `envoyproxy/ai-gateway` 出现非预期重定向，不能据此确认仓库许可证或维护状态；这些能力不适合无条件下沉到单节点产品。
- **Portkey Gateway**：MIT metadata、AI gateway/guardrail/多 provider 经验值得对照，具体企业功能和 self-host/许可证边界仍需锁版本。

#### 3.5 文档与体验产品

- **文档/解析候选**：Docling、MinerU、Unstructured、Tika 必须比较中文、来源定位、许可证、模型/外部依赖和崩溃恢复；ONLYOFFICE 可作为私有化 Office 平台参考，但社区许可证、商业版边界和目标软件等价性必须独立审查；PDFium、Skia、HarfBuzz 是渲染/几何/shaping 工具，许可证和沙箱边界需按组件锁定，不能被当作完整 Office 语义引擎。
- SANDUN：当前 UX 北极星，吸收透明阶段和用户控制；不复制 SVG/B 级编辑、画布负担、黑盒置信度和积分墙。
- Presenton：自托管/BYOK/provider registry/模板输入有价值；PPTX 可编辑声明必须独立实测。
- PPT Master：原生 PPTX 深度、确定性转换、postflight 质量报告有价值；Agent-host 绑定和项目专用中间语言不能直接当服务端架构。
- PPTist：结构化编辑器、schema、撤销/重做、中文资源有价值；AGPL 和自身保真边界决定只借鉴。
- Dify/LibreChat/Open WebUI：模型/provider、文件、流式事件、权限/群组和工作台经验有价值；不能整体复制其许可证、服务规模或产品定位。
- Flowise：工作流 UI 值得作为历史经验，但 README 已标注归档，不能作为长期基础。

### 4. 三套端到端长期架构方案

#### 方案 A：产品控制面 + durable workflow + 专用文档编译流水线

```text
React/Vue/Svelte Web Workbench
        │ typed REST + resumable event stream
Product Control Plane
        │ workflow protocol / audit / authorization
Durable Workflow Runtime
        ├── Parse/Extract Worker
        ├── Content/Provider Worker
        ├── PPTX Compiler Worker
        ├── Preview/QA Worker
        └── PowerPoint/WPS Gate Runner
PostgreSQL facts + S3-compatible immutable object storage
OIDC/local identity boundary + OpenTelemetry/SBOM/signing
```

优点：最贴合四道门、审计和 PPTX 专用质量；前端/控制面/worker 可独立演进；单节点可以运行同一生产组件，未来按 worker/对象存储/身份扩展。风险：需要选择并验证 durable runtime、对象存储默认实现和多语言协议。当前这是 **形态首选**，不是已经决定 Temporal/.NET/React。

#### 方案 B：事件原生平台 + Durable Services

```text
Web Workbench
  -> API/Command service
  -> NATS JetStream or Kafka event backbone
  -> Restate/Hatchet durable services and stateful workflow objects
  -> parser/compiler/provider services
PostgreSQL projections + S3-compatible object store
Enterprise OIDC + OpenTelemetry + event replay tooling
```

优点：事件可重放、跨服务边界清晰、失败恢复和集成能力强；Restate/Hatchet/NATS 可以形成高韧性运行时。风险：事件 schema、重复投递、投影一致性和运维复杂；若把所有事实复制到事件/投影，审计和调试反而更难。适合长期平台化，但必须证明单节点安装、备份和贡献者可理解。

#### 方案 C：企业流程/容器平台

```text
Web Workbench
  -> API gateway / Keycloak or enterprise IdP
  -> Camunda 8 or Argo Workflows on Kubernetes
  -> task workers / parser / compiler / QA pods
PostgreSQL or CockroachDB + Ceph/S3 + OpenSearch
OTel + SBOM/signing + GitOps/Helm release
```

优点：人工任务、流程运营、artifact、审计、扩容和企业运维能力最强。风险：Kubernetes/Ceph/OpenSearch/流程引擎带来的平台门槛很高，许可证和升级面广，与当前 Linux Docker 单节点支持范围不对齐。应作为企业部署参考，不作为默认产品形态。

#### 方案 D：数据编排优先

```text
Web API
  -> Prefect/Dagster data flows
  -> Docling/MinerU/Unstructured parser tasks
  -> Postgres/S3/search projections
  -> separate PPTX compiler service
```

优点：解析、索引、数据 lineage、重跑和观察成熟。缺点：对用户确认、阶段门、局部回滚、实时反馈和交付审计不是第一公民。适合材料 ingestion/indexing 子系统，不适合作为完整产品控制面。

### 5. 无返工评审结果

| 方案 | 用户阶段门 | PPTX/数据事实保护 | 五年维护 | 单节点长期基线 | 企业扩展 | 总体判断 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| A 产品控制面 + durable workflow + 专用流水线 | 4.8 | 4.9 | 4.4 | 4.5 | 4.6 | **首选形态** |
| B 事件原生 + durable services | 4.6 | 4.5 | 4.0 | 3.6 | 4.9 | 强候选，需恢复/运维 Spike |
| C BPM/容器企业平台 | 4.8 | 4.6 | 4.2 | 2.3 | 5.0 | 企业 profile，不是默认 |
| D 数据编排优先 | 3.0 | 4.3 | 4.1 | 3.8 | 4.2 | 解析/索引子系统 |

这些是架构家族的预评分，不是具体 vendor 的最终评分。A 的“首选”只表示产品形态最匹配，不能被翻译成 React + .NET + Temporal 已经拍板。

### 6. 旧判断的撤回与保留

**撤回**：

- React + Vite 是默认前端；它只能作为候选，必须在 SANDUN 体验基准、中文输入、阶段流、桌面复用和长期生态矩阵中重新比较；
- ASP.NET Core + .NET/Open XML worker 是强基线；它仍有 Spike C 证据，但不能代表控制面、编译器、worker、身份和数据的总答案；
- Temporal 是首要 workflow；Restate、Hatchet、Camunda、Inngest、NATS/JetStream 组合和事件原生方案必须进入同题恢复/升级比较；
- PostgreSQL + 本地 BlobStore 是长期部署；PostgreSQL仍是候选，但生产对象存储必须从第一天遵守 S3-compatible 长期合同，本地目录仅测试 scratch；
- Docling 是强解析候选；它必须和其他 parser 在中文同题集、来源 locator、许可证/模型和崩溃恢复上比较；
- “组件少的最小方案”更可靠；已证明这是错误的评价函数。应比较五年总返工、数据恢复、升级和用户体验风险。

**保留**：

- 原始 OPC 包是 PPTX 事实源；
- A/B/C/D 可编辑性、中文量字、PowerPoint/WPS 双目标、审计报告和铁三角质量门；
- 解析/编译/预览/目标软件四层职责分离；
- provider、搜索、缓存、Agent 图不是事实源；
- 证据分级、许可证、同题 fixture 和可替换适配边界。

## Experience Benchmark: SANDUN as UX North Star

现有研究回放和横切结论表明，SANDUN 是当前最值得作为交互基准的样本。这里的“基准”只指用户体验结构，不代表接受它的 PPTX 技术路线、商业模式或画布编辑器。

### SANDUN 已验证值得保留的体验

- **项目连续性**：用户进入的是一个持续积累的项目，而不是一次性 prompt；材料、风格、历史和任务上下文有归属。
- **透明流水线**：用户能看到调研、策划、大纲、初稿、设计稿和成品的阶段变化，等待有对象，过程不是黑盒 spinner。
- **阶段产物分离**：先看结构，再看页面，再看设计，返工发生在便宜的阶段；用户能在方向错误时早停。
- **便利贴式大纲**：页面角色/结论可增删、拖拽、调序、确认，用户能理解“这份稿子要讲什么”。
- **逐页上下文**：页面与检索词、参考材料、来源数量或相关信息相邻呈现，用户不必猜模型从哪里得到结论。
- **风格连续性**：项目级风格库、模板或参考稿会影响后续输出，减少每次重新解释审美方向。
- **模型档位/成本意识**：不同模型质量和消耗有可理解的差异，用户能在质量、速度、成本间选择。

### SANDUN 的已知边界，不能照搬

- SVG/形状级“可编辑”不等于图表数据、表格结构和嵌入工作簿的 A 级语义编辑；
- 置信度数字如果没有原文片段、来源定位、冲突和验证状态，只是黑盒安慰；
- 自由画布提高表达上限，但增加学习成本、状态复杂度和编辑一致性风险；
- 视觉输出可能出现题材同质化，流程透明不等于内容、中文排版和事实质量真实可靠；
- 托管、积分和模型锁定不符合本项目开源、自托管、BYOK 和数据主权目标；
- 公开工作流不能替代 PowerPoint/WPS 重开、保存、编辑和直接汇报验收；
- 上传旧稿/美化路径会把受控补丁、未知部件保留和授权范围问题提前带入，不能因为体验顺滑就跳过安全边界。

### PptxSmith 的综合体验基线

| 借鉴来源 | 吸收 | 明确补强或拒绝 |
| --- | --- | --- |

### 首次使用十分钟的体验要求

后续票 07/14 必须用 SANDUN 作为基准样本，且达到以下更高标准：

1. 进入后先看到项目目标、材料入口、模型/数据策略和预计成本，不先看到技术配置表；
2. 上传后显示材料解析进度、发现的页/表/图表/风险、来源覆盖和需要用户确认的问题；
3. 澄清门只问影响结构的问题，并允许默认假设；
4. 大纲门使用结构化卡片/便利贴式排序，支持增删、调序、锁定和回到材料证据；
5. 代表页门给出 2–3 个不同页面角色，显示预计成本/时间和已知风险，用户可确认、修改或跳过；
6. 全量生成期间能看到当前阶段、已完成/待处理页、模型调用摘要、成本、可取消状态和失败恢复入口；
7. 交付门显示对象可编辑等级、中文排版检查、来源核验、目标软件验证范围和未覆盖项，不用一个“完成”标签掩盖风险；
8. 每次修改都生成可命名版本，允许回滚、比较和局部重做；不要求用户进入自由画布修补系统错误。

### 体验质量指标

SANDUN 的“过程顺滑”必须转化为可测指标，而不是审美印象：

- 首次上传到第一个有意义的结构反馈时间；
- 首次进入大纲门的用户完成率和大纲确认耗时；
- 代表页确认后的全量交付成功率；
- 从失败/阻塞状态恢复成功率；
- 用户从生成到上会的总耗时与返工分钟数；
- 每个阶段的取消、回滚、重试和放弃率；
- 用户看到的来源/风险/成本与最终审计记录的一致率；
- 目标软件抽检后发现的阻断问题，而不是只看界面完成率。

这条基准会进入全景架构的用户任务评分，也会在前端、首次使用、同题测试集和交付闸门中重复出现。技术架构必须服务于这些体验承诺，不能反过来让用户适应内部组件。

### 外部产品补充证据

- **Gamma 官方帮助中心**：支持 Generate/Paste/Import 三种入口，生成后可对单页或整稿进行 AI 修改，并允许用户在应用变更后继续手工调整和撤销。吸收点是低摩擦预览、局部修改和回滚；必须补上本项目的版本命名、来源、审计和 PPTX 语义验收。
- **Plus AI 官方指南**：先展示 outline，再生成；在 PowerPoint/Google Slides 内提供 Rewrite、Remix、增页、重排和手工编辑。吸收点是“先确认结构”和把修改动作拆成清晰命令；必须隔离其宿主插件依赖，不能把商业插件当自托管基础。
- **Gemini in Google Slides 官方帮助**：通过追问澄清目标，生成包含 overview、sources、steps 的计划，用户修改并批准后才生成；生成结果可逐页预览、插入/替换并继续手工编辑，也能匹配参考稿风格。吸收点是来源/计划/批准/预览链路；必须补上 PowerPoint/WPS 双目标、中文量字和本地部署。
- **SANDUN 本项目实测回放**：在项目连续性、透明流水线、策划/设计分阶段、便利贴大纲和逐页上下文上作为当前最佳体验基准；其 SVG 级编辑、黑盒置信度、画布负担和积分墙不进入本项目。

外部资料证明的是交互模式存在且可用，不证明其 PPTX 目标软件、中文排版、事实保真或长期自托管符合本项目质量门。所有吸收项仍须落入同题体验夹具和交付闸门。

## Hard constraints

- 不得以“先最小实现、以后替换”作为长期架构理由；
- 不得因为一个语言生态熟悉或 stars 高就把它当系统答案（但活跃度是**入场门槛**，见票 13 G1–G5：生态冷门者直接淘汰，不得评估）；
- **单机部署是硬前提**，与使用者人数无关；不得以「多人共用」「将来可能扩展」为由引入集群级组件；
- **任何候选必须能回答「它让 PPTX 这件事做得更彻底吗」**；不能回答者不进首期调查；
- 不得把部署组件数量少等同于维护成本低；要计算迁移、数据丢失、升级和目标软件返工成本；
- 不得让任何向量库、缓存、预览器、模型网关或 Agent 框架成为事实源；
- 生产数据库、对象存储、备份恢复、权限和审计必须从第一天满足长期合同；
- 研究阶段不得创建生产脚手架，只能形成决策与最小验证规格；
  在 `research/experiments/` 下的可丢弃验证原型属已授权的例外（见地图 Notes 的研究实验物豁免）。
