# 评估任务编排与模型接入体系

Type: research
Status: open
Blocked by: 21

## Question

为澄清门、大纲门、代表页门、全量生成和交付门选择长期可维护的任务编排、模型路由和 provider 接入方案。

必须调查：

- LLM、检索、生图模型的可替换接口与用户自配；
- 流式事件、长任务、重试、取消、幂等、人工确认和版本恢复；
- BullMQ、Temporal、Hangfire、Dapr、内置队列或其他方案的适用边界；
- LiteLLM、Bifrost、OpenAI-compatible gateway 等模型网关的许可证、部署和观测；
- 成本记录、速率限制、模型降级、数据路由和敏感材料策略；
- 是否需要 MCP、Agent SDK 或图式编排框架，及其长期锁定风险。

结论必须围绕“可控、可审计、可回滚”，不以 agent 概念数量为质量指标。

### 1. 结论

任务编排与模型接入必须分成三个层次：

1. **领域工作流**：澄清门、大纲门、代表页门、全量生成、交付门，以及用户确认、版本恢复和审计状态；
2. **durable execution/队列**：负责持久化运行状态、重试、取消、定时、worker 恢复和事件历史；
3. **provider gateway/adapter**：负责 LLM、embedding、检索、生图和 reranker 的能力声明、路由、限流、成本和错误归一化。

这三层不能互相替代。队列有重试不等于能恢复人工确认；OpenAI-compatible 不等于结构化输出语义兼容；Agent 图能暂停不等于它拥有 PPTX 版本和审计事实。

**主要候选结论**：

- Temporal 是完整 durable workflow 的首要 Spike 候选，尤其适合四道门的 Signal/Query/Activity、人工等待、恢复、重试和工作流版本演进；但它需要独立服务、持久存储和新的运维知识，Spike 通过前不得写入最终总架构 ADR。
- BullMQ、Hangfire、Celery 是有价值的执行队列：BullMQ 适合 Node/Redis 任务，Hangfire 适合 .NET 持久后台作业，Celery 适合 Python 解析 worker；它们不能单独承担跨版本、人工确认和长期工作流语义。
- LangGraph 只作为材料策划/局部 Agent Activity 的候选，不能成为项目任务、PPTX 版本、权限或审计的事实源。
- LiteLLM 和 Bifrost 都应作为可选外部 gateway 候选；PptxSmith 内部必须保留 provider registry 和能力探测，不能把网关的模型列表或 OpenAI 兼容声明当作产品事实。
- MCP 只允许作为显式、可审计、可授权的工具扩展；不进入首期核心生成路径，也不能让模型直接获得宿主文件系统或任意网络权限。

### 2. 编排候选矩阵

评分为研究期预评分，满分 5 分；先过票 13 的硬门，再比较。权重：人工确认/恢复 25%，失败/重试/取消 20%，版本演进与审计 20%，自托管和运维 15%，生态/语言适配 10%，复杂度 10%。

| 候选 | 人工确认/恢复 | 失败/取消 | 版本/审计 | 自托管运维 | 生态适配 | 复杂度 | 预评分 | 分类 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| Temporal + SDK | 4.9 | 4.9 | 4.9 | 3.3 | 4.3 | 3.2 | **4.3** | 首要 Spike |
| BullMQ + Redis | 3.0 | 4.1 | 2.8 | 4.0 | 4.6 | 4.4 | 3.6 | 队列候选 |
| Hangfire + SQL/Redis | 3.1 | 4.0 | 2.9 | 4.2 | 4.3 | 4.3 | 3.6 | 队列候选/许可审查 |
| Celery + broker/backend | 3.2 | 4.0 | 3.0 | 3.7 | 4.7 | 3.8 | 3.7 | Python worker |
| LangGraph checkpoint | 4.2 | 3.8 | 3.6 | 3.7 | 4.7 | 3.5 | 3.9 | 局部 Agent |
| Dapr Workflow | 4.1 | 4.0 | 3.8 | 2.6 | 3.8 | 2.6 | 3.5 | 暂不采用 |
| 自研 DB 状态机 + worker | 3.5 | 2.8 | 4.0 | 4.4 | 4.0 | 2.2 | 3.4 | 仅最小 fallback |

“自研 DB 状态机”不能因为初期组件少就获得高分：它会把事件历史、重试、定时器、worker lease、恢复、版本迁移和 replay 责任全部转移给本项目，只有在 Temporal Spike 明显超出单节点部署预算时才保留为受限替代。

### 3. Durable workflow 与四道门模型

领域工作流不直接暴露 provider 细节，而是编排稳定的 Activity 合同：

```text
CREATED
  -> CLARIFICATION_PENDING -> CLARIFICATION_CONFIRMED
  -> OUTLINE_GENERATING -> OUTLINE_PENDING_USER -> OUTLINE_LOCKED
  -> REPRESENTATIVE_GENERATING -> REPRESENTATIVE_PENDING_USER
  -> FULL_GENERATING -> DELIVERY_QA
  -> DELIVERED

任何可恢复阶段 -> FAILED_RETRYABLE / FAILED_REVIEW / CANCELLED
FAILED_REVIEW -> USER_CORRECTION_PENDING -> RESUMED
```

- `CLARIFICATION_PENDING`、`OUTLINE_PENDING_USER`、`REPRESENTATIVE_PENDING_USER` 和 `FAILED_REVIEW` 是持久化的人机确认点，不是前端 spinner；用户操作以 Signal/命令写入工作流历史。
- 每个阶段绑定 `project_id`、`input_version`、`style_pack_version`、`workflow_definition_version` 和 `provider_policy_version`，恢复时不能偷偷使用另一版本的输入或风格包。
- Activity 只做有边界的外部副作用：解析材料、调用模型、生成图片、编译 PPTX、渲染预览、运行审计。Activity 输入/输出使用版本化 schema，不能把未验证的模型自由文本直接当下一个阶段的领域对象。
- 用户回滚不是删除历史；它创建一个新的派生输入版本并重新启动受控分支，原稿、旧任务、旧审计和旧产物只读保留。
- 每个长任务有可查询状态、事件序列和成本摘要；SSE/WebSocket 只是投影，断线后从持久事件补偿。

Temporal 官方资料明确要求 Workflow 逻辑可 deterministic replay，外部 API、LLM 调用、数据库查询和文件副作用放入 Activities；其 Signals/Queries/Conditions 能表达取消、状态查询和人工等待，Workflow versioning/pinning 可处理长流程升级。这些能力正好对应四道门，但也引入 event history、replay、worker versioning 和 Temporal Server 运维成本。

### 4. 队列候选的正确边界

#### 4.1 BullMQ

BullMQ 是 MIT、Redis-backed 的 Node 队列，官方文档和源码覆盖 attempts/backoff、并发、全局限流、父子依赖和 worker 处理。它适合作为简单执行队列或 Node 控制面 worker：

- 可复用：任务入队、优先级、并发、延迟、重试、进度和 rate limit；
- 必须自建：四道门状态、人工等待、版本迁移、审计事实、跨任务的可恢复业务语义；
- 风险：Redis 成为额外持久化依赖，队列状态和业务数据库需要一致性策略；job payload 不能放敏感原文或大文件；
- 分类：**适合二开/队列候选**，不作为完整 workflow。

#### 4.2 Hangfire

Hangfire 的官方文档覆盖 .NET 的 fire-and-forget、delayed、recurring jobs、持久化 storage 和 dashboard，适合 .NET 控制面快速提供可靠后台作业。仓库/官方标识显示其核心许可证为 LGPLv3 方向，不能把 GitHub API 的 `NOASSERTION` 当 MIT；需要在主线依赖清单和再分发方式上做法律核验。

- 可复用：持久 job、重试、定时、简单 dashboard；
- 缺口：长工作流的 Signal/Query、人工等待、定义版本和复杂补偿要另建；
- 分类：**条件复用/许可证审查**，如果 MIT 主线只允许 permissive 依赖，则隔离或替换。

#### 4.3 Celery

Celery 是成熟 Python distributed task queue，Canvas 提供 group/chain/chord，late acknowledgment 和 prefetch 可调节失败恢复；它适合 Python parser、OCR 或模型 worker。

- 可复用：解析任务队列、并行抽取、重试、结果 backend；
- 必须自建：业务版本、四门等待、审计、provider capability 和跨语言协议；
- 风险：broker/result backend、ack/幂等、任务 payload 和 Python 依赖矩阵增加部署复杂度；
- 分类：**适合 Python worker**，不作为整个产品 workflow。

### 5. Agent/图式编排的边界

LangGraph 的官方资料提供 checkpoint、interrupt/resume、streaming 和 human-in-the-loop，适合“从材料事实到大纲建议”的局部状态图；它不应拥有以下事实：用户项目权限、PPTX 版本、最终来源、审计报告、交付状态和模型密钥。

推荐把 LangGraph 或同类 Agent 图限制在一个 Activity 内：

```text
Input: normalized material + source refs + stage policy
Graph: extract -> classify -> propose -> validate -> return structured draft
Output: schema-validated draft + citations + model-call records
```

- Agent 图失败只影响该 Activity，可重试或请求用户确认；
- graph state 必须序列化到 Activity 输出或工作流输入，不把隐式 Python/JS 对象作为长期事实；
- prompt、工具和模型版本进入 `workflow_definition_version`/`provider_policy_version`；
- 图式节点不得直接写 PPTX 包、修改权限或发送未经批准的外部请求。

Dify、Flowise、n8n 等完整平台可借鉴可视化编排、provider 管理、审计和运维体验，但 Dify/n8n 许可证存在附加限制，Flowise 当前 README 已标明归档，且它们的产品运行时远大于本项目需要；全部标为 **仅可借鉴/必须隔离**，不作为 MIT 核心依赖。

### 6. Provider registry 与能力契约

PptxSmith 内部必须有自己的 provider registry；gateway 是实现，不是协议。每个 provider/model deployment 至少声明：

```json
{
  "providerId": "deployment-a",
  "kind": "llm",
  "model": "model-name",
  "capabilities": {
    "streaming": true,
    "jsonSchema": true,
    "jsonObject": true,
    "toolCalls": false,
    "vision": true,
    "images": false,
    "maxContextTokens": 128000
  },
  "policy": {
    "dataResidency": "deployment-defined",
    "retention": "provider-defined",
    "allowExternalSearch": false,
    "maxCostPerTask": 2.0
  },
  "pricing": { "inputPerMillion": 0, "outputPerMillion": 0 },
  "rateLimit": { "rpm": 0, "tpm": 0, "concurrency": 0 }
}
```

实际实现应使用版本化 schema，不把示例字段直接当代码契约。每次模型调用记录：`call_id`、task/stage、provider/model、capability decision、input/output token 数、估算/实际成本、延迟、attempt、fallback reason、错误分类和脱敏 trace ID；默认不记录完整材料、密钥或完整 prompt。

结构化输出能力分级：

| 等级 | Provider 行为 | 允许的阶段 |
| --- | --- | --- |
| S1 | 原生 JSON Schema/structured output，并通过本地 schema 校验 | 大纲、语义对象、审计数据等关键阶段 |
| S2 | 原生 JSON object，但不保证 schema | 可在本地校验、有限修复后用于非关键草稿；关键阶段需人工确认 |
| S3 | 只接受 prompt 约束文本 | 普通解释、候选文案；不得直接生成交付语义对象 |
| S0 | 不支持所需能力或能力声明不可信 | 拒绝路由，提示更换 provider |

OpenAI-compatible 仅证明 HTTP 请求/响应形状。Presenton 的公开 issue 与本项目风险相符：网关可能接受 `response_format=json_schema`，但下游 Gemini 适配器未保留语义，导致正常聊天成功、结构化阶段失败。因此必须做 capability probe、提交小 schema、验证返回对象，并在失败时明确降级或拒绝；不能静默把 S2/S3 当 S1。

### 7. Gateway 候选

#### LiteLLM

LiteLLM 的官方文档/仓库资料覆盖 100+ provider 的统一接口、routing、fallback、预算、virtual keys、spend tracking 和 proxy。核心许可证文件包含 MIT 部分，但 enterprise 目录/功能存在独立许可边界，必须按锁定版本审查。

- 可复用：provider 适配、统一请求形状、预算/virtual key、路由和观测模式；
- 风险：Python gateway 增加服务和依赖；provider 语义差异、structured output、tool call、vision 仍需本项目 capability matrix；
- 分类：**可选外部 gateway/适合二开边界**，不让业务直接绑定 LiteLLM 内部 API。

#### Bifrost

Bifrost 是活跃的 Go、Apache-2.0 gateway 候选，官方仓库/发布资料强调多 provider、adaptive routing、virtual keys、治理规则和兼容端点。它的 Go 运行时和较新的生态可以作为 LiteLLM 的对照，但“更快”是官方/项目声明，不能替代本项目的 provider 兼容性与成本测试。

- 可复用：治理规则、model alias、provider key 管理、路由审计思路；
- 风险：版本变化快、与业务 schema/事件/成本模型仍需适配；
- 分类：**可选隔离 gateway/仅可借鉴**，先做 adapter，不把其配置模型暴露给领域层。

#### Direct adapters

直接在 provider registry 内实现少量 HTTP adapters 是 v0.1 的必要兜底：控制数据路由、错误分类、能力探测和敏感材料策略，减少对 gateway 的硬依赖。代价是 provider SDK 和协议变动由项目维护。推荐“内部 adapter interface + 可选 LiteLLM/Bifrost endpoint”，而不是“只选一个 gateway”。

### 8. 成本、限流、降级与数据路由

- 每个项目/成员/provider/model 有并发、RPM/TPM、单任务预算和日/月预算；超过预算进入用户确认或安全失败，不自动换到未授权 provider；
- fallback 只能在能力兼容、数据路由策略相同、预算允许和用户授权的 deployment 集合中发生；必须记录 `fallback_reason`；
- 生成文字、结构化对象、图片、embedding、检索 rerank 分开计费和计量；图片失败不应重跑整稿；
- provider request 默认不带额外联网能力；联网检索由显式阶段开关控制，来源进入事实模型；
- 敏感材料只发送到用户允许的 deployment，日志只保留摘要、哈希/引用和计量；provider 的 retention、region、训练使用声明进入配置审计；
- 速率限制导致延迟时，UI 显示排队/预计等待，不用“失败重试”制造成本风暴；
- 重试按错误类别：网络/429/5xx 可指数退避；认证、schema、权限、内容策略和事实冲突不得盲重试；
- 所有降级和 provider 变更都写入审计报告，用户可以看到使用了哪个模型和成本。

### 9. MCP 与工具安全

MCP 不进入 v0.1 生成核心。未来若引入：

- 每个 server 有明确 allowlist、版本、来源、权限、网络和数据范围；
- 工具调用必须经过 Activity/网关，不得由模型直接访问宿主路径、Docker socket、任意 URL 或数据库；
- 写入、外发、删除和购买等副作用默认需要阶段门确认；
- 工具输入输出写入可脱敏审计；失败可重放但不能重复副作用；
- 工具 schema、server 版本和授权策略绑定 workflow definition version；
- 任何提示注入只被当作不受信输入，不能改变权限或 provider policy。

### 10. 失败、取消和恢复模型

必须把状态和错误分开：

- `RUNNING`/`WAITING_USER`/`PAUSED`/`CANCEL_REQUESTED`/`SUCCEEDED`/`FAILED_RETRYABLE`/`FAILED_REVIEW`/`CANCELLED` 是工作流状态；
- `ProviderAuthError`、`RateLimited`、`CapabilityMismatch`、`SchemaInvalid`、`SourceConflict`、`UnsafeInput`、`WorkerLost`、`TargetSoftwareGateFailed` 是结构化错误类别；
- `FAILED_RETRYABLE` 只允许符合策略的 Activity 重试；`FAILED_REVIEW` 进入用户修正或换 provider，不自动循环；
- `CANCEL_REQUESTED` 必须在阶段边界和 Activity cancellation 处收敛，取消后不得标记交付；
- worker 崩溃后由 durable engine/queue 重新派发，Activity 必须幂等；文件写入采用临时路径→校验→原子提交；
- 工作流版本升级使用 Temporal worker versioning/patch 或新 workflow type；不能直接修改已有历史要求的命令序列；
- 任何恢复都生成可审计事件，不覆盖原事件。

### 11. 最小验证计划

1. **Temporal .NET Spike**：Linux Docker 单节点运行 Temporal server 与 .NET SDK；实现四门最小工作流、Signal/Query、人工等待、Activity retry、cancel、worker crash/restart、event replay 和 workflow version upgrade。
2. **队列对照 Spike**：用 BullMQ 或 Hangfire 实现同样任务，记录需要自建的人工等待、事件历史、版本升级、幂等和恢复代码量；Python parser 单独用 Celery 做对照，不把三种队列混进主线。
3. **Provider capability probe**：对至少三个真实 provider 和一个 OpenAI-compatible gateway 测试 streaming、JSON Schema、JSON object、tool call、vision、图片和错误码，输出统一矩阵；故意使用不支持 schema 的 endpoint 验证不会误标 S1。
4. **成本/限流/降级**：模拟 429、5xx、超预算、超并发、provider key 失效和数据路由冲突；验证重试分类、fallback 授权、事件和审计记录。
5. **用户恢复**：在大纲确认前后、代表页等待中、交付 QA 失败时分别刷新 Web、断开 SSE、杀掉 worker、恢复任务并比较版本/事件/成本一致性。
6. **敏感材料**：验证密钥不进 workflow history、普通日志或浏览器；provider 只收到允许的文件引用和脱敏请求。
7. **替换成本**：以一个 fake provider 和一个 fake workflow worker 替换真实实现，证明领域对象和 UI 协议不依赖 LiteLLM、Bifrost、Temporal 或 LangGraph 私有类型。

### 12. 硬淘汰条件

- 只能提供队列执行，不能表达人工等待、恢复、版本和审计，且项目需要大量自研隐式状态；
- 通过重试机制重复不可幂等副作用，或无法区分可重试和不可重试错误；
- provider gateway 不能报告能力、成本、限流和 fallback 原因，或把完整敏感材料写入日志/历史；
- “OpenAI-compatible”测试只检查 HTTP 200，不检查 structured output、tool calls、vision、streaming 和错误语义；
- Agent 框架把权限、PPTX 包、来源或交付状态交给模型自由决定；
- 许可证、企业目录或网关服务条款无法与 MIT 自托管主线兼容；
- 引入 Temporal/Dapr 等基础设施后，单节点安装、备份、升级和故障恢复成本没有明确预算与文档；
- MCP/server 工具可任意写文件、发网络请求、读取密钥或绕过用户确认。

### 13. 来源与证据边界
