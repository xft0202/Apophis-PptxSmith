# 评估后端运行时与应用服务体系

Type: research
Status: open
Blocked by: 21

## Question

比较 .NET/ASP.NET Core、Go、Rust、Node/TypeScript、Python 和必要时 Java 作为 Linux Docker 后端的适用性，重点不是语言排名，而是对本项目产品目标的支持程度。

必须覆盖：

- PPTX 文档引擎集成边界；
- 长任务、流式进度、文件处理、并发、取消、恢复和资源隔离；
- 多用户账号、权限、模型配置、审计和 API 设计；
- AI 辅助开发、长期贡献者、调试/测试/可观测生态；
- Docker 镜像、升级、跨平台和未来 Rust 客户端边界；
- 现有成熟库的复用/二开机会与许可证。

输出应允许“后端运行时”和“文档引擎语言”分离，不强行追求全栈单语言。

### 1. 结论

v0.1 后端采用 **ASP.NET Core 控制面 + 受限执行 worker** 的候选基线，但暂不把具体 .NET 小版本和任务编排产品写成最终总技术栈。控制面负责账号、项目、权限、任务命令、事件读取、版本、审计和 API；PPTX 编译面以 .NET/Open XML SDK 为强候选，材料解析或 AI 专用能力可以由 Python worker 提供，但必须通过版本化协议、文件句柄/对象存储引用和资源限制隔离。

推荐的最小进程边界：

```text
Web Client
    │ REST + SSE
    ▼
ASP.NET Core API / Control Plane
    ├── relational state: users, projects, tasks, versions, audit
    ├── authorization, idempotency, event cursor
    └── job submission
          │ durable job contract
          ├── PPTX Worker (.NET: Open XML SDK + selected high-level layer)
          ├── Parse Worker (Python only when Docling/other parser is selected)
          └── Model/Provider Adapter (HTTP, capability-aware)
```

这不是现在就拆成微服务。v0.1 可以用一个 Compose 部署、一个 API 进程和一个或多个 worker 进程；边界先以模块/进程/协议落实，等负载、权限和故障证据证明需要再独立扩容。

**关键原则**：运行时选择不改变 PPTX 事实源。原始 OPC 包、关系、嵌入工作簿和审计结果必须由文档层保存；API 只编排和授权，不能把文档对象压扁成普通 JSON 后再整稿重建。

### 2. 统一评分方法

按票 13 的硬门先淘汰，再使用以下权重预评分；满分 5 分，不是性能 benchmark，也不替代同题验证。

| 维度 | 权重 | 关注点 |
| --- | ---: | --- |
| PPTX/文件引擎集成 | 20 | Open XML/包关系/字体/图表/嵌入对象/解析器边界；失败是否可审计。 |
| 长任务与资源隔离 | 20 | 排队、取消、超时、重试、恢复、进程隔离、文件处理和流式事件。 |
| 多用户 API/权限/审计 | 15 | 认证授权、项目隔离、稳定错误模型、幂等和版本审计。 |
| AI/解析生态 | 15 | provider、结构化输出、OCR、文档解析、embedding 和本地模型接入。 |
| Docker/运维/观测 | 15 | Linux 镜像、健康检查、优雅关闭、日志、指标、trace、升级。 |
| 维护与贡献者 | 10 | 活跃度、许可证、调试测试、人才可进入性和五年风险。 |
| Rust 客户端/API 演进 | 5 | API/事件协议是否与服务端语言解耦，未来 Tauri 是否可复用。 |

### 4. 运行时取舍

#### 4.1 ASP.NET Core / .NET

**优点**：

- 与 `DocumentFormat.OpenXml`、ShapeCrawler 候选、SkiaSharp/HarfBuzz 量字在同一运行时，减少 PPTX 包和字体数据跨语言序列化；
- ASP.NET Core 的 DI、认证授权、健康检查、结构化日志、OpenTelemetry 和 Docker 部署适合控制面；Context7 官方资料显示可区分 liveness/readiness，并有请求指标和标准标签；
- 官方 `BackgroundService`/`IHostedService` 支持长驻 worker、队列和取消 token，且文档明确优雅关闭时会等待任务结束；这适合实现 worker 外壳，但它本身不是崩溃后 durable workflow；
- C# 贡献者和测试工具成熟，Open XML SDK 官方维护信号强，适合把低层包事实源留在服务端。

**限制**：

- .NET SDK/SkiaSharp 镜像和 native 依赖需要控制体积与字体安装；Spike C 记录运行时约束和镜像成本；
- 从零生成主题、母版、版式、关系和风格包仍需项目封装，不能把 Open XML SDK 当现成生成器；
- 解析、OCR、科学计算和部分模型生态弱于 Python，需要以 worker/HTTP 适配，而非把 Python 依赖硬塞进 API 进程。

分类：ASP.NET Core 和 .NET worker **可直接复用/适合二开**；低层 Open XML SDK **强基线**；ShapeCrawler **条件二开**；Python parser **按适配层引入**。

#### 4.2 NestJS / Node / TypeScript

**优点**：

- 与 React/TypeScript 前端共享类型、错误模型和开发者生态，NestJS 的模块、DI、队列和 WebSocket/HTTP 生态适合控制面；官方文档明确 Bull/BullMQ 可把 processor 放到独立进程，并可更新任务进度；
- 流式事件、文件上传、provider SDK 和 JSON Schema 处理成本低，AI 应用贡献者进入门槛低；
- Fastify/NestJS 的容器化和测试生态成熟。

**限制**：

- PPTX 核心仍需要 .NET worker 或重新寻找不成熟的 TS OOXML 生态；这样不能消除多运行时，只是把控制面换成 Node；
- CPU 密集、超大 ZIP、字体 shaping 和图表缓存操作必须移出 Node 主进程，不能依赖 event loop；
- BullMQ/Redis 解决队列执行，不自动提供版本审计、长流程演进、业务幂等或交付门事实源。

分类：NestJS/Node **强替代**；队列/进度模式 **可借鉴**；PPTX 仍 **必须隔离到专门 worker**。若后续贡献者结构和 API 开发速度成为主要瓶颈，可用同一协议替换控制面，不改变领域模型。

#### 4.3 FastAPI / Python

**优点**：

- FastAPI 官方资料提供类型验证、OpenAPI、依赖注入、WebSocket、流式 JSON 和客户端生成；Docling、MinerU、OCR、模型 SDK 和数据处理生态最接近材料解析任务；
- Python 适合快速接入 provider、结构化输出修复、文档抽取和实验性算法；
- 控制面和解析面都可以用 Python，减少早期语言数量。

**限制**：

- FastAPI `BackgroundTasks` 官方文档明确适合响应后的小任务；重计算和多进程/多服务器任务应使用 Celery 等外部系统。它不能单独证明任务可恢复；
- PPTX 的低层保真、Open XML SDK、SkiaSharp/HarfBuzz 路线要通过 .NET sidecar 或 Python 另建包层；
- Python 依赖、native OCR/ML 包和字体库更容易造成镜像体积、供应链和版本矩阵扩大；CPU/内存隔离必须由 worker/container 完成。

分类：FastAPI **适合解析/AI worker，也可作为控制面替代**；不直接承担 PPTX 核心事实源，除非同题验证证明 Python 引擎能保留同样的包闭包和编辑性。

#### 4.4 Go

**优点**：

- 单二进制、低运行时成本、并发和容器部署优秀，适合文件服务、队列 worker、代理或高并发 API；OpenTelemetry-Go 和 HTTP 生态成熟；
- API/事件协议容易稳定，未来 Rust 客户端不受影响。

**限制**：

- `gopptx` 当前为 alpha、单一作者信号弱，本项目已实测跨生成器图表路径兼容失败；不能以 Go 的语言优势补偿 PPTX 生态风险；
- OCR/文档理解/模型 SDK 需要外部服务或 cgo/native 依赖，AI 解析贡献者生态不如 Python；
- 直接作为 PptxSmith 控制面会迫使项目自行补齐更多领域、权限和文档适配层。

分类：Go **条件保留为边界服务**；`gopptx` 当前 **研究隔离**；不作为 v0.1 主控制面或唯一文档引擎。

#### 4.5 Rust / Axum

**优点**：

- Axum/Tokio/Tower 提供模块化路由、中间件、流式 body 和优雅关闭；内存安全和低资源运行适合未来执行器或客户端相关服务；
- 可与未来 Rust/Tauri 客户端共享部分协议工具和安全边界。

**限制**：

- 当前缺少已通过本项目 PPTX 语料库的成熟 Open XML 读写/保留引擎；文档、字体、解析和 AI 生态需要大量自建或绑定；
- Rust 不因“未来客户端计划”自动成为服务端最佳选择；将未验证引擎风险前置会拖慢 v0.1；
- 编译、跨平台 native 依赖和新人贡献门槛增加长期维护成本。

分类：Axum **可借鉴/后续可用**；未来可用于独立高性能 worker，但不进入 v0.1 主线控制面或 PPTX 核心。

#### 4.6 Spring Boot / Java

**优点**：

- Spring Boot 的 Actuator 官方能力覆盖审计、健康、指标和生产管理，企业部署、认证、数据库、迁移和测试生态非常成熟；
- Java 贡献者和长期支持体系强，适合已有 Java 团队。

**限制**：

- 与当前 Open XML/SkiaSharp 验证、Python 解析和前端生态没有直接优势；
- 运行时和工程面较重，对单节点自托管 v0.1 的最小安装不占优；
- 需要额外验证中文字体、PPTX 包操作和 provider/解析边界，不能以企业成熟度替代产品同题证据。

分类：Spring Boot **条件保留**；适用于既有 Java 企业团队或后续控制面重构，不作为当前默认。

### 5. 任务、文件和 API 边界

本票不冻结具体队列/编排产品，但冻结以下后端契约：

- HTTP 请求只创建命令、查询状态或读取事件，不在请求线程直接完成 PPTX 编译、OCR 或长模型流程；
- 每项任务有稳定 `task_id`、`project_id`、`input_version`、`idempotency_key`、`attempt`、`state`、`cancellation_requested_at` 和 `event_sequence`；
- worker 只能通过受控输入引用访问文件，禁止任意宿主路径；上传包先做大小、展开比、关系、宏/OLE/外链和压缩炸弹检查；
- worker 输出临时目录、结构化结果、日志和产物必须带任务/项目范围，任务结束后按保留策略清理；
- 取消是协作式且可审计的：API 写入取消请求，worker 在阶段边界和可中断 I/O 检查 token；不能承诺强杀后仍保留半成品；
- 重试按错误类别区分：provider 临时错误可重试，校验/权限/事实冲突不得盲重试；同一幂等键不能产生多个可交付版本；
- 事件必须可从数据库/持久队列补偿，SSE/WebSocket 只是传输，不是事实源；
- OpenAPI 错误码、权限拒绝、审计事件和 trace context 跨运行时保持一致。

### 6. 进程与部署策略

v0.1 的最小 Compose 形态暂定为：

- `api`：控制面和短请求；
- `worker-pptx`：.NET 文档/字体/校验 worker；
- `worker-parse`：仅在选定 Python 解析器时启用；
- `db`/队列/对象存储：由票 16、17 决定最小形态，不能因为运行时选择而提前引入；
- `otel`：开发/企业部署可选，应用输出 OTLP 或结构化日志，不把观测服务写死为唯一安装依赖。

所有容器必须有 CPU/内存/临时盘限制、非 root、只读基础文件系统或明确可写目录、网络出口策略、健康检查和优雅关闭。API 与 worker 镜像可独立升级，但协议版本和迁移必须向后兼容一个支持窗口。

### 7. 硬淘汰条件

任一条件成立，候选不得作为 v0.1 主控制面或文档核心：

1. 只能在 HTTP 请求或进程内临时后台任务中运行长编译，进程崩溃/重启后没有可恢复状态；
2. 无法把不受信任 PPTX/ZIP、OCR、模型调用和字体处理隔离，或会把任意宿主文件路径暴露给 worker；
3. PPTX 引擎没有同题语料库中的关系/部件闭包、嵌入工作簿、PowerPoint/WPS 重开和编辑探针证据；
4. API 不能提供稳定 OpenAPI/错误码/幂等/取消/事件游标，前端只能解析日志或 provider 原始错误；
5. 运行时和关键依赖许可证不清、不可再分发或与 MIT 主线冲突；
6. 需要把敏感材料强制发送至托管服务，或 provider 密钥必须进入浏览器；
7. 为获得单一语言而放弃更成熟的文档/解析基础，且没有量化的用户价值或替换计划；
8. 引入多进程/多语言却没有版本化协议、观测关联、故障模型和测试预算；
9. 维护信号显示归档、单点作者或上游不透明，而关键能力无法被项目接管。

### 8. 最小验证计划

在票 15 关闭后，必须做以下 spike，仍不进入生产脚手架：

1. **控制面 API**：用 ASP.NET Core 实现最小任务命令、状态查询、SSE 事件和 `after=sequence` 补偿；模拟重复命令、断线、权限拒绝和版本冲突。
2. **worker 生命周期**：API 创建任务，.NET worker 执行 Open XML 包检查/图表补丁，测试取消、SIGTERM、进程崩溃、重启恢复和临时目录清理。
3. **跨运行时协议**：Python parser worker 通过版本化 JSON/文件引用协议返回结构化材料和来源，不传大二进制到 API 内存；验证超时、坏 JSON、进程退出和 schema 不兼容。
4. **资源隔离**：恶意 ZIP、超大图片、坏字体、嵌入 OLE/外链和模型超时分别触发限制；确认 API 不被 worker 拖垮。
5. **观测关联**：任务、项目、用户、worker attempt、provider call 和审计事件共享 trace/correlation ID；敏感原文、密钥和完整材料不进普通日志。
6. **容器升级**：单节点 Compose 中先升级 API 再升级 worker、模拟 worker 回滚，验证旧任务和旧事件可读。
7. **同题对照**：至少将 .NET 控制面/worker 与 NestJS 或 FastAPI 控制面对同一个协议 fixture 对照，避免语言偏好掩盖真实运维差异。
