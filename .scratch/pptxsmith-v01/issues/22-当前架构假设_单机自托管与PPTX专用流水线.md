# 当前架构假设：单机自托管 + PPTX 专用流水线（待验证，非定论）

Type: grilling
Status: resolved
Blocked by: 13

> **证据状态警告（2026-09-25 所有者纠正）**：本票内容为**当前证据下的工作假设**，不是定论。
> 本项目处于立项前、打地基阶段，任何结论都必须在后续同题验证中被证实或被推翻。
> 文中出现的「冻结」「不可逆」措辞一律理解为「在获得更强证据前按此推进」，
> 不构成不可更改的决定。

## Question

票 21 的架构家族比较已经收敛出**形态**结论（控制面 + durable workflow + 专用解析/编译/QA worker + PostgreSQL 事实库 + S3-compatible 对象合同 + 长期身份/审计/观测边界），但该结论当时与 vendor 级候选一起挂在同一张票上，导致**已经成熟的决定陪着尚未证据充分的决定一起阻塞**。

本票只解决一件事：**整理出家族级形态的**当前最佳假设****，明确哪些是不可逆合同、哪些是可延后决定但必须保持契约的实现，以及哪些被明确排除。vendor 级选择（workflow runtime / 前端框架 / 对象存储实现 / 身份产品 / 模型网关 / parser）不在本票范围内，由票 21 收窄后继续。

本票不做新的调查，只做**收敛**：把票 21 已产出的形态证据整理成一份**可被证伪的工作假设**，并补齐论证。它随时可能被后续证据推翻。

## Answer

### 1. 当前假设的形态

**产品控制面 + durable workflow + 专用文档流水线**（票 21 的「方案 A」形态）：

```text
PC Web 工作台（独占，>=1440px）
        │ typed REST + 可恢复事件流
产品控制面（授权 / 审计 / 阶段状态 / 版本）
        │ workflow 协议
Durable Workflow Runtime
        ├── 解析/抽取 Worker
        ├── 内容/Provider Worker
        ├── PPTX 编译 Worker
        ├── 预览/QA Worker
        └── 目标软件验收 Gate Runner
PostgreSQL 事实库 + S3-compatible 不可变对象存储
长期身份边界（本地账号 + OIDC 接入）+ OpenTelemetry / SBOM / 签名
```

### 1.1 部署前提（所有者明示，已确认）

**单机部署是唯一形态，且与人数无关。** 一人部署自用、或一人部署给多人共用，**都是单机**。
不存在「多人使用所以要上集群」的推理。

因此以下形态被**直接排除**（不是因为技术差，而是因为与本项目规模不匹配，属于过度工程）：

- Kubernetes / Argo Workflows / Helm / GitOps 平台；
- Ceph / OpenSearch / CockroachDB / 分布式消息总线（Kafka/NATS 集群）；
- BPMN 流程引擎（Camunda 类）与容器级工作流编排；
- 企业 IdP 全家桶（SCIM、LDAP 联邦、多租户运营）；
- 任何需要「平台团队」才能运维的组件组合。

**服务端唯一支持的部署方式**：一台 Linux 服务器上的 Docker Compose，与 ADR-0007 一致。

### 2. 当前假设：需要先定下来的合同（待验证）

按票 21 与票 13 的结论，以下属于**形态级不可逆决策**，不随 vendor 变化：

| 合同 | 内容 | 为什么不可逆 |
| --- | --- | --- |
| 耐久执行边界 | 长任务、四道门的人工等待、取消、恢复、重试必须有显式耐久语义；**禁止进程内任务队列** | 无耐久层时，四道门会退化成隐式状态机，恢复与审计无从谈起 |
| 事实源分层 | PostgreSQL 保存成员/项目/版本/审计/来源/任务事实；S3-compatible 保存不可变对象；**原始 OPC 包是 PPTX 事实源** | 缓存、向量库、预览器、模型网关、Agent 图只能是可重建投影 |
| 文档引擎解耦 | 引擎通过进程/API/队列边界与应用运行时隔离 | 引擎语言不得反向锁定控制面语言，否则替换引擎即重写产品 |
| Provider 解耦 | LLM/嵌入/生图/检索经过 capability registry 与 provider 契约，带超时、预算、错误、数据路由边界 | 直接散落调用会让 provider 变更穿透业务代码 |
| 预览不是交付真相 | 浏览器/LibreOffice 只作预览与独立信号；编辑性与中文排版以目标软件验收为准 | 见 ADR-0013 与票 03 |
| 身份与隔离 | 项目/成员级隔离、密钥保护、审计日志从第一天存在；提供 OIDC 接入边界 | 后补权限会迫使数据模型重做 |
| 观测与供应链 | OpenTelemetry、结构化审计、SBOM、签名、备份/恢复从第一天进入受支持路径 | 见 ADR-0006 与票 13 的长期生产基础原则 |
| 部署形态 | 单节点 Linux Docker Compose 运行**同一生产组件**；扩容加副本或外部服务，不更换地基 | ADR-0007 + 票 13；禁止 SQLite 与本地生产文件 |

### 3. 可延后但必须保持契约的实现

以下**不冻结具体产品**，只冻结它们的契约形状，由票 21 收窄后的 vendor 调查填充：

- **Durable workflow runtime**：Temporal / Restate / Hatchet / Camunda / DBOS / 事件原生组合等，必须在统一 fixture 下可比；契约是「durable 语义 + 人工等待 + 版本升级 + 审计一致性」。
- **前端框架**：React / Vue / SvelteKit 等均为候选，不由样本产品反向锁定；契约是「typed API + 可恢复事件流 + 中文 IME + 1440px 信息密度 + 未来客户端可复用」。
- **对象存储实现**：至少两个 S3-compatible 实现必须通过同一备份恢复 fixture；契约是 S3 语义 + 版本 + 校验 + 临时 URL + 删除恢复。
- **身份产品**：应用内身份 / Keycloak / Ory / 企业 OIDC；契约是登录、成员、项目隔离、密钥、注销、备份、升级矩阵。
- **模型网关**：直接 adapter / LiteLLM / Bifrost / Kong / Higress / Portkey；契约是 capability 探测、结构化输出、限流、预算、fallback、数据路由。
- **Parser 与 PPTX 编译器**：Docling / MinerU / Unstructured / Tika / Open XML SDK 系；契约是中文、来源 locator、许可证、崩溃恢复、目标软件验收。
- **控制面与 worker 的实现语言**：**完全未定**（ADR-0003 仍 challenged，ADR-0009 仍 proposed）。

### 4. 明确排除的形态

| 被排除 | 原因 |
| --- | --- |
| 模块化单体**且无耐久执行层** | 可作为应用形态，但不得偷掉耐久执行层 |
| 全系统事件化（所有事实复制进事件/投影） | 会让审计与调试更难，事件主干只作 workflow/审计的内部机制候选，不自动全系统事件化 |
| Kubernetes/Argo + Ceph/OpenSearch + BPMN 流程引擎 | **直接排除**：与单机部署前提不匹配（见 1.1）。不是「保留为隔离 profile」，而是不进候选 |
| 数据编排优先（Prefect/Dagster）作为**产品控制面** | 对用户确认、阶段门、局部回滚、交付审计不是第一公民；只用于解析/索引子系统 |
| local-first/桌面壳作为 v0.1 形态 | 未来约束（Rust 客户端）参与设计，但不提前进 v0.1 |
| 事件原生/消息总线作为**首期**基础设施 | 超出单机规模；先证明 PPTX 核心链路需要它，再谈引入 |
| SQLite、本地生产文件、进程内后台任务、计划迁移的过渡组件 | 票 13 + ADR-0006 硬淘汰，不进入任何受支持部署 |

### 5. 为什么这是「长解」而非偏好

评价函数不是**组件数量最少**，而是**五年总返工最小**。形态 A 的论证要点：

1. **阶段门是产品的核心资产**，而阶段门天然需要耐久、可暂停、可恢复、可审计——这直接排除了无耐久层的形态。
2. **PPTX 与事实保真是存量质量承诺**，要求原始包、来源、版本、审计有明确事实源，缓存/投影/网关不得成为事实源。
3. **用户任务与形态同向**：用户任务（确认方向、早停、回滚、追责）与形态（阶段、版本、审计）一一对应，不需要为架构妥协体验。
4. **替换成本被隔离**：vendor 级组件全部在契约之后，替换 vendor 不触发数据模型与交付返工——这正是票 13 的「长期无返工」要求。
5. **单节点可行**：形态 A 可以在单台 Linux 上以同一生产组件运行，企业规模时才加副本或外部服务，不需要更换地基。

反过来说，「组件少的最小方案」已被票 21 明确证伪为错误的评价函数（见票 21 第 6 节撤回列表）。

### 6. 与既有 ADR 的关系

- **ADR-0003（TS 全栈）**：仍为 `challenged`。本票只冻结形态，**不解除**其被挑战状态。
- **ADR-0009（.NET 引擎路线）**：仍为 `proposed`。本票不预判引擎语言；「文档引擎与应用运行时解耦」这条合同的存在，正是为了让 ADR-0009 的答案不被形态绑定。
- **ADR-0006 / 票 13**：本票是其「长期生产基础一次到位」原则在形态层的具体化。
- **ADR-0007 / ADR-0013**：部署形态与验收宿主边界已由这两条覆盖，本票不重复。

### 7. 本票不解决的问题（转交票 21 收窄后）

以下全部保持开放，由统一 fixture 的证据决定，不接受偏好或语言熟悉度作为理由：
