# 评估前端应用技术体系

Type: research
Status: open
Blocked by: 21

## Question

针对 PC Web、视口 ≥1440px、对话式 Agent、四道阶段门、结构化大纲面板、代表页预览、版本回滚和审计报告，比较 Next.js/React、Nuxt/Vue、SvelteKit 及必要的 UI/state/data-fetching 方案。

必须调查：

- 长期维护、组件生态、复杂后台交互、实时流式状态、可访问性和中文输入体验；
- 自托管 Linux Docker、与后端 API 解耦、未来 Rust/Tauri 客户端复用；
- 账号/项目/任务/版本/审计的桌面信息架构；
- UI 质量与设计系统如何落地，不以模板拼装代替产品体验；
- 许可证、维护状态、贡献者门槛和迁移成本。

输出候选矩阵、适用条件、淘汰条件和最小验证方式，不以个人框架偏好作结论。

## Reopened

本票原有答案中的“候选基线”已撤回，不再作为架构或工程依据。原因是它把单节点部署误化为最小组件组合，并在全景架构调查完成前过早收敛到既有技术路线。保留原文只作为研究记录；所有 React/Vite、Next.js、Vue/Nuxt、SvelteKit 的分数和基线标签必须重新调查、重新评分。

v0.1 前端采用 **React + TypeScript + Vite 的独立 Web 工作台**作为基线，前端只负责交互、视图、客户端缓存和事件呈现；业务 API、长任务、文件处理和 PPTX 编译由后端体系提供。路由采用 React Router，服务端状态采用 TanStack Query，长任务采用“REST 命令 + SSE 事件流 + 可恢复游标”，本地瞬时 UI 状态优先使用 React state/reducer，只有跨页面且确有必要时再引入 Zustand。

组件层不直接采用一套不可替换的“后台模板”。使用 Radix UI primitives 或 React Aria Components 提供对话框、菜单、Popover、Tabs、焦点管理和键盘行为，再由项目维护自己的设计令牌和组件封装；表格、拖拽排序、阶段门、审计报告等高价值交互必须有产品级 fixture 和可访问性验收。

**保留替代项**：Vue 3 + Vite 是可行的第二路线；Nuxt 和 SvelteKit 可用于后续独立实验或在 React 基线长期不满足时重新评估。它们不因能力不足淘汰，而是因为 v0.1 的 API 解耦、贡献者生态和不需要 SSR 的约束使 React + Vite 当前综合风险最低。

**明确不采用**：Next.js App Router 不作为 v0.1 的全栈边界；PPTist 不作为代码依赖；Flowise 不作为前端基座；Open WebUI/LobeHub 等项目只吸收工作台交互和自托管经验，不复制其受限许可证代码或整个产品架构。

> **当前状态警告**：下方原有“v0.1 基线”、评分和候选结论均为全景调查前的历史研究记录，已撤回，不得作为当前技术或 ADR 依据。全景票 21 关闭后必须按统一体验夹具、许可证、恢复和替换成本重新评分。

### 2. 候选矩阵

| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| React + Vite | React/TS SPA，独立 API | 4.7 | 4.5 | 4.8 | 4.9 | 4.8 | **4.7** | **基线** |

### 3. 证据与取舍

#### 3.1 React + Vite

- GitHub API 快照显示 `facebook/react`、`vitejs/vite`、`remix-run/react-router`、`tanstack/query`、`radix-ui/primitives`、`TanStack/table`、`clauderic/dnd-kit`、`pmndrs/zustand` 和 `microsoft/playwright` 均活跃、许可证清晰，核心项目为 MIT 或 Apache-2.0；具体 stars/forks 是随时间变化的信号，不作为质量证明。
- LibreChat 的官方源码显示其前端使用 React、Vite、React Router、TanStack Query、Radix UI、Jotai、SSE 等，说明复杂多 provider、多文件、长对话和工具交互可以落在独立 React 工作台上。它的产品范围远大于 PptxSmith，不能整体复制。
- Context7 对 React、Next.js、TanStack Query、Radix、React Aria、TanStack Table 和 XState 的官方资料可核对组件组合、缓存失效/回滚、键盘焦点、表格模型和状态机能力。
- Vite 让浏览器层和后端服务完全解耦，未来 Tauri/Rust 客户端可以复用 API、事件协议、类型包和部分 React 视图；它不要求 Web 前端承担 PPTX 编译和长任务。
- 代价是需要自己处理 API 代理、认证刷新、SSE 重连、错误边界、文件上传、部署路径和设计系统；这些是可控的产品代码，不应通过引入全栈框架来隐藏。

分类：React/Vite/React Router/TanStack Query/Playwright **可直接复用**；Radix 或 React Aria、TanStack Table、dnd-kit **适合二开/封装**；LibreChat 的交互模式 **仅可借鉴**；不复制其服务端、身份、模型和文件架构。

#### 3.2 Next.js App Router

- Context7 官方资料确认 App Router 支持 Server/Client Components、Route Handlers 和流式响应；自托管时反向代理必须关闭 buffering，否则阶段门进度和 SSE/streaming 会被延迟。
- 官方资料同时明确：某些部署为 lambda 时不能承载长时间 OCR/文件工作，不能依赖请求生命周期保存状态或写文件；这与 PptxSmith 的长任务和审计要求冲突。
- Next.js 生态和贡献者规模很强，若产品以后需要 SEO、公开模板市场、同仓 BFF 或服务端渲染，重新采用它有合理条件。
- v0.1 已明确只承诺 PC Web、无营销首页、后端 API 独立和 Linux Docker；因此把 Next.js 当全栈边界会重复后端职责、增加 Server/Client 边界和部署/缓存规则，不是当前最小解。

分类：React 组件和部分自托管经验 **可借鉴**；Next.js 可作为未来公开内容/SSR 外壳的 **条件保留**；不把 Route Handler 当任务执行器，不把 ISR/缓存当任务状态源。

#### 3.3 Vue 3 + Vite / Nuxt

- GitHub API 快照显示 `vuejs/core`、`nuxt/nuxt`、`vuejs/pinia` 活跃且 MIT；Nuxt 官方资料显示 Nitro 提供 API routes、代码分割和多部署适配，Vue Router、Pinia 和 Vue I18n 生态完整。
- PPTist 的官方 README 是有价值的领域证据：Vue 3 + TypeScript 能承载复杂的 slide editor、右键菜单、快捷键、撤销/重做、表格/图表和中文字体资源。但 PPTist 明确承认 PPTX 导入/导出存在复杂对象保真边界，且仓库为 AGPL-3.0；不能把它的代码放进 MIT 主线。
- Vue 的响应式和单文件组件适合结构化面板，但团队未来若要大量复用 React AI 工作台组件或 React Aria/Radix 生态，需要承担双生态成本。
- Nuxt 的 Nitro/SSR 是成熟能力，但本项目没有 SEO 和首屏公开内容需求；引入它会增加服务端渲染、部署适配和前后端职责重叠。

分类：Vue 3 **强替代**；Pinia **仅在 Vue 方案被选中时可直接复用**；PPTist 的 schema/编辑器交互 **仅可借鉴**；Nuxt **条件保留**，不作为 v0.1 默认。

#### 3.4 SvelteKit

- GitHub API 快照显示 `sveltejs/kit` 活跃且 MIT；Context7 官方资料确认 adapter-node 可生成 Node 服务，SvelteKit 支持路由、SSR、form actions 和多部署 adapter。
- Open WebUI 的官方 `package.json` 显示 SvelteKit、Svelte、Vite、TypeScript、Cypress、Vitest、Tiptap、Yjs、虚拟列表和复杂文件/检索交互；它证明 Svelte 可支撑成熟 AI 工作台，而不是只能做静态页面。
- 代价是企业级组件、中文社区可进入性、第三方库类型覆盖和长期迁移经验相对 React/Vue 小；Svelte 版本和 adapter 变化也需要独立升级验证。

分类：Open WebUI 的信息架构、事件呈现和本地/远端 provider 模式 **仅可借鉴**；SvelteKit **条件保留**；当前不作为主线，除非 React/Vue 的阶段门交互在最小验证中出现无法接受的问题。

#### 3.5 组件、状态和数据层

| 能力 | 结论 | 吸收边界 |
| --- | --- | --- |
| Server state | TanStack Query | **可直接复用**。负责项目、任务、版本、审计查询缓存、失效、mutation 和失败回滚；不保存编译真相。 |
| Client transient state | React state/reducer，必要时 Zustand | **优先内置，按需二开**。避免全局 store 复制服务端状态。 |
| 阶段门状态 | 后端状态机为事实源，前端只投影；复杂局部交互可评估 XState | **后端优先；XState 条件复用**。不能让浏览器状态决定任务是否已执行。 |
| Accessible primitives | Radix UI 或 React Aria Components 二选一 | **适合二开/封装**。必须保留焦点、键盘、ARIA、中文标签和错误播报测试；不直接采用完整模板主题。 |
| Data table | TanStack Table | **可直接复用**。无样式 headless；审计报告和任务列表由项目设计系统呈现。 |
| Outline reorder | dnd-kit 或同等 MIT 方案 | **适合二开**。拖拽只是大纲顺序变更，不进入自由画布；必须支持键盘替代操作和版本回滚。 |
| Browser tests | Playwright | **可直接复用**。Chromium/Firefox/WebKit 和 Edge channel 做 Web 交互验证；PowerPoint/WPS 仍走独立目标软件门。 |
| UI kit | Ant Design/MUI/shadcn 只做对照 | **仅可借鉴**。完整套件可能带来模板化视觉、全局 CSS 和升级绑定；最终由项目维护自己的 tokens/components。 |

### 4. 前端边界与协议

前端不拥有以下事实：PPTX 包、任务执行、模型密钥、来源真相、审计最终结果、版本提交和权限判定。前端只展示后端已授权的数据并发出明确命令。

推荐交互协议：

- `REST/JSON`：创建项目、提交材料、确认阶段门、修改大纲、取消/重试、创建版本、下载产物；
- `SSE`：任务进度、阶段状态、模型调用摘要、审计检查结果和需要用户确认的事件；每个事件带 `task_id`、单调 `sequence`、`version`、`occurred_at` 和 `replayable` 标记；
- `GET /tasks/{id}/events?after={sequence}`：SSE 断线后的补偿读取；前端不把断线期间的本地状态当事实；
- OpenAPI 生成类型/客户端，领域错误使用稳定 `code` 和结构化 `details`，不能让前端解析人类错误文本；
- 所有面向用户的任务状态都能定位到项目、版本、材料、模型/provider 和审计报告。

### 5. 质量与验证计划

最小验证不建生产脚手架，只做前端技术 spike：

1. **阶段门工作台**：在同一页面完成澄清→大纲→代表页→交付的状态投影，模拟 SSE 乱序、重复、断线、补偿、取消和回滚；验证 1440px 与 1920px，不承诺更窄视口。
2. **中文输入**：测试 IME compositionstart/update/end、中文标点、粘贴长段落、快捷键与输入法冲突、表格单元格编辑和错误播报；不能只测试英文键盘事件。
3. **结构化面板**：大纲增删/排序/锁定、来源引用、成本预估、审计报告、任务列表和版本比较；键盘能完成所有非画布操作。
4. **可访问性**：对话框、Popover、Tabs、菜单、拖拽替代操作、焦点恢复、`aria-live` 进度和错误状态；Playwright + axe 类检查加人工键盘走查。
5. **长任务体验**：UI 交互 p95 `<500ms`；任务启动后首个进度事件目标 `<2s`；SSE 断线后可恢复，不出现假完成或无限 spinner。
6. **Docker 静态部署**：Vite 构建产物由独立 Web 容器提供，API URL、base path、认证 cookie/SSE 代理和健康检查可配置；不把 provider 密钥编译进前端。
7. **桌面复用检查**：API 类型、事件协议和业务组件不依赖浏览器专有全局；未来 Tauri/Rust 只替换壳与本地文件桥接，不重新设计领域协议。

### 6. 前端候选淘汰条件

任一条件成立，候选不得进入 v0.1 主线：

- 需要自由画布才能完成阶段门流程，或把画布坐标当核心领域模型；
- 无法可靠呈现长任务事件、断线补偿、取消、重试和版本回滚；
- 组件库对中文 IME、键盘、焦点、屏幕阅读器或错误播报没有可测试边界；
- 只能依赖托管平台、把部署配置或密钥绑定到供应商，不能在 Linux Docker 独立构建；
- 把服务端状态复制进多个客户端 store，导致刷新、重连或多用户并发时显示过期事实；
- 许可证、商标或组件代码来源不清，不能进入 MIT 主线；
- 需要同时维护两套互相耦合的前端运行时，且没有新增用户价值、替换路径或测试预算；
- 通过完整 UI 模板快速堆页面，但不能满足项目自己的设计令牌、信息密度和长期可维护性。

### 7. 未决与后续约束

- 票 15 决定后端 API/事件协议的具体运行时和认证中间件；本票只冻结浏览器边界。
- 票 16 决定任务编排后，需将其事件模型映射到本票的 SSE/补偿协议；不得让前端绕过后端直接连接 provider。
- 票 19 决定认证、成员和项目权限后，前端需要补充权限矩阵和无权状态 fixture。
- 组件库最终在一次可访问性/中文输入 spike 后二选一，当前不提前锁定 Radix 或 React Aria。

## SANDUN 基准约束

工作台评审必须以 SANDUN 的透明流水线、阶段产物、便利贴大纲、项目/风格连续性和逐页上下文作为体验基准，并横向对照 Gamma、Plus AI、Gemini in Slides 的低摩擦修改、回滚、宿主交付和来源/计划模式。技术候选不能因为复刻某个产品的界面而提前锁定；所有模式都必须通过中文 IME、断线补偿、阶段门、权限、版本和审计 fixture。
