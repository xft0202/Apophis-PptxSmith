# 评估数据文件与检索基础设施

Type: research
Status: open
Blocked by: 13, 21

## Question

确定项目数据、文件、版本、审计、来源和检索索引的长期存储方案，适配 Linux Docker、一人部署多人使用和敏感材料。

必须覆盖：

- PostgreSQL/long-term relational baseline, schema migrations and backup recovery；
- 本地文件、对象存储、S3 兼容服务和大文件生命周期；
- 文档版本、幂等任务、审计记录、删除和租户/成员隔离；
- 文本/表格/来源索引是否需要全文检索、向量检索及可替换实现；
- ZIP/PPTX 安全、展开比、宏/外链/嵌入对象隔离；
- 数据不出部署环境、模型路由和用户可见数据路径。

输出最小自托管方案、扩展方案和迁移边界，不提前引入复杂云基础设施。

## Reopened

本票原有答案已撤回为研究记录。尤其撤回“SQLite 开发/低并发 fallback”“本地文件卷 v0.1 默认”“PostgreSQL + 本地 BlobStore 最小方案”等表述：SQLite 不进入任何受支持部署，生产数据/文件存储和迁移策略必须从第一天按长期架构设计。全景调查完成前，不冻结 PostgreSQL 扩展、对象存储、搜索或向量方案。

> **当前状态警告**：下方原有 PostgreSQL/对象存储/检索候选结论均为全景调查前的历史研究记录，已撤回，不得作为当前实现或迁移依据。全景票 21 关闭后必须按统一 storage、备份恢复、许可证和替换成本重新评分；SQLite 和生产本地文件的淘汰规则除外，已由票 13 冻结。

### 1. 结论

v0.1 的生产数据基础设施从第一天按长期基线建设，不提供需要后续替换的临时数据库或生产文件后端：

1. **PostgreSQL 是业务事实库**：用户、成员、项目、材料版本、语义对象、工作流运行、产物清单、审计事件、来源引用和可重建索引元数据都在数据库中；
2. **S3-compatible 对象存储是生产 BlobStore 合同**：原稿、材料、字体、图片、生成的 PPTX、渲染快照和审计附件按 SHA-256/版本 manifest 保存，不把大文件和 PPTX XML 塞进数据库；默认自托管实现另由全景架构票从 SeaweedFS、Garage、Ceph、用户已有 S3 等候选中选定；
3. **检索和向量是可删除、可重建的投影**：首期使用 PostgreSQL 的结构化查询、全文/模糊索引和来源定位；embedding 只在验证有明确收益后启用，不能成为事实源或唯一来源定位机制。

PostgreSQL、生产对象存储和 BlobStore 协议是长期基线；不得把“单节点可部署”理解为“先用临时数据库/本地目录，未来再迁移”。

### 2. 候选比较

#### 2.1 关系数据库

| 候选 | 适用性 | 主要优点 | 主要风险 | 分类 |
| --- | --- | --- | --- | --- |
| PostgreSQL | **长期生产基线** | MVCC、多用户事务、约束、JSON、全文检索、RLS、备份和扩展生态；与任务/审计/版本一致性匹配 | 需要文档化备份、升级、权限和容量策略 | **可直接复用** |
| PostgreSQL + pgvector | PostgreSQL 的可选扩展 | 事实库、元数据和向量过滤同库；可用 exact/HNSW/IVFFlat，避免另起事实库 | embedding 维度/模型升级、索引重建、向量检索质量和资源开销 | **条件复用** |
| 独立 Qdrant | 中后期或用户已有向量平台 | payload filter、快照、local mode、.NET/Python 客户端和高规模向量检索 | 增加服务、备份、租户隔离和一致性；向量与事实库需双写/重建 | **扩展适配** |
| OpenSearch | 已有企业搜索平台 | Apache-2.0、全文/向量/观测一体 | Java 服务重、运维面大，v0.1 过度 | **企业外部集成** |
| Meilisearch | 面向搜索体验的独立服务 | 全文、过滤、混合向量搜索和易用 API | GitHub API 许可证为 `NOASSERTION`，需锁版本核验；额外索引一致性和服务 | **仅可借鉴/条件隔离** |

PostgreSQL 官方资料证明 MVCC 适合多用户并发事务；RLS policy 可作为第二道隔离防线；GIN/`tsvector` 可提供文本搜索。数据库选择以长期生产基线为准，不能用开发数据库降低首期架构门槛。

#### 2.2 文件/对象存储

| 候选 | 适用性 | 主要优点 | 主要风险 | 分类 |
| --- | --- | --- | --- | --- |
| S3-compatible object storage | **生产默认合同** | 版本、生命周期、multipart、跨节点/远端扩展和用户已有对象存储兼容；应用不绑定厂商 | 需要从 SeaweedFS、Garage、Ceph、用户已有 S3 等候选中选择默认自托管实现，并验证认证/region/一致性 | **可直接复用接口** |
| Local filesystem | 仅测试/开发 fixture | 便于单元测试和临时 worker scratch | 不作为生产 BlobStore，不提供从本地目录迁移作为正常产品路径 | **仅测试** |
| MinIO | 可选用户自管对象存储 | S3 API、版本、生命周期、加密和生态成熟 | 当前仓库显示 AGPL-3.0 且已归档信号；不应作为 MIT 项目默认打包核心 | **必须隔离/用户自选** |
| SeaweedFS | 大文件/大量对象扩展 | Apache-2.0、S3/file/filer、多节点扩展 | 对 v0.1 单节点过重，运维和故障矩阵增加 | **后续扩展** |
| 数据库 BLOB | 不采用 | 事务方便、部署简单 | 备份体积、数据库膨胀、流式访问、恢复和 PPTX 处理不适合 | **淘汰** |

### 3. 推荐数据模型和生命周期

数据库只记录事实和引用，原始内容用 blob 引用：

| 实体 | 关键字段 | 不变量 |
| --- | --- | --- |
| `workspace` / `user` / `membership` | `workspace_id`, `user_id`, role | 所有项目和文件访问必须经过 membership/permission 判定。 |
| `project` | owner、名称、状态、保留策略 | 不能跨 workspace 引用材料或产物。 |
| `blob` | `sha256`, size, media type, storage key, scan status | 内容寻址、不可变、上传完成前不可引用；重复字节只存一次。 |
| `material_version` | project、blob、parent、source kind、created_by | 原稿永不覆盖；每次修改/导入创建新版本。 |
| `semantic_document` / `source_fact` | version、stable id、text/value/unit、source locator | 事实带来源定位；模型改写必须产生显式新字段和审计。 |
| `workflow_run` | input version、policy version、state、attempt、cost | 任务状态与事件可恢复、可幂等；交付绑定确定版本。 |
| `artifact` | workflow、version、blob、quality status | PPTX、PDF、PNG、审计报告均不可变；新生成创建新 artifact。 |
| `audit_event` | actor、action、target、before/after hash、trace id | append-only 语义；删除是事件，不物理抹掉审计链。 |
| `search_document` | source id、text hash、index version、deleted_at | 索引可重建；不让索引内容绕过权限。 |
| `embedding` | source id、model id/version、dimensions、vector | 模型或 chunk 策略变化时新建索引版本，不覆盖旧结果。 |

文件路径不能由用户输入直接拼接。推荐逻辑 key：

```text
blobs/{sha256[0:2]}/{sha256[2:4]}/{sha256}
projects/{project_id}/manifests/{version_id}.json
artifacts/{artifact_id}/{type}
```

实际 key 必须由后端生成，并在下载/预览前重新做 workspace/project 权限检查。前端只拿短时授权的下载/预览句柄，不接触宿主绝对路径。

上传和生成流程：

1. 流式写入临时目录并限制总字节、entry 数和解压后体积；
2. 计算 hash、媒体类型和安全扫描结果；
3. 通过 ZIP/PPTX 包检查后原子移动到 content-addressed blob；
4. 在事务中写 `blob`、版本 manifest、来源和审计事件；
5. 解析/索引/embedding 作为可重试的派生任务；
6. 删除先标记 tombstone 和保留期，再异步清理 blob/index；审计记录保留最小不可逆证据。

### 4. 检索边界

v0.1 的材料优先和事实保真要求决定了检索顺序：

1. **结构化精确检索**：项目/版本/来源/页码/表格行/事实 ID/数值单位；这是来源核验和审计的优先路径；
2. **词法检索**：标题、段落、表格文本、备注和来源标签；PostgreSQL `tsvector`/GIN 或明确的 `pg_trgm`/中文 tokenizer 适配器；不能默认英语 stemming 能解决中文；
3. **可选向量检索**：只返回带 `source_id`、chunk locator、版本和权限过滤的候选，必须与词法/结构化结果融合；
4. **重排**：需要在同题测试集上证明召回和事实引用收益后再引入，不以向量相似度代替来源；
5. **上下文装配**：先按 workspace/project/version 权限过滤，再按来源/页码/事实完整性装配给模型。

推荐 v0.1 先用 PostgreSQL 的关系、结构化字段、全文/模糊索引和固定来源定位；embedding 通过 `VectorIndex` 接口留口。如果需要向量，优先评估 pgvector 同库方案：官方资料支持 exact search、HNSW/IVFFlat 和 metadata filter；Qdrant 作为规模或用户已有基础设施的扩展。

索引一致性：每次材料版本提交产生 `index_version`；索引构建成功前状态为 pending，不得静默使用旧索引；删除/撤销版本必须同步删除或屏蔽词法和向量命中；provider/model 看到的引用必须回到 `source_fact`/`source_locator`。

### 5. ZIP/PPTX 安全模型

PPTX 是 ZIP/OPC 包，不能当普通图片或文本上传：

- 限制压缩包原始大小、解压后总大小、单 entry 大小、entry 数、嵌套深度和处理时间；
- 规范化 entry 路径，拒绝 `..`、绝对路径、重复冲突路径、符号链接和超出工作目录的写入；
- XML 解析禁用外部实体、外部 DTD、网络访问和不受控 schema 下载；
- 读取 `[Content_Types].xml`、`.rels` 和目标 part，检查关系闭包、循环、外链、宏、OLE、嵌入文件和未知部件；
- 不执行宏、OLE、ActiveX、外部链接、脚本或媒体；必要时把它们隔离为“存在但不处理”的风险对象；
- LibreOffice/预览器/解析器运行在无特权 worker，限制 CPU、内存、临时盘、进程数和网络出口；
- 任何安全扫描失败进入 `UNSAFE_INPUT`/人工复核，不自动重试、不自动交付；
- 不把“能 unzip”当作“PPTX 安全/可编辑”；包校验、关系检查、语义探针和目标软件验收分层执行。

### 6. 备份、恢复和删除

默认单节点运维基线：

- PostgreSQL 定期逻辑备份，生产部署可选物理/PITR；
- 文件卷与数据库 manifest 同步快照，恢复时先还原数据库/manifest，再校验 blob hash；
- 审计报告、原稿、版本和授权记录不能只存在临时目录；
- 每次升级前生成数据库备份、schema migration 版本和 blob 清单；
- 备份恢复演练必须验证用户、项目、权限、任务、artifact、审计和索引重建；
- 初始目标按票 13 的参数待校准，建议以 RPO 24h/RTO 4h 作为单节点基线，不对所有企业部署做统一保证；
- backup 中的 provider key、用户材料和字体同样是敏感数据，必须加密、限制访问并写入保留策略。

迁移策略：

- 不提供 SQLite profile，也不把本地文件目录作为生产迁移起点；所有受支持部署使用 PostgreSQL 和 S3-compatible BlobStore 合同；
- PostgreSQL schema 使用版本化迁移，禁止应用启动时隐式破坏性变更；
- 不同 S3-compatible 实现共享 `BlobStore` 合同，迁移通过 hash manifest 校验，不通过目录复制假设；
- `pgvector`/Qdrant/Meilisearch 索引都可删除重建，不能把迁移依赖写入交付事实。

### 7. 长期生产基线与扩展方案

**生产基线**：

```text
web/api/worker
    ├── PostgreSQL: facts, versions, tasks, audit, lexical metadata
    └── S3-compatible object storage: immutable source/material/artifact blobs
```

- PostgreSQL 和生产对象存储从第一天进入受支持部署；
- 默认实现、备份、版本、生命周期、加密和单节点 Compose 形态由全景架构票选定；
- 不提供 SQLite、本地目录或临时数据库作为产品 profile；
- 不强制独立向量 DB，但 `VectorIndex` 必须可选、可重建、可替换；

**扩展方案**：

- `PgVectorIndex`：同库向量检索，适合强 metadata filter；
- `QdrantIndex`：大规模/已有向量平台，使用 source/version/policy payload filter；
- `SearchIndex`：用户已有 Meilisearch/OpenSearch/Tantivy 服务，作为重建投影；
- 读副本、分离 worker、对象存储集群和索引服务只有在容量/恢复/维护证据完成后启用。

### 8. 数据候选取舍

- **PostgreSQL**：**长期生产基线**。事实、权限、审计、版本和事务首选；RLS 只能作为 defense-in-depth，应用层 workspace/project 授权仍必须存在。
- **SQLite**：**淘汰**。不进入开发、演示、生产或迁移 profile；其零配置优势不能抵消多人、worker、审计和长期升级返工。
- **pgvector**：**适合二开/可选投影**。同库过滤和备份简化；embedding 模型变化必须版本化。
- **S3-compatible object storage**：**长期生产合同**。默认实现待全景架构票选定，不把本地目录作为可交付替代。
- **Qdrant**：**后续扩展**。Apache-2.0、payload/filter/local mode 有价值；不提前引入第二事实库。
- **Local filesystem**：**仅测试/临时 scratch**。不得作为生产 BlobStore。


### 9. 硬淘汰条件

- 把原稿或 PPTX 包只存数据库 JSON/图片，无法保留原始字节和关系；
- 文件、索引或审计没有 workspace/project 权限边界，或下载 URL 暴露永久宿主路径；
- 数据库/BlobStore/索引没有 hash、版本、删除和恢复策略；
- 向量索引是唯一来源，无法返回稳定 source locator、版本和事实引用；
- 索引或缓存不可重建，导致换 embedding/provider/搜索引擎必须丢失业务数据；
- ZIP/XML 处理没有解压比、路径穿越、外链、宏/OLE、资源和网络隔离；
- 默认组件许可证不兼容 MIT 主线，或许可证/归档状态不明却被打包进默认部署；
- 为低规模 v0.1 强制引入多个分布式服务，且没有容量、恢复和运维证据；
- 删除、备份、迁移会静默覆盖原稿、审计或用户授权记录。

### 10. 最小验证计划

1. **并发事实测试**：PostgreSQL + 生产 BlobStore 下两个成员同时修改大纲/确认阶段，验证事务、版本冲突、幂等、权限和对象一致性。
2. **BlobStore 契约测试**：至少对两个 S3-compatible 实现/配置做 upload/download/range/hash/atomic commit/delete/restore fixture；本地文件只用于单元测试，不作为产品 profile。
3. **索引重建测试**：删除词法和向量索引，仅凭 material/source/version/blob manifest 重建，结果包含同样的来源定位和权限过滤。
4. **检索质量测试**：中文数字、单位、表格行、同义词、页码、版本和跨项目同名事实；比较结构化/词法/embedding 结果，记录召回、误引和延迟。
5. **恶意包测试**：压缩炸弹、路径穿越、超大 XML、外部实体、坏关系、宏/OLE、外链和损坏图片；验证隔离、超时、资源释放和审计。
6. **备份恢复演练**：数据库、blob manifest、原稿、artifact、审计和权限完整恢复；故意缺一个 blob，系统必须报告不可交付而不是静默生成。
7. **删除与留存测试**：成员删除项目、管理员执行保留期清理、撤销版本和重建索引，验证审计链与数据物理清理边界。
8. **容量基线**：单节点下材料上传、解析、生成、预览并发运行，测量 DB、blob、临时目录和索引增长，不先宣称多节点能力。
