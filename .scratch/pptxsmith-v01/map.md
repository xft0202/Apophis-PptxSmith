# Wayfinder：PptxSmith v0.1 工程启动规格

## Destination

定稿一份可以交给后续工程会话执行的 **PptxSmith v0.1 工程启动规格**：影响首期产品价值、技术路线、用户体验、质量验收和开源维护的决定全部有答案、有证据、有取舍；没有关键未知会迫使工程过程中临时改方向。

## Notes

> **证据状态（2026-09-25 所有者纠正）**：本项目处于**立项前、打地基阶段**。
> 本地图与所有关联研究文档里的内容都是**当前证据下的工作假设**，不是定论，
> 随时可被更强的证据推翻。文中「冻结」「不可逆」「决策」等措辞一律按
> 「在获得更强证据前按此推进」理解。

- **博采众长 → 必须落到「吸收分类」字段上（所有者 2026-09-26 再次强调，且此为强制执行）**：
  原则不是口号，**每份候选比较 / 每个外部样本 / 每张研究票的产出，都必须逐项标注吸收分类**，
  缺这项即视为**未完成**。五个取值（CONTEXT.md 与票 13 的固定口径）：

  | 分类 | 含义 | 对主线的后果 |
  | --- | --- | --- |
  | **可直接复用** | 作为依赖引入，许可证与维护均达标 | 进主线，仍须过 G1–G5 与交付闸门 |
  | **适合二开** | 以它为基座改造，或包一层适配 | 进主线，须写明改造边界与上游跟进策略 |
  | **仅可借鉴** | 只学设计思想 / 协议 / 交互，不引代码 | **不进依赖树**，须写明借鉴点 |
  | **必须隔离** | 有价值但许可证或风险不允许进核心 | 只能进程隔离或研究样例，写明隔离边界 |
  | **应当淘汰** | 不满足目标或风险过高 | 出候选池，写明淘汰理由 |

  **分层要求（避免用一句话概括整个项目）**：同一外部样本往往**各层结论不同**，
  必须分开判定，不得笼统。例如 SANDUN：交互与前端 = 仅可借鉴；
  其规划层的结构化图表数据 = 仅可借鉴；其导出路线 = 应当淘汰（实测与 A 级语义冲突）。

  **自检**：任何比较类产出的收尾必须回答「这五个分类分别是谁」。
  只有「入场/淘汰」二元判定 = 未贯彻本原则。

- **部署硬前提（所有者明示，已确认）**：**单机部署是唯一形态，与使用者人数无关。**
  一人自用或一人部署给多人共用，都是单机 Docker Compose。不存在「多人使用所以要上集群」
  的推理。需要 Kubernetes / 分布式存储 / 集群消息总线 / 平台团队才能运维的组件直接出局。
- **目标专注（所有者明示，已确认）**：**只把 PPTX 这件事做到彻底**，解决打工人的真实痛点。
  不是通用平台，不做面子工程。裁判只有一条：**它让 PPTX 做得更彻底吗**？
- **入场硬门（票 13 G1–G5）**：生态活跃度是**入场资格**，不是评分项。生态冷门、
  无人维护、单点作者、无版本策略的候选**直接淘汰，不做能力评估**。理由：长期开源项目
  的代码必须有人接得住。（此前误把「stars 高不能当答案」用于忽略活跃度，已纠正：
  活跃度管入场，能力管胜负，顺序不可颠倒。）

- 领域：中文商务 AI PPTX，首期为公司内部工作汇报、培训、展示；听众是领导与同事。
- 当前阶段：只做研究、决策和必要的最小验证；不在本地图内直接建设 v0.1。
- 工作方式：按模块逐个清；每张票只解决一个决定/调查；解决票后再推进下一张。
- 必读：`VISION.md`、`CONTEXT.md`、`docs/企业级工程流程与项目治理.md`、`research/2026-09-24_仓库全量审查.md`、四份 v2 报告、相关 `docs/adr/`。
- 当前阶段门：先冻结架构决策驱动和质量属性，再按前端、后端、文档引擎、任务/模型、数据文件、解析/渲染、安全供应链、测试/可观测/发布逐模块调查，最后做总架构决策。
- 原则：证据分级（官方声称/第三方实测/本项目实测）；技术优先复用成熟方案，必要时二开；每个模块至少横向比较多个候选，并明确可直接复用、适合二开、仅可借鉴、必须隔离和应当淘汰的部分；只有没有合适基础时才自建。
- 技术终决纪律：先围绕核心目标定义淘汰条件，再做候选比较；在同一兼容性语料库和 PowerPoint/WPS 交付门通过前，不接受任何语言或库为最终答案。
- **架构地基规则**：单节点/一键部署不等于临时技术；生产数据库、对象存储、备份、身份、任务恢复、审计和供应链从第一天按长期合同建设，禁止把 SQLite、本地生产文件、仅进程内队列或计划迁移组件放入受支持路径。
- 决策票类型：`grilling` 需要所有者判断；`research` 由联网/源码调查解决事实；`prototype` 用具体低保真产物帮助决策；`task` 只做阻塞决策的准备工作。
- **研究实验物豁免**（所有者 2026-09-25 授权）：为执行 Spike D 而生成的二进制 fixture 与四套架构的最小验证原型，允许存在于 `research/experiments/` 并明确标注「可丢弃」，以换取真实恢复/升级/验收证据。该豁免只覆盖夹具与验证原型，不授权创建生产脚手架、生产 monorepo 或任何进入 v0.1 主线的代码。
- **环境约束**（本项目实测 2026-09-25，详见 `docs/目标软件验收矩阵.md` 与 ADR-0013）：
  - 唯一部署形态是 **Linux 服务器 + Docker Compose**；用户安装项恒为「Docker + 自己的模型 key」，零其他安装；
  - **验收宿主 ≠ 部署宿主**：Windows 只是维护者侧质检与测量仪器，不进生产镜像/依赖树/安装步骤；脚本与产物隔离在 `research/experiments/`；
  - 唯一验收宿主是本机 **WPS 演示 11.8.2.8411**（`F:\WPS Office\11.8.2.8411\office6\wpp.exe`）；**本机无 Microsoft PowerPoint**，该侧已按方案 A 接受为未验证；
  - **不建第二台机器**：S4/S5 所需的 .NET SDK、Rust、Temporal/Restate/Hatchet、PostgreSQL、对象存储、身份与 provider gateway 全部在 Docker Desktop（29.7.2 / Compose v5.4.0 / 6 CPU / 8 GB）容器内运行，与生产形态同构；
  - **不要在 Windows 宿主机上验证架构或数据库**，容器优先；
  - WPS 的 COM 自动化服务器注册在 **32 位（WoW6432Node）** 节点：自动化验收脚本须以 x86 目标编译或经 32 位宿主调用；`PowerPoint.Application` 与 `KWPP.Application` 指向同一 `wpp.exe`，脚本必须显式断言宿主身份，不能靠 ProgID 判断。

- **交互与前端基线（所有者 2026-09-26，经澄清）**：所有者认可 SANDUN 的
  **交互方式与前端设计**，作为**借鉴样本而非照抄对象**——
  「就按照 sandun 的基础上来，是我喜欢的」；随后澄清：**指的是交互方式与前端设计**，
  **不是照抄**。

  **借鉴范围（做什么像它）**：分阶段流水线的交互节奏、阶段产物分离的呈现、
  逐页来源可见、风格选择与风格库的用法、项目连续性、过程可回看。
  **借鉴方式**：学其组织结构与信息排布，**不复制其视觉细节、文案、组件实现**。

  **不随基线一并接受的（两条，均有实测支撑）**：
  1. **导出路线**：实测其导出产物 0 个原生图表部件、0 个嵌入工作簿、0 个原生表格、
     0 个备注页，411 个形状 + 307 个文本 run（图表被展平成形状拼图）——
     与「A 级原生语义」承诺直接冲突；
  2. **字体处理**：其产物把 CSS 字体族名 `system-ui` 带进 PPTX，
     目标机器无此字体将被静默替换——与「中文零溢出」承诺直接冲突。

  → 实证见 `research/2026-09-26_SANDUN真实流程与产物实证.md` 第 4–5 节、
  `research/2026-09-25_SANDUN全量解剖与反超清单.md` 第 8–9 节。
  → 本条**只约束交互与前端层**，不构成任何导出、引擎或实现语言的决定。
- **插图生成策略（所有者 2026-09-26，经澄清）**：本项目使用图像模型（Image 2 一类）
  生成**插图与配图素材**——**不是整页位图**。

  **确切含义**：生图产出**一张图**，作为素材放进页面；它在 PPTX 中是一个
  **原生 `<p:pic>` 图片对象**（本身可替换、可裁剪、可移动），
  **页面的文字、图表、表格仍是原生语义对象**，不受影响。

  **与 SANDUN 的 Image 2 是两件事**（不得混同）：
  | | SANDUN 的 Image 2 | 本项目 |
  | --- | --- | --- |
  | 生图产物 | **整页位图**（把整页画成一张图） | **插图素材** |
  | 页面内容 | 文字/图表全被烤进图里 | 文字/图表仍是原生对象 |
  | 可编辑性 | 整页不可编辑 | 只有那张图不可编辑，页面照旧 |
  | 与 A 级语义 | **直接冲突** | **不冲突** |

  **对交付闸门的含义**：审计报告按既有 A/B/C/D 分级如实标注——
  插图即 **C 级（局部图片）**，**不得**因含插图就把整页降级。
  这正是 CONTEXT.md 里 C 级定义的用途。

  **结论**：本策略**不牺牲任何既有承诺**（A 级原生语义、中文零溢出均保住），
  也不改变导出路线与引擎选择（仍由票 23 回答）。
- [引擎基座复用盘点](issues/02-引擎基座复用盘点.md)：**过活跃度硬门后仅 2 个候选**——Open XML SDK（C#，MIT）与 Apache POI（Java，Apache-2.0）；ShapeCrawler（头号88%）、PptxGenJS（停更15个月）、python-pptx（停更两年）、ppt-master（★56k但头号98%）、unioffice（商业许可）、officegen、gopptx/cjk-pptx-engine 全部淘汰；**Go 侧无过门候选**，该比较路径关闭；过门只表示获得被比较资格，**实现语言仍未锁定**。
- [当前架构假设](issues/22-当前架构假设_单机自托管与PPTX专用流水线.md)：家族级形态冻结为「控制面 + durable workflow + 专用文档流水线 + PostgreSQL 事实库 + S3-compatible 对象合同 + 长期身份/审计/观测边界」；列出 9 条不可逆合同、7 类可延后但契约形状固定的实现、5 类明确排除的形态；不预判任何实现语言。单机部署前提已写入第 1.1 节。
- [验收宿主与部署宿主分离](../../docs/adr/0013-验收宿主与部署宿主分离.md)：Linux Docker 是唯一部署形态，Windows 只是维护者侧质检与测量仪器；当前唯一验收宿主是 WPS 演示 11.8.2.8411，本机无 Microsoft PowerPoint，已按方案 A 接受为未验证并以保守余量与审计明示补强。

## Not yet specified

- 受控补丁何时重启、首个支持对象边界与旧稿保护承诺；
- 从既有 PPTX 提取风格包的输入协议和授权边界；
- **Microsoft PowerPoint 验收宿主的长期方案**：是否引入第二台机器/VM 与正版 Office 授权，或长期只以 WPS 为主验收目标；留待 01 总架构定稿时决定（当前按方案 A 接受未验证）；
- **WPS 版本跨度**：11.8.2.8411 属较早期专业版，与新版个人版/专业版的行为差异未测；若目标用户多在较新版本，校准与探针需在新版本复跑；
- 风格包 v1 以外的场景包（党政、咨询、学术、培训等）及发布标准；
- 模型成本预算、并发、任务取消与失败重试的产品策略；
- Rust 客户端的离线能力、同步协议与何时启动；
- 社区治理、版本支持周期、贡献者晋升和安全响应细则。

## Out of scope

- v0.1 的移动端与原生 Windows/macOS 客户端；
- v0.1 的商业 SaaS、积分、订阅、邀请裂变；
- v0.1 的自由画布编辑器；
- v0.1 的已有 PPTX 受控补丁入口；
- v0.1 的 Kubernetes / Argo / Helm / GitOps / Camunda 类企业平台形态；
- v0.1 的分布式存储与搜索（Ceph / CockroachDB / OpenSearch）与集群消息总线；
- v0.1 的企业 IdP 全家桶（SCIM / LDAP 联邦 / 多租户运营）与 provider gateway 产品矩阵；
- v0.1 的 durable workflow runtime 横评（先证明 PPTX 链路需要它，再谈引入）；
- 任何与 PPTX 核心链路无关的平台型组件（无论其技术上多先进）；
- 任何未经同题测试和交付闸门验证的“全格式/全对象/全平台”承诺。
