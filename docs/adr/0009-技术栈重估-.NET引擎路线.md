# 技术栈重估：文档引擎改为 .NET（Open XML SDK），前端保留 Next.js，Rust 客户端按服务型壳预留

Status: proposed (2026-09-24，待所有者确认；若确认则 supersede ADR-0003)

所有者对 ADR-0003 的 TS 全栈选型明确不满意；换位重估 + Spike C 同题实测（research/experiments/2026-09-24_spike-C_dotNET路线_实测记录.md）后提出：本项目五年期核心资产是**OOXML 文档引擎**（生成/审计/受控补丁/保真），该引擎不应寄托于单维护者的 JS 渲染库。新方案：

- **后端与文档引擎：.NET 8 + ASP.NET Core + DocumentFormat.OpenXml（MIT，微软官方维护，全 PresentationML schema 强类型覆盖，自带校验）**；
- **中文量字：SkiaSharp**（HarfBuzz 级整形；Spike C2 实测与 fontkit 数值完全一致）；
- **前端：Next.js/React**（纯 UI 层，与引擎通过 API 解耦；未来 Rust 客户端以 Tauri 壳复用同一 Web UI 与服务端 API，**引擎无需重写**——所有者明示 Rust 客户端为远期计划）；
- 部署不变：Linux + Docker（ADR-0007）；运行时镜像 ~210MB，可接受。

## Considered Options

- 维持 TS 全栈（ADR-0003）：被否。Spike A 证明 PptxGenJS 能"生成"，但它**不能读、不能补丁、不能校验既有稿**——读/补丁/审计恰是本项目的护城河科目；footgun 清单长；单维护者风险。
- Rust 核心引擎（与未来客户端统一语言）：被否于当前。OOXML crate 生态不成熟，等于先造引擎再造产品；且客户端为服务型壳时引擎根本不需要进客户端。留作远期复议项（若出现离线刚需）。
- Java + Apache POI：维持 ADR-0003 的否决。

## Consequences

- ADR-0003 作废（若本 ADR 被确认）；Spike A/B 的 TS 实验价值不损失：它们验证的是产品承诺而非语言。
- 需要自建"SDK → 语义对象模型"的包装层（C3 证实 SDK 从零建包无电池included，工作量集中在这一层）；该包装层反而是我们真正的自有资产。
- AI 辅助开发对 C# 友好；OOXML 的啰嗦由包装层吸收，不扩散到业务代码。
- 贡献者生态小于 TS 圈，用文档质量与社区运营补偿（VISION.md 承诺项）。
