# 验收宿主与部署宿主分离：Linux Docker 是唯一部署形态，Windows 只是维护者侧质检与测量仪器

Status: accepted (2026-09-25，所有者确认方案 A)

本项目此前在讨论验收时产生了真实歧义：把「在哪里验证成品 PPTX」与「产品在哪里运行」混为一谈，进而可能被误读为产品需要 Windows 或需要用户安装办公软件。本 ADR 一次性切开这两个概念，并登记当前的宿主现实。

## 决定

1. **唯一部署形态是 Linux 服务器 + Docker Compose**（不变，见 ADR-0007）。用户新增安装项恒为「Docker + 自己的模型 key」，**零其他安装**。
2. **验收宿主是维护者侧的质检工具与测量仪器**，与部署拓扑无关，**永不进入生产镜像、Compose 依赖、运行时依赖树或用户安装文档**。
3. **当前唯一验收宿主是本机 Windows 上的 WPS 演示 11.8.2.8411**；本机无 Microsoft PowerPoint，该侧验收**未做**，按保守补强与明示边界处理（方案 A，详见 `docs/目标软件验收矩阵.md`）。
4. **容器化验证环境（Docker Desktop 内的 Linux 容器）是 Spike D 四套架构、数据库、对象存储、身份与 provider gateway 夹具的执行环境**，与生产形态同构，优先于在 Windows 宿主机上验证。
5. **Office 相关的 SDK、COM 自动化与脚本一律隔离在 `research/experiments/`**，标注「可丢弃」（ADR-0006）；依赖边界检查由票 19 强制。

## Considered Options

- **建独立 Windows 验收机/VM 装正版 Office**：否决于当前。需要额外授权与维护成本，且所有者明确只有本机一台 Windows；相关能力留作长期议题，不阻塞 v0.1。
- **完全放弃目标软件验收，只信 LibreOffice 渲染**：否决。票 03 已冻结「校验器不是渲染器，渲染器不是 PowerPoint」，LibreOffice 只能作独立信号，不能代表用户实际软件——放弃它等于让铁三角承诺失去验收依据。
- **把 Office SDK 或 WPS 自动化写成产品依赖**：否决。会让用户被迫安装办公软件，直接违反「部署在自己手里、Docker 一条命令」的承诺。
- **在 Windows 宿主机上跑架构验证与数据库**：否决。生产是 Linux 容器，在 Windows 宿主验证会引入环境差异，反而降低证据可信度。

## Consequences

- 目标软件验收矩阵成为交付闸门的组成部分：`docs/目标软件验收矩阵.md` 记录宿主现实、32 位 COM 前提、探针规格、失败清单格式与版本记录纪律。
- **降级必须记账**：铁三角的「原生语义」「中文零溢出」当前只有 WPS 半边实测证据；Microsoft PowerPoint 一侧标为**未验证**，并在每份稿的审计报告与 v0.1 发布说明中明示。
- **保守补强替代缺失宿主**：量字安全余量按更保守一侧取值（PowerPoint 外部校准系数与 WPS 实测值中更保守者），余量宁可偏大；外部系数证据级别标为第三方实测，不得标为本项目实测。
- **WPS 的 32 位 COM 注册**是自动化验收脚本的硬性前提（脚本须以 x86 目标编译或经 32 位宿主调用）；`PowerPoint.Application` 与 `KWPP.Application` 在本机指向同一 `wpp.exe`，脚本必须显式断言宿主身份，不能靠 ProgID 判断宿主。
- 用户安装步骤不因此 ADR 发生任何变化；本 ADR 不涉及、不预判任何技术选型（ADR-0003 仍为 `challenged`，ADR-0009 仍为 `proposed`）。
