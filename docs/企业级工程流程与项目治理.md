# 企业级工程流程与项目治理

*适用于 Apophis-PptxSmith 长期维护开源项目；不是临时开发约定。*

## 1. 项目阶段模型

项目按以下阶段推进，阶段必须按顺序通过，不允许边实现边补决策：

1. **产品与问题定义**：明确用户、场景、痛点、成功标准、非目标和证据边界。
2. **架构决策驱动**：把产品目标转成可衡量的质量属性场景、约束、优先级和淘汰条件。
3. **技术调查**：按模块调查成熟方案、源码、许可证、维护状态、集成成本和真实边界。
4. **架构评审**：比较候选方案，做必要的最小验证，形成 ADR 和架构基线。
5. **详细设计**：冻结领域模型、接口、数据生命周期、错误模型、测试夹具和迁移策略。
6. **受控实现**：按已批准设计开发；新增需求或改变边界必须走变更评审。
7. **验证与硬化**：功能、兼容性、安全、性能、可观测、升级、恢复和真实办公软件验收。
8. **发布与运营**：版本说明、迁移说明、回滚方案、支持范围、漏洞响应和社区反馈闭环。

当前项目仍处于第 2–3 阶段之间，不能进入第 5 阶段，更不能进入生产实现。

## 2. 决策与证据纪律

- 每个不可逆或高成本决策必须有一个 ADR；一个决策只能有一个权威位置。
- 每个候选技术必须区分：官方声明、源码证据、本项目实测、推断。
- “有 API”不等于“满足产品需求”；必须映射到真实用户任务和验收场景。
- “测试通过”必须写明测试夹具、目标软件、字体、版本和未覆盖范围。
- 研究失败必须记录失败原因，不得用缺失证据填成乐观结论。
- 候选技术必须经过复用/二开评估；禁止为了体现自主开发而重造已有能力。
- 所有模块必须贯彻“博采众长，取其精华，去其糟粕”：至少比较多个成熟候选，明确可复用、可二开、可借鉴、应隔离和应淘汰的边界，并把组合后的验证矩阵、升级成本和替换路径纳入决策；不能用单一项目的 README、单项 benchmark 或语言偏好替代架构证据。
- **长期无返工规则**：受支持部署不得引入计划迁移的临时数据库、文件后端、权限、任务恢复、事实存储或 provider 适配。单节点/一键部署只允许简化安装与运维入口，不允许降低生产地基；所有新增组件必须说明五年维护、备份恢复、升级、替换和社区接手成本。

## 3. Definition of Ready

任何模块进入详细设计前，必须具备：

- 明确的用户问题和使用场景；
- 输入、输出、边界和失败行为；
- 质量属性与可测量验收条件；
- 候选方案及淘汰理由；
- 许可证、维护状态和供应链风险；
- 至少一份可复现的验证计划；
- 与已有 ADR、CONTEXT 和报告无冲突的变更记录。

## 4. Definition of Done

任何模块称为完成，必须同时满足：

- 需求追踪关系完整：问题 → 需求 → 设计 → 实现 → 测试 → 发布证据；
- 自动化测试和真实样本测试通过；
- 失败、降级、取消、重试和回滚行为明确；
- 安全、许可证、性能和可观测检查完成；
- 文档、迁移、运维和贡献者说明同步；
- 没有未说明的临时实现、隐藏 fallback 或“以后再补”的核心能力。

## 5. 架构变更控制

- 未通过架构评审的技术只能存在于隔离研究实验中，不得进入主线。
- 发现新候选足以改变结论时，必须重新打开原研究票或 ADR；不能为了保持流程整洁而压制新证据。
- 多语言、多引擎、多渲染器都会扩大测试矩阵；增加组件必须说明新增价值和新增验证成本。
- 未来 Rust 客户端、离线能力、旧稿补丁等远期目标必须作为约束参与设计，但不能提前把未验证能力塞进 v0.1。

## 6. 项目级质量底线

- 交付文件必须真实可用，不以“能生成”代替“敢拿去汇报”；
- PPTX 语义、中文排版、事实保真、范围保护和交付审计属于产品质量，不是可选技术细节；
- 任何默认值必须能解释，任何不支持的对象必须明确拒绝或降级；
- 以用户口碑、真实任务成功率、返工时间和贡献者可接手程度衡量项目，而不是只看代码量或功能数量。
